# Version 1.6 — Beta Deployment Plan

**Type:** Documentation and product-planning exercise. No application code
was written or modified to produce this document. Written directly on the
already-checked-out `v1.6.0-ux-polish-phase-1` branch.

**Scope of this beta, stated up front because it governs every section
below:** this beta runs **entirely in SIMULATED / Paper Trading mode,
across all three engines.** No live broker connection, no live market/
fundamentals data provider, and no real capital are in play at any point.
This is not a beta-specific restriction invented for this document — it is
simply the platform's current, unchanged state: `docs/Production-Readiness-Report.md`
confirms Sprints 75 (Engine 1 live data) and 76 (Options Income live
broker) remain **blocked** on credentials that have never been present in
any session, and the Trading Engine's own live-data provider was
explicitly, permanently deferred by the project owner at Phase 3's close.
Nothing in this plan proposes resolving any of that — a beta program is
exactly the wrong time to also be debugging a first-ever live-data cutover.

**Relationship to existing operational documentation:** this platform
already has a full production deployment/operations doctrine —
`docs/Production-Rollout-Plan.md` (the general go-live procedure),
`docs/Operations-Handbook.md` (day-to-day operations), `docs/Incident-Response-Runbook.md`
(per-alert diagnosis and recovery), and `docs/Production-Readiness-Report.md`
(current-state assessment). This document does not repeat that material —
it is the **beta-scoped subset and beta-specific additions** on top of it.
Read this document first for "what does a beta deployment specifically
need," then the four documents above for full operational depth.

## 1. Environment Preparation

- **Topology:** a single environment tier for this beta — no separate
  staging/production split is required, since the beta itself *is* the
  first real-user-facing exposure of this build. Frontend and backend
  should be served from **the same origin** to sidestep the one genuinely
  unresolved configuration gap in this platform (`CORS_ALLOWED_ORIGINS`,
  flagged unresolved since Phase 1 Sprint 6 — a split-origin deployment
  would require the project owner to first supply a real production
  frontend URL, which has never happened in any session; a same-origin
  deployment needs no value here at all, per `.env.example`'s own
  documentation of that variable).
- **Branch/commit:** deploy from the specific, approved commit the project
  owner designates for beta start — not a moving branch head. Record the
  exact commit hash as part of the deployment record (§1.3 of
  `docs/Production-Rollout-Plan.md`'s own convention).
- **Core runtime variables** (`.env.example` is the authoritative list —
  confirm every one of these is set before starting the process):
  - `DATABASE_URL` — points at a real, dedicated beta database. **Do not
    reuse a development/test database for beta** — beta users are real
    people creating real (simulated) trades, journal entries, and
    watchlists; that data should not share a database with disposable
    local test runs.
  - `NODE_ENV=production` — gates several behaviors correctly (pino
    transport formatting, the rate-limiter's test-mode skip).
  - `PORT` / `BASE_PATH` — set per the hosting platform's own requirements.
    The application intentionally exits immediately at startup if `PORT`
    is unset — a fast, loud failure, not a bug to route around.
  - `LOG_LEVEL=info` — beta-appropriate verbosity; `debug` would be too
    noisy for a multi-day, multi-user run, and too quiet at `warn`.
- **Auth variables:**
  - `BETTER_AUTH_SECRET` — a fresh, real value (`openssl rand -base64 32`),
    never a value that has appeared in any test run or this conversation.
  - `BETTER_AUTH_URL` — the beta environment's own real public base URL.
  - `REQUIRE_AUTH=true` — **this must be explicitly set for beta**, unlike
    the unset/false default this platform has run under for most of its
    development history. Beta means multiple real, distinct users; leaving
    this unset would route every unauthenticated request to the
    legacy-owner stand-in account, which is exactly wrong for a real
    multi-tenant beta. Confirm sign-in/sign-up work end-to-end against the
    beta database before announcing the beta start date.
- **Rate limiting variables:** leave at their Sprint 52 measured-baseline
  defaults (`RATE_LIMIT_MAX_REQUESTS=300`, `AUTH_RATE_LIMIT_MAX_REQUESTS=20`,
  both per 60s) — a 5–8-user beta (see `docs/v1.6.0-Beta-Operations-Guide.md`)
  will not come close to tripping either threshold under normal use; do not
  pre-emptively raise or lower them without a real reason observed during
  the beta itself.
- **Provider credentials — deliberately left unset for this beta:**
  `ALPACA_API_KEY`/`ALPACA_API_SECRET`, `FMP_API_KEY`/`ALPHA_VANTAGE_API_KEY`.
  This is not an oversight — setting any of these would silently change
  what beta testers see (a live data path instead of SIMULATED), which
  this beta is explicitly not testing and has not been verified for. If
  any of these happen to be present in the target hosting environment for
  an unrelated reason, confirm the relevant `*Connected` settings field
  reads `false` for every beta account before go-live.

## 2. Database Setup

- Provision a fresh Postgres instance dedicated to the beta (see §1 —
  never reused from dev/test).
- Apply **every** manual migration in `lib/db/manual-migrations/`, in
  strict numeric order (46 files as of this writing, `000` through `045`
  — confirm the actual current count in the repository at deployment time,
  since this platform ships new, additive migrations frequently and this
  number will already be stale by the time beta actually starts). Every
  one of these is hand-reviewed, additive-first (nullable → backfill →
  enforce-not-null per `CLAUDE.md` rule 7) — never apply via a raw,
  unreviewed `drizzle-kit push` against this database.
- After applying migrations, run `drizzle-kit push` in non-force,
  diff-only mode and confirm it reports **zero pending changes** — any
  drift here means a missed migration, and must be understood before
  proceeding, never silently pushed through.
- **No seed data beyond what the application itself creates.** Every new
  beta signup automatically receives 3 example trades and a computed
  Portfolio Health Score via the existing `ensureSeedTrades()` behavior —
  this is intentional, unmodified, pre-existing product behavior, not
  something this deployment plan needs to set up. (Its lack of an
  on-screen explanation to a first-time user is a known, disclosed UX gap
  — see `docs/v1.6.0-Known-Limitations.md` and Item 5 of the Final Report's
  Top 10 post-beta list, not something to fix as part of deployment.)
- Confirm the database is reachable from the deployed application process
  before proceeding to §5 (Smoke-Test Checklist) — `GET /api/monitoring/status`'s
  `database.connected` field is the authoritative check (§6 below).

## 3. Backup Strategy

Directly follows `docs/Production-Rollout-Plan.md` §4, scoped for a beta's
real but modest data volume (a handful of users, days to a few weeks of
activity):

- **Before the beta starts:** take one full logical backup (`pg_dump`)
  immediately after migrations are applied and before any real user
  signs up, so there is always a clean "beta day zero" restore point.
- **Daily, for the duration of the beta:** a scheduled daily `pg_dump`
  (or the hosting platform's own managed backup feature if available —
  prefer that over the manual procedure wherever it exists), retained for
  the full duration of the beta plus at least one week after it ends, in
  case a post-beta question requires looking back at exactly what a
  tester saw on a specific day.
- **Before any mid-beta deployment** (a hotfix, see §4): an additional,
  out-of-band backup immediately before applying it — non-negotiable, per
  `docs/Production-Rollout-Plan.md` §1.2, even for a "trivial" change.
- **Storage:** genuinely independent of the primary database instance
  (separate object storage or the hosting platform's own retention),
  never only on the same disk/volume as the live beta database.
- This beta introduces no new backup mechanism — it uses the same
  procedure `docs/Production-Rollout-Plan.md` §4.1 already documents,
  scoped to a shorter real-world retention window than a production
  deployment would need.

## 4. Rollback Plan

- **A code-only issue found mid-beta** (the most likely case — this
  platform's own beta-relevant risk is almost entirely UX/wording/
  navigation, not data-corrupting logic): `git revert` the offending
  commit(s), rebuild, redeploy, following `docs/Production-Rollout-Plan.md`
  §6.1 in full. Never a force-reset on the beta branch.
- **A migration-involving hotfix:** follow `docs/Production-Rollout-Plan.md`
  §6.2 — the vast majority of this platform's migrations are additive-only
  (new nullable columns/tables), so a code-only rollback is almost always
  sufficient; only a `NOT NULL`-enforcing or data-mutating migration would
  ever require restoring from the pre-deployment backup (§3 above) instead
  of attempting a hand-written down-migration.
- **A tester reports something that looks like cross-account data
  exposure:** treat as the single highest-priority beta incident type,
  full stop. Disable the affected account(s)' sessions if a targeted
  response is possible, otherwise take the beta environment offline
  entirely rather than leave a real tenant-isolation gap live for even a
  short window, then diagnose against `lib/tenantIsolation.test.ts`'s own
  established coverage before resuming. See `docs/v1.6.0-Beta-Issue-Triage.md`
  §Critical for the full severity/response definition.
- **This beta has no automation-kill-switch rollback scenario to plan
  for** — since the beta runs entirely in SIMULATED/Paper Trading mode
  with no live broker connected for any account, the kill switch
  (`autoExecuteEnabled`/`autoAdjustEnabled`) still exists and functions
  exactly as documented (`docs/Incident-Response-Runbook.md` §2.2,
  `docs/Operations-Handbook.md` §6.1), but there is no real-capital
  consequence to a beta-stage failure of it — the same disarm procedure
  remains the correct first response to any concern involving it, purely
  out of consistent operational discipline, not because real money is at
  risk during this beta.

## 5. Smoke-Test Checklist

Run this immediately after deployment and before announcing beta access
to any tester, and again after any mid-beta hotfix deployment:

- [ ] `GET /api/healthz` returns `200 {"status":"ok"}`.
- [ ] `GET /api/monitoring/status` resolves with `database.connected: true`
      and, once the process has been running long enough for each job's
      own first tick (up to 5 minutes for the slowest, `alerts`), all 3
      tracked background jobs (`auto-execution`, `auto-adjustment`,
      `alerts`) report `lastStatus: "ok"`.
- [ ] A brand-new sign-up completes end-to-end (name/email/password → a
      real session → the Command Centre/Home landing page renders).
- [ ] The newly-created account shows its own auto-seeded starter trades
      and Portfolio Health Score (confirms `ensureSeedTrades()` still
      fires correctly against the real beta database).
- [ ] One real, manual walkthrough of Journey 1 and Journey 2 from
      `docs/v1.6.0-Beta-Testing-Guide.md` (First Login, First Market Scan)
      succeeds without error.
- [ ] One page from each of the three engines loads with real (SIMULATED)
      data and no console/network errors: Scanner or Options Dashboard
      (Options Income), Trading Research (Trading Engine), Value/Stock
      Research (Investing Engine) — mirroring the exact per-engine smoke
      coverage the automated E2E suite already exercises
      (`engine1-investing.spec.ts`, `engine2-trading.spec.ts`,
      `engine3-options-income.spec.ts`, `artifacts/e2e/tests/`).
- [ ] Confirm no beta account has `alpacaConnected`, `fundamentalsConnected`,
      or the trading-engine live-data equivalent reading `true` — the
      explicit proof that this beta is genuinely running SIMULATED-only,
      not an accident of leftover credentials in the environment (§1
      above).
- [ ] Confirm `REQUIRE_AUTH` is genuinely enforced: an unauthenticated
      request to a business route (e.g. `GET /api/trades` with no session
      cookie) returns `401`, not a silently-scoped legacy-owner response.
- [ ] Two different real test accounts confirm they cannot see each
      other's trades/journal entries/watchlists (a live spot-check of the
      same guarantee `lib/tenantIsolation.test.ts` proves automatically).

## 6. Health Checks

Reuses the platform's existing, already-built health infrastructure —
nothing new was built or needs to be built for this beta:

- **`GET /api/healthz`** — the basic liveness check, exempt from
  authentication and rate-limiting, exactly as it is in every other
  environment. Point whatever uptime-monitoring tool is chosen for the
  beta (see §7) at this endpoint at minimum.
- **`GET /api/monitoring/status`** (Sprint 74) — the deeper readiness
  check: database connectivity, background-job health (§5 above), current
  request-volume window, and audit-log-derived alert signals (guardrail
  block rate, auth-failure rate — both genuinely meaningful even at a
  handful of beta users, since either threshold firing at that scale is a
  much stronger signal than the same firing at production traffic
  volumes).
- Neither endpoint needed any change to support this beta — they were
  built provider/scale-agnostic from Sprint 74 onward.

## 7. Monitoring

- Wire whichever external uptime/monitoring tool is available for this
  beta's hosting environment to poll `GET /api/healthz` and, ideally,
  `GET /api/monitoring/status` — this platform's own monitoring stack is
  designed to be polled by exactly this kind of external tool
  (`docs/Incident-Response-Runbook.md` §1.4); it does not itself send a
  push notification anywhere.
- Perform `docs/Production-Rollout-Plan.md` §7's Monitoring Verification
  checklist once, before beta start, including its one **non-production-only**
  step (deliberately triggering a synthetic alert to confirm the full
  detect → log → persist path) — this beta environment is exactly the
  kind of pre-production environment that step is meant for.
- **Given the small scale of a beta (5–8 users, see
  `docs/v1.6.0-Beta-Operations-Guide.md`), a human — whoever operates the
  beta day to day — should also simply check `GET /api/monitoring/status`
  directly, once daily**, per `docs/Operations-Handbook.md` §2's existing
  daily-operations checklist. A beta of this size does not need — and
  should not wait for — a fully automated paging pipeline to be stood up
  first; a human glance at the endpoint each morning is sufficient and
  consistent with this platform's own "quality over infrastructure" beta
  philosophy.
- The two operator-facing alert categories most likely to actually fire
  during a real beta are `errors.elevated_5xx_rate` (a genuine bug a
  tester's real usage pattern exposed that this project's own test suite
  didn't) and `auth.elevated_failure_rate` (more likely a tester
  forgetting their password than an attack, at this scale) — both are
  fully documented, with diagnosis and recovery steps, in
  `docs/Incident-Response-Runbook.md` §2.4 and §2.6.

## 8. Logging

- No new logging mechanism is needed — every request and every background
  job tick already logs through the shared `pino` logger
  (`lib/logger.ts`), unchanged for this beta.
- Set `LOG_LEVEL=info` for the beta environment (§1 above) — verbose
  enough to diagnose a real issue after the fact, not so verbose that a
  multi-day run's logs become unreviewable.
- **Two real, already-existing audit tables are directly useful during a
  beta, beyond raw application logs:**
  - `platform_audit_log` — every sign-in/sign-in-failure and every
    settings change (field names only, never values) for every beta
    account. The first place to look if a tester reports "I made a change
    and it didn't stick" or "I couldn't sign in."
  - `auto_execution_log` — since the automation scheduler still runs even
    in SIMULATED mode for any beta account that arms it, this remains the
    authoritative record of every open/adjust/close decision the
    automation made and why, exactly as it would in a live deployment. A
    beta tester exploring AutoPilot/Adjustments is a genuinely realistic
    scenario worth being able to explain after the fact.
- Whoever operates the beta day-to-day should skim the previous 24 hours
  of logs each morning for any `error`-level line not already surfaced by
  `GET /api/monitoring/status`, per `docs/Operations-Handbook.md` §2 —
  unchanged from that document's own existing daily-operations guidance,
  simply applied to this shorter, smaller-scale environment.
