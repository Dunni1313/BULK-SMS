# v1.2.0 — Trade Execution Center

Frontend-only feature release on top of `v1.1.0` (the sidebar navigation
redesign). Ships one new page — a guided, single-page workflow over the
Options Income Engine's already-shipped, already-tested pipeline. **Zero
new backend routes were added; zero business logic was duplicated;
`execution.ts`/`optionsMath.ts`/`risk.ts`/`autoExecution.ts`/
`autoAdjustment.ts` all have a zero-line diff for this release, confirmed
via `git diff --stat`.**

## Objective

Before this release, placing and managing a Paper Trading order required
navigating between five separate pages — Scanner, the Trade Ticket
(`/ticket/:scannerId`), Trades, Adjustments, and the Paper Portfolio
Dashboard — each with its own context. The Trade Execution Center
(`/trade-execution-center`) puts the entire Scanner → AI Score → Strategy
→ Order Preview → Risk Review → Confirm → Paper Order Submission → Order
Status → Trade Monitor → Adjust/Close workflow on one page, as a step-by-
step wizard, without re-implementing any step's own underlying logic.

## Repository audit performed before implementation

Every one of the following was located and read before any code was
written, specifically to confirm it could be reused as-is:

| Workflow concept | Reused implementation |
|---|---|
| Opportunity Scanner | `useGetScannerResults` / `useRunScanner` (`routes/scanner.ts`), the exact hooks `pages/Scanner.tsx` already uses |
| AI Opportunity Score | The scanner result's own `ravishScore`/`ravishTier`/`pop`/`ev` fields, plus the shared `TradeExplanationSheet` component (already used by `Scanner.tsx`, `Trades.tsx`, `Backtest.tsx`) for the AI-narrated breakdown |
| Strategy templates | The scanner candidate's own `strategy` field — no backend strategy-reassignment capability exists, so this step is honestly a review/confirm step, not a picker (see "Known limitations") |
| Order Preview | `usePreviewExecution` (`POST /execution/preview`, `routes/execution.ts`), the exact hook `pages/TradeTicket.tsx` already uses — itself built on the protected `lib/execution.ts` |
| Portfolio Risk Engine | The same preview response's own `validation` field (`PreTradeCheck[]`, warnings, violations, `riskPct`, `portfolioRiskBeforePct`/`AfterPct`) — computed once, server-side, never recomputed client-side |
| Position sizing | The ticket's own quantity stepper (`+`/`-`), which re-runs the same preview at the new quantity — the same interaction `TradeTicket.tsx` already implements |
| Alpaca Paper Trading | `useSubmitExecution` (`POST /execution/submit`) for order placement, and `useGetBrokerHealth` (`routes/brokerHealth.ts`, the same "Check Connection" pattern `Settings.tsx` already uses) for connectivity |
| Trade Monitor | `useGetTradeMonitor` (`GET /trades/:id/monitor`, already shipped) |
| Position Management | Links out to the existing `/ticket/adjust/:tradeId` (roll/convert), `/adjustments`, and `/trades` pages — none of their own logic is re-implemented here |
| Sidebar navigation | `lib/nav-items.ts`'s existing `NAV_GROUPS` array and item shape, extended by one entry |
| Shared UI components | `Card`, `Button`, `Badge`, `Skeleton`, `Checkbox`, `Table`, `AlertDialog`, `EventRiskBadge`, `TradeExplanationSheet` — all pre-existing, none forked |
| Existing hooks | Every data hook listed above comes from the already-generated `@workspace/api-client-react` package — no new OpenAPI schema, no new codegen |

### Dependency map

```
Scanner (useGetScannerResults/useRunScanner)
        │  select candidate
        ▼
AI Score panel (candidate's own ravishScore fields + TradeExplanationSheet)
        │  confirm
        ▼
Strategy review (candidate's own `strategy` field — review only)
        │  confirm
        ▼
Order Preview (usePreviewExecution → lib/execution.ts, protected, reused verbatim)
        │  same response
        ▼
Risk Review (ticket.validation — already computed by the same preview call)
        │  + Broker connectivity (useGetBrokerHealth)
        ▼
Confirm & Submit (risk-acknowledgement checkbox + AlertDialog + useSubmitExecution)
        │  on success: { orderId, broker, tradeId, journalId, message }
        ▼
Order Status (submit response, displayed as-is)
        │
        ▼
Monitor & Manage (useGetTradeMonitor(tradeId) + links to /ticket/adjust/:id,
                  /adjustments, /trades — not reimplemented)
```

## What is genuinely new on this page

Only the workflow orchestration itself — nothing that duplicates a
calculation that already exists elsewhere:

- The step state machine (`stepIndex`/`furthestReached`) and the visual
  stepper component.
- **Risk acknowledgement gate**: an explicit checkbox, required (alongside
  a valid, passing risk validation and a connected broker) before the
  Submit button is enabled — a genuinely new safeguard, not present on
  `TradeTicket.tsx`'s own, slightly different confirm flow.
- **Stale-preview detection**: if more than 60 seconds elapse between the
  last successful preview and reaching the Confirm & Submit step, the page
  blocks submission and requires an explicit "Refresh Preview" click,
  re-running the same `usePreviewExecution` call.
- **Duplicate-submission protection**: a `hasSubmittedRef` flag, set the
  instant Confirm & Submit is pressed, blocks any further submit call for
  that ticket regardless of how the button is re-triggered; combined with
  disabling the button while the mutation is in flight.
- **Client-side activity timeline**: a simple, session-local, timestamped
  log of the major actions taken during this workflow visit (candidate
  selected, preview built, broker checked, order submitted). This is
  explicitly *not* a new audit-log endpoint — the real, persistent audit
  trail for every order is still the existing one (`POST /execution/submit`
  already writes to the trades table and the trading journal, exactly as
  it does when called from `TradeTicket.tsx`). The timeline is a
  session-local UX convenience only, cleared on page reload.

## Paper Trading limitation

Alpaca is Paper-Trading-only by unconditional platform design (see
`docs/Alpaca-Paper-Trading-Architecture.md`) — there is no live-trading
code path anywhere in this codebase for this page (or any other) to
accidentally expose. `useSubmitExecution` calls the same
`submitOptionOrder()` function every other order-submission surface in the
app already calls; nothing about this release changes what that function
does. Live execution therefore remains disabled throughout this release,
with no toggle of any kind added.

## Supported execution strategies

Whatever the Options Income Engine's scanner itself currently ranks
candidates for (Iron Condor, Iron Fly, Calendar Spread, Earnings —
the same list `Scanner.tsx`'s own strategy filter shows). The Trade
Execution Center does not add, remove, or restrict any strategy; it
reuses the scanner's own candidate pool unmodified.

## Sidebar placement — a disclosed deviation

The kickoff instructions named "Trading Workbench → Trade Execution
Center" as the intended nav location. `lib/nav-items.ts` already has a
group literally named `"Trading Workbench"`, but it is Engine 2's own
group (Trading Research, Market Structure Workbench, Trading AI Coach,
etc.) — a different engine from the one this page's entire dependency
list belongs to. The page was placed instead in the pre-existing
`"Options Trading"` group (Engine 3), directly after "Scanner," since
every one of its reused hooks/routes lives in that group already. This
choice is disclosed here rather than silently applied.

## Known limitations

- **"Strategy Selection" is a review step, not a re-assignment picker.**
  No backend capability exists to change a scanner candidate's assigned
  strategy after the fact; building one would be new business logic this
  release's scope explicitly excludes ("do not duplicate business logic,"
  "reuse existing architecture"). If real strategy re-assignment is wanted
  in a future release, it is new scanner/execution-layer work, not a
  frontend-only change.
- **The activity timeline is session-local only.** It is not persisted,
  not an audit log, and does not survive a page reload. The durable audit
  trail remains the existing trades/journal writes `POST /execution/submit`
  already performs.
- **No new automated accessibility audit or responsive-layout test
  suite was added.** The page reuses the same shadcn/ui primitives
  (`Card`, `Button`, `Table`, `AlertDialog`, `Checkbox`) and the same
  Tailwind responsive/dark-mode conventions every other page in this
  codebase already relies on (dark mode and color-scheme theming are
  inherited "for free" from those shared components, not re-implemented
  here) — this release did not introduce a new, separate accessibility
  testing methodology beyond what the rest of the platform already
  follows (`role`/`aria-current` on the stepper, native keyboard operability
  of every button/checkbox/dialog).
- **Broker connectivity is checked on demand, not polled.** Consistent
  with `Settings.tsx`'s own established "Check Connection" pattern
  (`useGetBrokerHealth` with `enabled: false` + manual `refetch()`), the
  broker health check on the Risk Review step must be explicitly triggered
  by the user, not fetched automatically on every visit.
- **No dedicated end-to-end (Playwright) spec was added this release.**
  Coverage is 13 Vitest component tests (`TradeExecutionCenter.test.tsx`)
  covering workflow progression, risk blocking, confirmation gating,
  submission, error handling, monitoring, and state restoration — a future
  release could add a browser-level E2E spec following the pattern in
  `artifacts/e2e/`.

## Future live-trading requirements

None of this release's own scope. Per `docs/Known-Limitations.md` and
`docs/Version-2-Roadmap.md`, live (non-Paper) trading is an explicitly
deferred, unconditional platform-wide decision requiring: (1) a formal
project-owner decision to leave Paper-Trading-only scope at all, (2) a
`BrokerProvider`-shaped seam extracted from `execution.ts`'s current
Alpaca-specific calls (itself a protected-file change requiring the
highest scrutiny under CLAUDE.md rule 1), and (3) real broker credentials
verified end-to-end (Sprint 76 of the original Blueprint roadmap remains
blocked on this today). This release does not move any of those three
items forward, by design.
