## 4. Coach Registry design

`CoachRegistry` (`coachRegistry.ts`) is the one authoritative list of
registered conversational coaches:

```ts
const REGISTERED_COACHES = [tradingCoachConfig, investingCoachConfig, optionsCoachConfig];
export const CoachRegistry = { all(), get(id: CoachId) };
export const coachRegistrationIssues = validateCoachRegistry(REGISTERED_COACHES);
```

- Contains **only** Trading, Investing, and Options — each entry is the
  exact same config object its own page already imports; nothing is
  copied, cloned, or re-derived.
- **Prevents duplicate coach IDs and duplicate routes** — not by throwing
  at import time, but by running `validateCoachRegistry()` once at module
  load and exposing whatever it finds via `coachRegistrationIssues`
  (always `[]` for the real, shipped coaches — proven in
  `coachRegistry.test.ts`).
- **Provides typed coach lookup** — `CoachRegistry.get(id: CoachId)`
  returns `AnyCoachConfig | undefined`, an honest `undefined` for any id
  that was never registered.
- **Preserves current routes/names/configuration values exactly** — the
  registry never mutates, wraps, or re-shapes a config; `CoachRegistry.get("trading")
  === tradingCoachConfig` (proven directly by `toBe`, not just `toEqual`).
- **Exposes no new public API consumed by production code** — zero pages
  or components were changed to use `CoachRegistry` instead of importing
  their own config directly (confirmed by a zero-line diff across every
  page file, §7). It exists for test/tooling enumeration and for
  registration-time validation only.

`CoachId` (Sprint 4's own closed union: `"trading" | "investing" | "options"`)
has no `"portfolio"` member, so a 4th registry entry claiming that id would
be a compile-time error, not merely a missing runtime registration — the
Portfolio exclusion is enforced by the type system itself, not only by the
registry's own contents.

## 5. Configuration validation rules

`coachConfigValidator.ts` implements exactly the invariants this sprint's
own goals named:

| Rule | Function | Real-coach result |
|---|---|---|
| Coach id is recognised / unique across the registry | `validateCoachRegistry` | 3 distinct ids, 0 issues |
| Required fields present (`displayName`, `description`, `endpoint`) | `validateCoachConfig` | all populated, 0 issues |
| Route mapping is defined (`endpoint` non-empty, starts with `/`) | `validateCoachConfig` | all 3 satisfy this, 0 issues |
| Capabilities belong to the declared coach | `validateCoachConfig` (via `isCapabilityPermittedFor`, Sprint 4) | every real capability check passes, 0 issues |
| Duplicate capabilities within one coach are rejected | `validateCoachConfig` | no real coach repeats a capability, 0 issues |
| Duplicate routes across coaches are rejected | `validateCoachRegistry` | all 3 endpoints distinct, 0 issues |
| Starter prompts remain coach-specific | regression test (`coachRegistry.test.ts`), not a new rule | Trading/Investing still interpolate their own symbol; Options still returns its own fixed 2 prompts |
| Context providers remain isolated | regression test, reusing Sprint 4's own proof shape | Trading/Investing's `buildRequestBody` still produce `{symbol, question}`; Options still produces `{message, mode, level}` |
| Request builders remain coach-specific | same regression test | same as above |
| Tool access does not cross coach boundaries | `validateCoachConfig` (capability-ownership check) + `coachConfigValidator.test.ts`'s dedicated fixture proof | a fixture claiming `"greeks"` under `id: "trading"` is rejected |

**All of this is proven against the real, production coaches only as a
POSITIVE case** (`coachRegistrationIssues` is `[]`) — every NEGATIVE case
(duplicate id, duplicate route, cross-coach capability, duplicate
capability, missing field, unregistered capability) is proven exclusively
against deliberately-broken **fixture** configs in
`coachConfigValidator.test.ts`, never against `tradingCoachConfig`/
`investingCoachConfig`/`optionsCoachConfig` themselves — so it is
structurally impossible for a negative-case assertion to ever accidentally
fail against a real, shipped coach.

## 6. Coach Bootstrap design

**`useSpecialistCoach()` (Sprint 3) already is the Coach Bootstrap** — it
is the one function that connects a `CoachConfig` (capabilities, prompt
selection is server-side and out of its reach, context provider, endpoint
mapping) to the `ConversationEngine`/`StreamingEngine`
(`useCoachConversation()`). This sprint found no duplicated bootstrap code
behind it to consolidate, so **`useSpecialistCoach.ts` was not modified at
all** — confirmed by a zero-line diff.

**Explicit design decision, directly following this sprint's own repeated
warnings:** validation is **not** wired into `useSpecialistCoach()`'s
render path. Doing so would mean:
- Running a validation pass on every render of every specialist coach page
  (a genuine, if cheap, per-render cost with zero benefit, since the
  registry's own module-load-time validation already covers the same
  ground once).
- Introducing a brand-new failure mode — a hook that could throw during
  render — for a check that, by construction, always passes against
  today's real coaches.

Instead, `coachRegistrationIssues` is computed **once**, at
`coachRegistry.ts`'s own module load (which happens once per process, the
same as any other module-level constant in this codebase), and **never
throws**. The only function that *can* throw, `assertNoValidationIssues()`,
is called **exclusively from test files** (`coachConfigValidator.test.ts`,
`coachRegistry.test.ts`) — grepping the entire `artifacts/ravish-trading/src`
tree confirms zero non-test call sites.

## 7. Validation lifecycle

```
Module load (coachRegistry.ts)
  └── validateCoachRegistry(REGISTERED_COACHES)   [pure, never throws]
        └── coachRegistrationIssues: CoachConfigValidationIssue[]   [always [] today]

Test run (coachConfigValidator.test.ts, coachRegistry.test.ts)
  └── assertNoValidationIssues(coachRegistrationIssues, "CoachRegistry")
        └── passes silently today; would throw a clear, structural error
            (identifying coachId + field) the moment a future edit ever
            broke an invariant — caught in CI/local test runs, never in
            a user's browser.

Production (any page, any render, any conversation)
  └── useSpecialistCoach(config, params) — UNCHANGED, never validates,
      never throws for a configuration reason. A user's coach conversation
      can only ever fail for the same reasons it could before this sprint
      (network error, LLM unavailable, etc.) — never a new "invalid
      config" failure mode.
```

## 8. Failure behaviour

Every `CoachConfigValidationIssue` is `{coachId, field, message}` where
`message` is a **fixed, structural template string** — it names the field
or rule violated (`"capabilities"`, `"endpoint"`, `"id"`) and, at most, the
coach id and the specific capability string involved. It **never**
interpolates an arbitrary config field's actual VALUE (e.g. `description`'s
text, or an `endpoint`'s literal value beyond confirming it's missing/
malformed) into a message.

**Directly tested** (`coachConfigValidator.test.ts`'s own dedicated case):
a fixture is constructed with a fake "secret-looking" string
(`"sk-live-FAKE_SECRET_VALUE..."`) and a fake "prompt-looking" string
planted in fields the validator inspects; the thrown error from
`assertNoValidationIssues()` is asserted to `not.toContain()` either
literal string — proving the validator/assertion path can never leak an
arbitrary config value, a prompt, or a secret-shaped string into an error
message, even when one is present in the config being validated.

No portfolio, account, market, or user data is ever in scope for this
module at all — it only ever inspects a static `CoachConfig` object, never
a live conversation, a request body, or a user's question/answer.

## 14. Remaining technical debt

- `coachRegistrationIssues` is computed once at module load but never
  actively asserted against in any production code path — by design (§6),
  not an oversight. A future sprint could add a dev-tooling script (e.g. a
  pre-commit or CI-only check) that imports `coachRegistry.ts` and calls
  `assertNoValidationIssues()` explicitly, giving an even earlier signal
  than "the test suite catches it" — not built this sprint since the test
  suite already does catch it today.
- `CoachRegistry.get()` returns `AnyCoachConfig | undefined` rather than a
  per-id overloaded, narrowly-typed return (e.g. `CoachConfig<TradingCoachParams>`
  specifically for `"trading"`) — a reasonable enhancement if a future
  consumer ever needs to call `buildRequestBody` through the registry
  itself; not needed today since no page does that (every page still
  imports its own concretely-typed config directly).
- The Portfolio conversational-coach gap (Sprint 3's own finding) remains
  deferred, unchanged.
