# v1.5.0, Sprint 18 — Institutional Playbooks & Operating Procedures Engine

## Non-negotiable statement

This is **not** another Learning Centre, **not** another Workflow Engine, and
**not** another Knowledge Graph. It creates one reusable Playbooks &
Operating Procedures Engine defining **how** institutional workflows are
executed consistently — every playbook stage links to an already-existing
module. Playbooks orchestrate; they never duplicate functionality.

## 2. Playbook model

Every playbook (`Playbook` in `lib/playbooks.ts`) carries exactly the
fields the approved scope named:

```ts
interface Playbook {
  id, category, name, purpose, objective,
  prerequisites: string[],
  requiredInputs: string[],
  expectedOutputs: string[],
  validationRules: string[],
  commonMistakes: string[],
  institutionalNotes: string[],
  relatedLearning: { pathKey, topicKey, label }[],
  relatedKnowledge: string,
  relatedWorkflows: string[],
  entityBinding: "trade-plan" | "aggregate",
  stages: PlaybookStage[],
}

interface PlaybookStage {
  id, title, purpose, whyItMatters,
  requiredActions: string[],
  moduleLabel, moduleHref: string,
  signalType: "auto" | "manual",
}
```

`Playbook`/`PlaybookStage` are plain, static TypeScript data — the same
"deterministic, version-controlled content, never LLM-generated" discipline
`lib/learningPaths.ts` and `tradePlanChecklistTemplates.ts` already
established. A new playbook is a literal addition to the `PLAYBOOKS` array,
never a database migration — literally satisfying "NOT another database."

### `signalType`: the honesty mechanism

Every stage is explicitly typed `"auto"` or `"manual"`:

- **`auto`** — completion is derived from a real, already-computed platform
  signal (a Trade Plan's own `currentStage`, a notebook's own tag count, a
  Portfolio Health Score's own label). Never fabricated.
- **`manual`** — no platform signal exists for this step at all (e.g. "held
  the weekly investment committee meeting," "ran a stress test scenario").
  These are self-certified only, via a new client-side-only acknowledgement
  store (`lib/playbook-acknowledgements.ts`, mirroring
  `lib/workflow-dismissals.ts`'s exact localStorage pattern) — and the UI
  always discloses "Not tracked automatically" / "not automatically
  verified" whenever one is shown, so a manual acknowledgement is never
  visually confused with a genuine platform-verified reading.

This distinction is the direct implementation of the approved scope's
"Never fabricate patterns. Only report evidence" instruction, applied to
process-completion tracking specifically.

## 4. Stage-completion validation approach

`lib/playbookProgress.ts`'s `computeStageStatus()` is the single scoring
function every stage's status flows through. Four possible statuses:

- **`not-started`** — no real signal yet (or the bound entity hasn't
  reached this stage).
- **`in-progress`** — the bound entity currently sits at this exact stage
  with no outstanding blockers, or an aggregate signal shows real but
  incomplete progress.
- **`complete`** — a real signal confirms this stage's condition is met.
- **`blocked`** — the bound entity is stuck at exactly this stage with a
  real, already-computed outstanding task (`TradeLifecycleRecord
  .outstandingTasks`) — never a fabricated blocker; the actual blocking
  task's own text is surfaced in the stage's `detail` field.

For the trade-lifecycle playbooks, this is a straightforward comparison of
the bound record's `currentStage` index against the stage's own mapped
pipeline-stage index in `PIPELINE_STAGES` (Sprint 14's own canonical
11-stage order) — no new stage-progression math.

For the 7 aggregate playbooks, each stage reads a specific already-computed
signal:

- **Investment Research / Strategy Development** — notebook/strategy
  counts and tag/status fields (the same signals `workflowAutomation.ts`'s
  own `research-to-notebook`/`notebook-to-strategy`/`strategy-to-tradeplan`
  tasks already read).
- **Portfolio Review / Risk Review** — `PortfolioHealthScore.label`/
  `.confidenceLevel` and specific named `RiskSignal`s (`single_position_risk`,
  `open_trade_risk`/`total_portfolio_risk`), reusing the exact
  `/breach|above|exceed/i` detection Sprint 16 established (now shared via
  the newly-exported `hasBreachedRiskSignal()`).
- **Weekly Investment Committee** — real counts of trade plans/notebooks/
  strategies (is there anything to review at all).
- **Quarterly Performance Review** — closed-trade counts (real realized
  performance data to review), `discoverPatterns()`'s own output (recurring
  mistakes/successful examples), and real Learning Centre progress.

**Two stages were deliberately marked `manual` rather than `auto`**
(Monthly Portfolio Review's "Review Portfolio Construction"/"Review
Concentration & Correlation") — during implementation, wiring these to a
real signal would have required adding new hook dependencies
(`useGetPortfolios()`/`useGetPortfolioConcentration()`) purely for a single
boolean check with no other benefit to this sprint's own scope. Rather than
force an under-justified new dependency, they're honestly disclosed as
self-certified — a real, disclosed scope decision, not an oversight.

## 5. Entity graph / architecture

```
lib/playbooks.ts            — static content (12 Playbook objects)
lib/playbookProgress.ts     — pure scoring (computeStageStatus, computePlaybookProgress,
                               computeAllPlaybooksProgress, currentPlaybook,
                               recommendedNextPlaybook, buildPlaybookCoachNarrative)
lib/playbook-acknowledgements.ts — localStorage store for "manual" stage acks
lib/usePlaybooks.ts          — orchestration hook (mirrors useWorkflowAutomation.ts)
pages/InstitutionalPlaybooks.tsx — the execution UI (/playbooks)
```

`usePlaybooks()` composes, in one place:

- `listNotebooks`/`listStrategies` (Sprint 8/9 plain-fetch APIs), fetched
  the same way `useWorkflowAutomation.ts`/`useKnowledgeGraph.ts` already do.
- `useTradeLifecyclePipeline()` (Sprint 14).
- `usePortfolioRiskIntelligence()` (Sprint 15).
- `useListJournalEntries()`/`useGetLearningProgress()` (existing generated
  hooks).
- `buildKnowledgeGraph()` (Sprint 17) — built once, exposed to the page for
  Related Knowledge, and consumed internally by `discoverPatterns()` for
  the Quarterly Performance Review playbook's pattern-review stage.

No new backend route. No new database table. No new OpenAPI schema. Every
one of these was fetched entirely client-side from data other sprints
already expose.

## 6. AI Playbook Coach

`buildPlaybookCoachNarrative(playbook, selectedStage)` returns:

```ts
{
  whyThisStageExists,        // stage.purpose
  professionalExpectations,  // stage.whyItMatters
  typicalInstitutionalProcess, // playbook.institutionalNotes[0]
  commonErrors,              // playbook.commonMistakes
  whenToStopAndReassess,     // deterministic — names the real blocker when status === "blocked"
  relatedLessons,            // playbook.relatedLearning (verified pathKey/topicKey pairs)
  relatedHistoricalExamples, // playbook.relatedKnowledge
}
```

Every field is a direct read of already-authored playbook content — the
function invents nothing. This is the identical pattern
`buildWorkflowCoachNarrative()`/`answerKnowledgeQuestion()` established:
zero LLM calls, zero new AI infrastructure, per the sprint's own explicit
"reuse the existing AI Coach" instruction and "never invent process steps"
requirement.

## 7. Knowledge Graph integration

The execution page's `RelatedKnowledgeCard` calls the Knowledge Graph's own
exported traversal functions directly, for whichever entity a
trade-lifecycle playbook is currently bound to:

- `relatedEntitiesWithinTwoHops(graph, "trade-plan:<id>", "notebook")` →
  **Relevant Research**
- `relatedEntities(graph, "trade-plan:<id>")` filtered to `strategy` →
  **Related Strategy**
- `relatedEntities(graph, "trade-plan:<id>")` filtered to `journal-entry` →
  **Previous Journals**
- `discoverPatterns(graph, journalEntries, portfolioRisk)` → **Recurring
  Mistakes** / **Successful Examples**
- Journal entries with a real `lessonLearned` → **Lessons Learned**

Unbound aggregate playbooks fall back to their own `relatedKnowledge`
description text — never a fabricated connection for a playbook with no
single bound entity.

## 8. Command Centre integration

`PlaybooksCard` (new, in `InstitutionalCommandCentre.tsx`) shows exactly
what the approved scope named:

- **Current playbook** — `currentPlaybook()`: the in-progress playbook
  furthest along (most completed stages), honestly `null` when nothing has
  any real signal.
- **Progress** — stage count / percentage for the current playbook.
- **Blocked stages** — flattened across every playbook, never silently
  dropped.
- **Recently completed procedures** — playbooks currently at 100%. The
  card's own description honestly discloses this reflects *current*
  completion state, not a timestamped history — this platform tracks no
  "when did this playbook complete" data, and none was fabricated to
  satisfy the word "recently."
- **Recommended next procedure** — `recommendedNextPlaybook()`: the first
  genuinely not-started playbook, in `lib/playbooks.ts`'s own declared
  order.

## 9. Search integration

`CommandPalette.tsx` gained a new "Playbooks" group, listing all 12
playbooks by name — each item's `value` string includes the playbook's
name, purpose, **and every one of its stage titles**, so cmdk's own fuzzy
filter finds a playbook by any of its procedures/workflow stages (e.g.
typing "Pre-Trade Checklist" surfaces the Trade Planning playbook).
Selecting an item deep-links to `/playbooks?playbookId=<id>`, reusing the
exact `?planId=` query-param precedent `DecisionWorkflow.tsx` already
established. No second search engine was built.
