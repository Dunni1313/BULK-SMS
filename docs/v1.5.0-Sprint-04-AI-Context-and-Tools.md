## 2. Investigation — what was actually duplicated

Before writing any code, every one of the 5 named duplication categories
was checked against the real codebase, not assumed:

| Category | Found genuine duplication? | Where |
|---|---|---|
| Prompt selection | **Yes** | `narrateValueFreeform`/`Stream` and `narrateTradeFreeform`/`Stream` (`coachLLM.ts`) each hand-duplicated: pick a fixed prompt prefix → append `\n\nQUESTION: <question>` → call the shared `narrate`/`narrateStream` → optionally run a safety wrapper. |
| Tool registration | **No literal LLM tool-calling exists anywhere** (re-confirmed; unchanged from Sprint 3's own finding) — but `CoachConfig.capabilities` (Sprint 3) was an unvalidated `readonly string[]`, so "which coach may claim which capability" was an eyeballed convention, not an enforced one. |

| Capability checking | **Yes** | Nothing checked whether a capability string a coach declared was even real, or whether it belonged to that coach; a typo or a copy-pasted capability from another coach's config would have silently drifted with zero warning. |

### After (Sprint 4)


## 4. Prompt Loader design

`createFreeformNarrator(coachId, promptPrefix, safetyWrap?)` (private to
`coachLLM.ts`) is the factory both `narrateValueFreeform`/`Stream` and
`narrateTradeFreeform`/`Stream` are now built from. It:

1. Takes the coach's own already-existing, already-private prompt
   constant (`valueFreeformPrompt`/`tradeFreeformPrompt`) as a plain
   parameter — prompt **text** never moves, never gets duplicated, and
   never gets sent to the frontend (unchanged from Sprint 3's own explicit
   "prompts are server-owned" decision).
2. Builds the exact same `${promptPrefix}\n\nQUESTION: ${question}` string
   every pre-Sprint-4 call site built by hand.
3. Calls the same private `narrate()`/`narrateStream()` wrappers (which
   already guarantee `SYSTEM_PROMPT`/`COACH_DISCLAIMER` via
   `@workspace/ai-core`).
4. Applies an optional `safetyWrap` — `enforceValueSafety` for Investing
   (its persona-framing + anti-impersonation guard), or the factory's own
   no-op default for Trading (which invokes no persona, matching its
   pre-existing, unmodified behavior).

Why "Prompt Loader" is a factory function, not a lookup table keyed by
coach id alone: `valueFreeformPrompt` and `tradeFreeformPrompt` are
declared roughly 150 lines apart in `coachLLM.ts` (each sits next to its
own extensive historical doc-comment explaining that coach's own sprint
history) — a single file-scope `const FREEFORM_PROMPTS = {...}` object
referencing both would require reordering that existing, already-reviewed
layout for no functional benefit. Passing the prompt text as a parameter
avoids that churn entirely while still centralizing the actual
prompt-selection *shape*.

Options' `/ai/chat[/stream]` is **not** wired through this factory —
confirmed unchanged from Sprint 3's own finding: it mode-dispatches across
several distinct `narrate*()` functions (trade explanation, Greek lesson,
value research, deterministic templates) rather than a single fixed
freeform prompt, so it never shared this particular duplication.

**Tested** (`coachLLM.freeformPromptLoader.test.ts`, mocking the OpenAI SDK
the same way `coach-level.test.ts` already established, so the actual
final prompt text sent to the model is directly inspectable): each coach's
prompt is correctly prefixed and never leaks the other coach's persona
framing; the same question routed through both coaches produces two
genuinely different final prompts; prompt selection is stable/non-drifting
across repeated calls to the same coach.

## 5. Context Provider design

`ContextProvider<TParams> = (question: string, params: TParams) => unknown`
is a **named type alias** for the exact function shape `CoachConfig.buildRequestBody`
already had since Sprint 3 — a pure documentation/naming clarification, zero
signature change. No new context-construction logic was extracted, because
none is genuinely shared: each coach's real grounding data (Engine 1's
business-quality/valuation/committee fields vs. Engine 2's
structure/liquidity/regime/probability/risk fields vs. the Options Engine's
Greeks/EV fields) is domain-specific by nature, and forcing a shared
"build a context object" abstraction over three unrelated data shapes would
violate this sprint's own "do not force domain-specific logic into generic
abstractions" instruction.

**Deliberately NOT done:** moving each domain's actual prompt text into the
frontend `CoachConfig` as a literal "system prompt" field, even though the
sprint's own target-architecture list names "system prompt" as something
each specialist coach should define. Sprint 3 already established, and this
sprint re-confirms, that prompt text must stay backend-only — sending it to
the frontend would be a real architecture change (a new client-visible
surface for prompt text that could be inspected or tampered with) contrary
to "maintain existing behaviour exactly." `description`/`capabilities`
remain the frontend's own honest, non-duplicating summary of what each
coach answers.

**Tested** (`contextProvider.test.ts`, new): each coach's `buildRequestBody`
is called directly with a deliberately over-stuffed "superset" params object
containing every other coach's own fields (symbol + mode + level all at
once) — proving structurally that Trading/Investing's providers never read
`mode`/`level`, and Options' provider never reads `symbol`. Also proves
Options' request-body shape is always distinct from Trading's/Investing's,
while honestly documenting that Trading and Investing legitimately produce
the *same* `{symbol, question}` shape (both are single-symbol-scoped
coaches) — not a false claim of universal uniqueness.

## 6. Tool Registry / Capability Flags design

`src/lib/ai-coach/capabilityRegistry.ts` (new) is the "Tool Registry" for
this codebase's specialist coaches. Since no coach performs real LLM
function-calling (re-confirmed this sprint, unchanged from Sprint 3), the
honest content of a "tool registry" here is a single, validated vocabulary
over the capability strings a coach may declare:

- `CAPABILITY_REGISTRY`: all 14 capability strings the 3 existing coaches
  already use (6 Trading + 3 Investing + 5 Options), each entry carrying a
  human-readable `description` and its `owners: CoachId[]` (always exactly
  one owner today — no capability is currently shared across coaches).
- `RegisteredCapability = keyof typeof CAPABILITY_REGISTRY` — the closed
  string-literal union `CoachConfig.capabilities` is now typed against,
  replacing Sprint 3's bare `readonly string[]`.
- `isCapabilityPermittedFor(coachId, capability)` — the real, directly
  testable "does coach X have access to capability Y" check the sprint's
  own testing list asks for.
- `capabilitiesOwnedBy(coachId)` — the inverse lookup, used by tests to
  prove each coach's own declared `capabilities` array exactly matches what
  the registry says it owns.

**Deliberately kept out of any runtime code path**, not wired into
`useSpecialistCoach()` or any config file as a live assertion: all 3
coaches' existing `capabilities` arrays already exactly match the registry
(by construction — the registry was built directly from their real,
shipped values), so a runtime check would only ever pass today. Adding a
throw-on-mismatch check to a currently-always-passing path is a new
failure mode with no present upside, and "maintain existing behaviour
exactly" argues for keeping this a compile-time (via the `RegisteredCapability`
type) and test-time-only guarantee rather than a new runtime one. See
§9 for why this is flagged as a natural, low-risk Sprint 5 candidate rather
than done now.

**Tested** (`capabilityRegistry.test.ts`, new, 9 tests): every real coach's
own declared capabilities are permitted for that coach; a coach attempting
to claim another coach's capability is rejected (6 cross-coach checks); an
unregistered/typo'd string is rejected for every coach; `capabilitiesOwnedBy()`
exactly reconciles with each coach's real config; every registered
capability has exactly one owner; the registry's total entry count exactly
equals the sum of all 3 coaches' own declared capability counts (so a
capability can never silently go unregistered).

## 11. Remaining duplication

- `routes/ai.ts`'s `/ai/chat[/stream]` mode-dispatch (Options coach) still
  has its own distinct shape (persistence baked into the route, a
  `{id, message, createdAt}` response, dispatch across several
  `narrate*()` functions) that doesn't participate in the Prompt Loader —
  correctly so, per this sprint's own "do not force domain-specific logic
  into generic abstractions" instruction; it was never duplicated with the
  other two coaches in the first place.
- The two backend context-builder functions (`buildFreeformContext()`,
  `buildTradeCoachContext()`) remain domain-specific and unconsolidated —
  correctly, since their actual field sets share no real structure to
  extract.
- `CAPABILITY_REGISTRY`'s ownership checks are compile-time/test-time only
  — no runtime call site invokes `isCapabilityPermittedFor()` today (see
  §6 and §12).

## 12. Recommendations for Sprint 5

1. **Wire a runtime capability assertion into `useSpecialistCoach()`** (or
   a one-time module-load assertion in each config file) once the
   registry has proven stable across at least one more sprint — this
   sprint deliberately kept the registry compile-time/test-time-only to
   avoid introducing a new production failure mode; a low-risk follow-up
   once there's more confidence in the registry's own completeness.
2. **A conversational Portfolio AI Coach**, if the project owner decides
   this is worth building — still the same deferred architectural gap
   Sprint 3 first documented; unchanged this sprint.
3. **A shared message-list renderer**, extracted once a second
   full-history-rendering surface (beyond `TradingCoachWorkspace.tsx`)
   needs one — the same Sprint 2/3-carried-forward recommendation,
   unchanged.
4. Consider whether `routes/ai.ts`'s mode-dispatch shape could ever be
   cleanly generalized without distorting it — not attempted this sprint
   (would risk exactly the kind of forced abstraction this sprint's
   instructions warn against), but worth a dedicated investigation sprint
   if Options ever grows a second mode-dispatching sibling coach.
