# v1.5.0, Sprint 17 — Institutional Knowledge & Intelligence Graph

## Non-negotiable

This is **not** another database. **Not** another notebook. **Not** vector
search or RAG or semantic embeddings. It is a pure, in-memory composition
layer that connects data every prior sprint already fetches and computes.
It introduces **zero new persisted storage** and exactly **one new
heuristic** (shared-tag matching, disclosed below) — everything else is a
direct read of an already-computed field from an already-shipped module.

## Relationship model

Two kinds of edge, both disclosed honestly in the UI:

1. **Structural (strong)** — a real foreign key already in this codebase's
   data model: `TradePlan.strategyId`, a `LinkedExecution`'s own symbol, a
   Journal Entry's `tradeId` (matched via the exact `executedTradeRef`
   comparison `tradeLifecycle.ts` already performs). These are certain.
2. **Tag-based (heuristic)** — the one new inference this sprint adds: two
   entities that carry the exact same tag string are both linked to a
   *derived* node for that tag. A tag shaped like a ticker (1-5 uppercase
   letters) becomes a `company` node; every other tag becomes a `theme`
   node. Every such edge's own `evidence` field literally reads `"shared
   tag: X"` — never a fabricated or scored "similarity."

Company and theme nodes are **derived**, existing only as a grouping of
already-tagged real entities — never independently stored.

## Entity graph

`buildKnowledgeGraph()` (`lib/knowledgeGraph.ts`) produces:

```
KnowledgeGraph { nodes: KnowledgeNode[]; edges: KnowledgeEdge[]; generatedAt }
```

7 entity types: `notebook`, `strategy`, `trade-plan`, `journal-entry`,
`company` (derived), `theme` (derived), `portfolio-review` (one synthetic
node summarizing the current, already-computed Portfolio & Risk
Intelligence read).

Traversal helpers: `relatedEntities()` (1-hop, both directions),
`relatedEntitiesOfType()`, `relatedEntitiesWithinTwoHops()` (needed because
Notebook↔Strategy/Trade-Plan connections are frequently mediated by a
shared company/theme node rather than a direct edge — a Notebook and a
Trade Plan that both carry the "NVDA" tag are each 1 hop from
`company:NVDA`, 2 hops from each other), `nodesByConnectionCount()`,
`searchKnowledgeGraph()` (the same plain substring match the Command
Palette already uses).

## Timeline

`buildInvestmentTimeline()` is a pure *presentation* of Sprint 14's own
already-computed `PIPELINE_STAGES` ordering and `TradeLifecycleRecord` —
never a second stage model. Each of the 11 stages carries an honest
`reached`/`isCurrent` flag, a best-effort date (from the record's own
already-known `createdAt`/`updatedAt`/`executedAt`/`openedAt`/`closedAt`
fields), and a `sourceModule` label so a user can trace exactly which
prior sprint computed that fact. The "Reviewed" stage's own description is
substituted with the real `lessonLearned` text **only when that stage has
actually been reached** — a real bug caught by testing (see below) where
an earlier draft would have shown the lesson on an unreached future row.

## Pattern discovery — evidence-based, never fabricated

`discoverPatterns()` requires at least 2 corroborating pieces of real
evidence before reporting anything; a category with 0 or 1 match is simply
absent, never claimed as "no issues found" (a claim this module can't
honestly make from a small sample):

- **Recurring lesson keywords** — journal entries scanned for 4 keyword
  categories (stop-loss discipline, position sizing, trading psychology,
  entry timing); quoted evidence, never scored.
- **Winning strategy clusters** — 2+ closed, profitable trade plans on the
  same strategy.
- **Portfolio risk signals** — a direct surfacing of Sprint 15's own
  `RiskIntelligenceReport.signals`, filtered to the **exact same 4 codes**
  `buildPortfolioCoachNarrative()` (Sprint 15) already treats as its own
  "biggest risks" set (`portfolio_concentration`/`single_position_risk`/
  `open_trade_risk`/`total_portfolio_risk`) — see "A second real bug" below
  for why the naive "any available signal" filter was wrong.
- **Frequently referenced companies** — company nodes with 2+ connections.
- **Research linked to wins** — a notebook 2-hop-connected (via shared tag)
  to 2+ profitable, closed trade plans.

## AI Knowledge Coach

Reuses this platform's established "reuse the AI Coach" **narrative
pattern** — deterministic, cross-module, always cites its own source
module — rather than the `CoachDrawer` component itself (see reuse audit
above for why). 4 canned questions, matching the sprint's own examples:

- *"Show me every trade that used this strategy."* — cites every real
  trade plan using that strategy (structural edge).
- *"What research supported my best-performing trades?"* — for the most
  recent profitable, closed trade plans, cites any 2-hop-linked notebook.
- *"Which mistakes appear repeatedly?"* — reuses `discoverPatterns()`'s
  own recurring-lesson-keyword output directly, zero second detector.
- *"Which lessons could reduce my drawdown?"* — honestly hedged: this
  platform has no equity time-series to *prove* a lesson already reduced
  drawdown, so it surfaces the lessons captured specifically from losing
  trades (`realizedPnl < 0` with a non-empty `lessonLearned`), framed
  forward-looking, never a fabricated causal claim.

Every answer's `citations[]` links back to the real entity it came from.

## Real bugs caught and fixed during implementation

1. **Timeline description leaked a lesson before its stage was reached.**
   `buildInvestmentTimeline()`'s "reviewed" stage description substituted
   the real `lessonLearned` text whenever one was passed in, regardless of
   whether that stage had actually been reached yet — caught by a
   dedicated test constructing a record still at "closed." Fixed by
   gating the substitution on `reached`.
2. **A portfolio-review node was fabricated for a brand-new user with
   nothing recorded anywhere.** `computePortfolioHealthScore()` (Sprint
   15) never actually returns `null` — it honestly returns `0`/"Poor" when
   nothing is available, the same design already disclosed in Sprint 15's
   own report. `buildKnowledgeGraph()`'s original `if (portfolioHealth)`
   check therefore always created a "Current Portfolio Review" node, even
   for an empty account — the exact same category of bug Sprint 16's own
   `portfolioRiskToReviewTasks()` was fixed for. Fixed identically: the
   node is now only created when `confidenceLevel !== "Low"`.
3. **`discoverPatterns()`'s risk-signal pattern fired from an always-
   available, benign informational signal.** `computeRiskIntelligence()`'s
   own `pending_trade_impact` signal code is *always* `available: true`
   by that module's own design (it honestly reports "None pending" rather
   than being absent) — a naive `signals.filter(s => s.available)` filter
   therefore surfaced a "risk signal" pattern for a portfolio with
   literally nothing in it. Fixed by narrowing to the exact same 4 codes
   `buildPortfolioCoachNarrative()` (Sprint 15) already treats as genuine
   risk indicators — reuse, not a new filter invented from scratch.
4. **The detail panel only ever showed 1-hop connections**, so selecting a
   Notebook never showed the Strategy/Trade Plan it shares a tag with —
   only the intermediary company/theme node itself. `relatedEntitiesWithin
   TwoHops()` had already been built in the graph engine for exactly this
   case but was never wired into the UI. Fixed by combining 1-hop and
   2-hop (per real entity type) results in `EntityDetailPanel`.
5. **Redundant parallel hook instances slowed and destabilized the page.**
   The first draft called `useKnowledgeGraph()`/`usePortfolioRiskIntelligence()`
   independently inside `PatternsPanel` and `KnowledgeCoachPanel` (on top
   of the page's own top-level call), tripling the number of concurrent
   Notebook/Strategy/Trade-Plan/Portfolio-Risk fetches for no benefit.
   Fixed by lifting both hooks to be called exactly once at the page's
   top level and passed down as props — both a real production
   performance fix and what resolved a category of slow/flaky tests.
