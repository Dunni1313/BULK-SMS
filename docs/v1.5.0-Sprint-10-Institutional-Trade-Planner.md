# v1.5.0 Sprint 10 — Institutional Trade Planner

Branch: `v1.5.0-sprint-10-trade-planner` (stacked on
`v1.5.0-sprint-09-ai-strategy-builder`)

## What this sprint adds

**Institutional Trade Planner** — a Trade Plan represents a fully prepared
trade *before* execution: a 22-section structured document (title, strategy,
workspace, research notebook links, planned asset, asset class, direction,
lifecycle status) that becomes the central planning engine feeding the
Trading AI Coach, Investing AI Coach, and Options AI Coach. Portfolio Coach
remains excluded, the same exhaustive Sprint 3 finding Strategy Builder
already relied on. **This module is planning only** — it never calls a
broker, submits an order, or executes anything; every AI feature is
explicitly instructed to never recommend that the user actually execute the
trade.

Built directly on top of Sprint 7's AI Workspaces, Sprint 8's AI Research
Notebooks, and Sprint 9's AI Strategy Builder, following the exact same
architectural pattern all three established: free-text discriminator
columns, detach-not-destroy workspace association, append-only immutable
version history, and deterministic (never-LLM) analysis wherever an
analysis is honestly, exactly computable.

## Architecture

### Backend

- **Reuse, not duplication.** A Trade Plan referencing a strategy or a
  notebook never re-stores that data — it only points at the already-
  existing `ai_strategies`/`ai_notebooks`/`ai_coach_conversations` row.
- **Four new tables** (migration `043_trade_plans.sql`) — one more than
  Strategy Builder's three, and deliberately so:
  - `trade_plans` — one row per plan: `user_id` (FK, `RESTRICT`,
    universal convention), `workspace_id` (nullable FK, `SET NULL`,
    detach-not-destroy, mirroring `ai_strategies.workspace_id`), `coach_id`,
    `strategy_id` (nullable FK to `ai_strategies`, `SET NULL` — see "Linked
    Strategy" below), `title`, `planned_asset`/`asset_class`/`direction`
    (all free text, never DB enums), `status` (application-validated
    against `["draft","ready","watching","executed","cancelled","archived"]`),
    `pinned`, `tags` (array), `current_version` (int, default 1),
    `executed_trade_ref`/`executed_at` (see "Future execution compatibility"
    below), timestamps.
  - `trade_plan_sections` — one kind-discriminated table covering all 21
    named structure-list sections: 18 singleton qualitative kinds (Market
    Context through Personal Notes) plus 3 many-per-plan reference kinds
    (Attachments, Research References, Notebook References — the last also
    covering AI Conversation references, mirroring Strategy Builder's own
    `notebook_reference` kind exactly). Singleton-ness for the 18
    qualitative kinds is enforced via a partial unique index
    (`UNIQUE (trade_plan_id, kind) WHERE kind NOT IN ('attachment',
    'research_reference', 'notebook_reference')`), identical in shape to
    `ai_strategy_sections`' own index.
  - `trade_plan_versions` — a full, immutable snapshot log, mirroring
    `ai_strategy_versions` exactly: `trade_plan_id`, `version` (monotonic,
    `UNIQUE(trade_plan_id, version)`), `snapshot` (jsonb — every top-level
    field, every section, and every checklist item at that moment),
    `change_summary` (nullable), `author_user_id` (FK, `RESTRICT`),
    `created_at`.
  - `trade_plan_checklist_items` — **the one genuinely new table beyond
    Strategy Builder's own 3-table pattern.** Strategy Builder's checklist
    features are ephemeral: an AI-generated list of strings, never
    persisted, checked off only in the browser's own local state and
    discarded on navigation. The Checklist Engine's own explicit
    requirement ("required items, optional items, completion status,
    progress percentage") genuinely needs real, per-item, persistent rows
    — `label`, `required` (boolean), `completed` (boolean), `position`
    (int, for stable ordering), `trade_plan_id` (FK, `CASCADE`). A
    fabricated in-memory-only checklist could never honestly report
    "3 of 5 required items complete" across a page refresh.
- **Reference-kind mapping, resolved at the route layer, mirroring
  Strategy Builder exactly:**
  - `"attachment"` → `refFileId` (an existing `ai_workspace_files` row)
    **or** freehand `content` — no upload infrastructure exists anywhere
    in this codebase, so this is references-only, matching every prior
    sprint's own disclosed limitation.
  - `"research_reference"` → `content` only (a plain URL/text link).
  - `"notebook_reference"` → `refNotebookId` **or** `refConversationId`.
- **Two structure-list items are deliberately NOT their own section
  rows**, to avoid storing the same relationship twice:
  - **"Linked Strategy"** → `trade_plans.strategy_id`, a real top-level
    FK, not a section row.
  - **"Linked Notebook"** → the `notebook_reference` section kind (which
    also covers AI Conversation references) — reusing Strategy Builder's
    own precedent exactly rather than inventing a parallel mechanism.
- **No separate `archived` boolean.** Unlike `ai_strategies` (which has
  both a `status` enum and a standalone `archived` boolean), `trade_plans`'
  own `status` enum already includes `"archived"` as one of its 6 values
  — a redundant boolean would duplicate state that `status` already
  carries honestly.
- **Versioning philosophy: append-only, never rewrite**, identical to
  Strategy Builder's own discipline, extended with one new rule for the
  Checklist Engine:
  - A top-level field change (`PATCH`), any section create/delete, any
    checklist item add/remove/relabel/required-change, or applying a
    checklist template all call `bumpVersion()` — a genuine content edit.
  - Checklist item **completion toggling** deliberately does **not** bump
    the version — mirroring `pinned`/`archived`-only changes not counting
    as content edits in Strategy Builder. Ticking a checklist item off is
    a working-state change (did I do this yet?), not a change to what the
    plan actually says.
  - Restoring a prior version applies that version's own full snapshot
    (fields + sections + checklist items) to the live rows, then calls
    `bumpVersion()` again with an auto-generated `"Restored to version N"`
    summary — the restored-from version row itself is never modified.
- **Deterministic (never an LLM call) analysis** — `lib/tradePlanAnalysis.ts`:
  - `detectMissingInformation()` — checks which of the 18 qualitative
    section kinds have real, non-whitespace content, honestly listing
    exactly what's missing.
  - `findSimilarPlans()` — scores structural overlap between plans
    (shared `plannedAsset`, `assetClass`, `direction`, `coachId`, shared
    tags), never a fabricated "semantic similarity" claim; archived plans
    are excluded from candidacy, matching Strategy Builder's own
    `archived: false` filter precedent.
  - `computeChecklistProgress()` — a pure percentage/count computation
    over an array of `{required, completed}` items — no LLM involvement
    for something that has one correct, checkable answer.
- **Checklist templates are pure application data, not a database
  concept.** `lib/tradePlanChecklistTemplates.ts`'s
  `TRADE_PLAN_CHECKLIST_TEMPLATES` array holds 3 coach-specific starter
  templates (`trading-pre-trade`, `investing-pre-position`,
  `options-pre-trade`), each a list of `{label, required}` items. Applying
  a template only bulk-seeds a plan's own `trade_plan_checklist_items`
  rows (each independently editable/completable afterward) — the template
  itself is never persisted or re-read from the database. A 4th template
  is a one-line array addition, never a migration.
- **New route file** `routes/tradePlans.ts` — full CRUD for plans plus
  their nested sections/checklist-items/versions, checklist-template
  listing, a compare endpoint (deterministic + AI), deterministic analysis
  endpoints, and 9 AI action endpoints, mounted alongside (not replacing)
  `routes/aiStrategies.ts`. Kept outside the OpenAPI/orval typed contract,
  matching Sprint 6/7/8/9's own established plain-validation convention.
  `GET/POST /trade-plans/compare[...]` is registered *before* the generic
  `GET/PATCH/DELETE /trade-plans/:id` routes, the same route-collision
  avoidance Strategy Builder's own compare endpoints required.
- **Future execution compatibility without implementing execution.**
  `executedTradeRef` (a loose, unenforced text reference — mirroring
  `trading_journal_entries.tradingPositionId`'s own established precedent
  of an intentionally-unconstrained reference column) and `executedAt`
  (a timestamp, auto-set only when a `PATCH` transitions `status` into
  `"executed"` from a different status) exist purely so a future,
  separately-approved execution sprint can link a Trade Plan to whatever
  it actually executes — this module never calls a broker, and no
  execution-linkage code exists yet beyond these two columns.
- Every list/read/write is scoped by `(user_id, coach_id)` for plans, and
  transitively via plan ownership for sections/checklist-items/versions —
  the same isolation discipline every prior sprint established. 404,
  never a separate 403, for both "doesn't exist" and "isn't yours."

## Data model

```
trade_plans
  id, user_id (FK→users, RESTRICT), workspace_id (FK→ai_workspaces, SET NULL, nullable),
  coach_id, strategy_id (FK→ai_strategies, SET NULL, nullable),
  title, planned_asset (nullable), asset_class (nullable), direction (nullable),
  status ("draft"|"ready"|"watching"|"executed"|"cancelled"|"archived", default "draft"),
  pinned, tags (text[]), current_version (int, default 1),
  executed_trade_ref (nullable, loose/unenforced), executed_at (nullable),
  created_at, updated_at

trade_plan_sections
  id, trade_plan_id (FK→trade_plans, CASCADE),
  kind (21 values — see Architecture above),
  content (nullable),
  ref_notebook_id (FK→ai_notebooks, SET NULL, nullable),
  ref_conversation_id (FK→ai_coach_conversations, SET NULL, nullable),
  ref_file_id (FK→ai_workspace_files, SET NULL, nullable),
  created_at, updated_at
  UNIQUE (trade_plan_id, kind) WHERE kind NOT IN ('attachment', 'research_reference', 'notebook_reference')

trade_plan_checklist_items
  id, trade_plan_id (FK→trade_plans, CASCADE),
  label, required (boolean), completed (boolean), position (int),
  created_at, updated_at

trade_plan_versions
  id, trade_plan_id (FK→trade_plans, CASCADE), version (int),
  snapshot (jsonb — full top-level fields + all sections + all checklist items at that moment),
  change_summary (nullable), author_user_id (FK→users, RESTRICT), created_at
  UNIQUE (trade_plan_id, version)
```

## Trade lifecycle

1. **Draft** — a plan is created scoped to a coach, optionally linked to a
   Strategy and/or filed under a Workspace, with a title and any initial
   planned-asset/asset-class/direction fields. Version 1 is recorded
   immediately.
2. **Prepare** — the user fills in the 18 qualitative sections (Market
   Context through Personal Notes), attaches references (workspace files,
   research links, notebook/conversation references), and links a
   Strategy if one wasn't chosen at creation.
3. **Review with AI** — any of the 9 explicit AI features can be invoked
   at any point: Review Trade Plan, Summarise Plan, Highlight Risk
   Factors, Review Risk/Reward, Generate Executive Summary, Generate
   Preparation Notes, Generate Pre-Trade Checklist, Generate Questions To
   Verify Before Entry, Compare Similar Plans. None run automatically,
   none overwrite a section on their own, and every prompt explicitly
   instructs the model to never recommend executing the trade.
4. **Ready checklist** — the persistent Checklist Engine tracks required
   and optional readiness items (manually added or seeded from a
   coach-specific template), showing a live completion percentage; a plan
   is not automatically transitioned to `"ready"` by checklist completion
   — the user makes that call explicitly via the status control.
5. **Status transitions** — `draft` → `ready` → `watching` → `executed`
   (or `cancelled`/`archived` from any point). Transitioning into
   `"executed"` auto-stamps `executedAt`; `executedTradeRef` can be set to
   loosely point at whatever a future execution sprint actually creates.
6. **Version history** — every content edit (field change, section
   create/delete, checklist item add/remove/relabel/required-change, or
   template application) appends a new, immutable version. Completion
   toggling alone never bumps the version. Any prior version can be
   inspected in full or restored — restoring always appends a brand-new
   version, never rewrites history.
7. **Compare** — two plans can be compared side by side, section by
   section (deterministic), or via an AI-generated narrative comparison.
8. **Delete** — deleting a plan cascades its own sections/versions/
   checklist items; the strategy, notebook, or conversation it merely
   referenced is completely unaffected. Deleting a parent workspace or
   strategy detaches (never destroys) the plan.

## Checklist engine

- Real, persistent per-item rows (`trade_plan_checklist_items`) — not an
  ephemeral in-memory list — so completion state survives a page refresh
  and a progress percentage can be honestly reported at any time.
- Each item is independently `required` or optional, independently
  completable, and independently orderable (`position`).
- `computeChecklistProgress()` is a pure, deterministic function (no LLM
  call) returning total/required/completed counts and a completion
  percentage.
- Three coach-specific starter templates (`trading-pre-trade`,
  `investing-pre-position`, `options-pre-trade`) bulk-seed a plan's
  checklist on demand; a 4th template requires only a one-line array
  addition, never a schema migration.
- Completion toggling never bumps the plan's version (a working-state
  change); adding, removing, relabelling, or changing an item's
  required/optional flag — or applying a template — always does (a
  content edit).

## AI integration

Nine explicit, user-triggered POST endpoints (plus 3 deterministic GET
endpoints for the never-an-LLM-call features), each reading the plan's own
already-saved content and reusing `coachLLM.ts`'s existing narration
machinery — **none of these run proactively, on a schedule, or auto-save
their own output. Every prompt explicitly instructs the model to never
recommend that the user actually execute, enter, or place the trade** — the
AI remains advisory only.

- **`POST /trade-plans/:id/ai/review`** — a holistic review via
  `narrateTradePlanReview()`.
- **`POST /trade-plans/:id/ai/summarize`** — via
  `narrateTradePlanSummary()`.
- **`POST /trade-plans/:id/ai/risk-highlights`** — via
  `narrateTradePlanRiskHighlights()`, whose grounding context includes
  the deterministic missing-information list so its honest fallback
  specifically flags a missing stop-loss/invalidation section as a
  significant gap.
- **`POST /trade-plans/:id/ai/risk-reward-review`** — via
  `narrateTradePlanRiskRewardReview()`, reading the plan's own
  Risk/Reward and Maximum Risk sections.
- **`POST /trade-plans/:id/ai/executive-summary`** — via
  `narrateTradePlanExecutiveSummary()`.
- **`POST /trade-plans/:id/ai/preparation-notes`** — via
  `narrateTradePlanPreparationNotes()`.
- **`POST /trade-plans/:id/ai/pre-trade-checklist`** — via
  `generateTradePlanPreTradeChecklist()`, reusing the shared
  `generateJsonListExtraction()` helper (originally generalized in
  Sprint 9). Returns `{available: false, checklist: []}` — never a
  fabricated list — whenever the LLM is unavailable or unparseable.
- **`POST /trade-plans/:id/ai/verification-questions`** — the same
  pattern via `generateTradePlanVerificationQuestions()`.
- **`POST /trade-plans/compare/ai`** — an AI narrative comparison via
  `narrateTradePlanComparison()`.
- **`GET /trade-plans/:id/missing-information`**,
  **`GET /trade-plans/:id/similar`**, and
  **`GET /trade-plans/:id/checklist-progress`** — the three
  deterministic, never-an-LLM-call features.

## Workspace integration

- A Trade Plan optionally belongs to a Workspace (`workspace_id`, nullable,
  `SET NULL` on delete — detach, never destroy).
- A Trade Plan may reference: a Strategy (top-level `strategy_id` FK), a
  Research Notebook or AI Conversation (`notebook_reference` sections), and
  Uploaded Workspace Files (`attachment` sections). A future Journal Entry
  reference is anticipated by the same loose-reference pattern
  `executedTradeRef` already establishes, but no Journal integration is
  built this sprint.
- Workspace/Strategy scoping is validated at creation and update time —
  a plan can never be filed under a workspace or strategy belonging to a
  different coach.

## Version history

Identical append-only philosophy to Strategy Builder, extended for the
Checklist Engine (see "Versioning philosophy" above): every genuine content
edit appends a new, immutable snapshot; restoring a prior version always
appends a new version rather than rewriting history; a version's own
snapshot captures fields, sections, and checklist items together, so
restoring a version restores the whole plan's state at that point in time,
not just its prose.

## Future execution compatibility

`trade_plans.executed_trade_ref` (a loose, unenforced text reference) and
`executed_at` (auto-stamped only on a genuine transition into `"executed"`)
exist so a future, separately-approved execution sprint can link a Trade
Plan to whatever it actually executes, without requiring a schema change to
this module. **No execution, order-submission, or broker-calling code
exists anywhere in this sprint** — these two columns are the entire extent
of "future execution linkage without implementing execution."

## Privacy

- Every plan, section, checklist item, and version is scoped to
  `(user_id, coach_id)` and enforced at the query level. 404, never a
  separate 403, for both "doesn't exist" and "isn't yours."
- Referencing a strategy, notebook, conversation, or file requires the
  caller to already own it — a Trade Plan section can never reference
  another user's data.
- Every AI endpoint only ever sends the requesting user's own plan content
  to the LLM.

## A disclosed, honest technology limitation: no fabricated similarity/AI judgment where a deterministic answer exists

"Identify Missing Information," "Compare Similar Plans" (the ranking
itself), and checklist progress percentages were deliberately built as
pure, deterministic functions rather than LLM calls, mirroring Strategy
Builder's own disclosed precedent — each is honestly, exactly computable
from a plan's own already-saved data, and an LLM call here would risk an
inconsistent or fabricated-sounding judgment for something that has one
correct, checkable answer.

## Future roadmap

- Order execution, broker integration, and live trading — explicitly out
  of scope for this sprint and this entire module; `executedTradeRef`/
  `executedAt` exist only as a future linkage point, not an implementation.
- Trade Journal integration (a real `tradePlanId` reference from a journal
  entry) — anticipated by this module's design but not built this sprint.
- Backtesting integration, Portfolio management integration, Auto Trading,
  and Notifications tied to Trade Plan status changes — all explicitly out
  of scope per the approved sprint boundary.
- A 4th (and beyond) checklist template is a one-line array addition to
  `lib/tradePlanChecklistTemplates.ts`, never a migration.
