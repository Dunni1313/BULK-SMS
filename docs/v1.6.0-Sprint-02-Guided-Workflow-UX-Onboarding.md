# v1.6.0 Sprint 2 — Guided Workflow UX, Onboarding & Real-World Validation

**Branch:** `v1.6.0-sprint-02-guided-workflow-ux-onboarding`
**Base:** `main` at the merged Sprint 1 commit (`191427053ccfebf6bb3a79d3f2daf82c2d1fed9e`)
**Status:** Implemented, validated, PR opened against `main`. Not merged — awaiting explicit approval.

## Sprint objective

Improve the *user experience* of the AI Trading Coach Guided Workflow
Sprint 1 already shipped — never rebuild it, never a second workflow
engine, never a duplicate of any existing AI Coach, Learning Centre,
Workflow Automation Engine, Scanner, Research, Trade Planner, Decision
Engine, Execution Centre, Portfolio, or Trade Journal. This sprint is
entirely additive to the same, one panel and the same, one pure-logic
core Sprint 1 built.

Ten focus areas were named for this sprint: first-time onboarding, the
guided daily workflow itself, resuming a session in progress, better
blocked-state explanations, a professional No-Trade workflow, Beginner
Mode improvements, context preserved between steps, a clear "Next
Recommended Action" on every screen, responsive/accessible UX, and
end-to-end workflow validation.

## A real, disclosed Sprint 1 defect found and fixed

Before writing any UX code, this sprint re-read every Sprint-1 file in
full. `useTradingCoachWorkflow()` already exposed `markStepComplete` /
`markStepSkipped`, but **nothing in the shipped UI ever called them**.
Three of the 11 steps — **Morning Brief, Research, and Daily Review** —
have no `autoDetectedStatus()` case at all (unlike Market Scan,
Opportunity Review, Trade Planning, Decision & Risk Review, Execution
Preparation, Execution, Position Monitoring, and Trade Journal, which all
auto-complete from a real existing signal). Since `computeDailyWorkflow()`
always recommends the earliest not-done step in sequence, and Morning
Brief is first, **every user's workflow was permanently stuck on step 1**
— it could never advance, and the workflow could never reach 100% for
any user, on any day. This is fixed this sprint by wiring the
already-existing mutations into the panel's UI (a **Mark Complete** and a
**Skip** action on the active step) — zero new business logic, a genuine
bug fix squarely inside "Guided daily workflow" / "Clear Next Recommended
Action on every screen," verified by this sprint's own new end-to-end
test.

## What was built

All changes are confined to 4 existing Sprint-1 files (no new files
besides tests and one E2E spec) — the same one pure-logic core, the same
one navigation-mapping module, and the same one panel component:

1. **`lib/ai-coach/tradingCoachWorkflow.ts`** — added a `waitingReason:
   string | null` field to `DailyWorkflowStep` and a new
   `stepWaitingReason()` helper. Every `not-started` step now carries a
   real, honest, non-fabricated explanation: Position Monitoring/Trade
   Journal get their own signal-based reason ("No open position to
   monitor yet" / "No closed trade awaiting a journal entry yet") when
   they have no real work yet; every other step gets a generic,
   sequence-derived reason naming the real, still-incomplete earlier step
   ("Waiting for \"Research\" to be completed first"). `blockedReason`
   (market-closed execution) is unchanged and never duplicated by
   `waitingReason`.

2. **`lib/ai-coach/tradingCoachNavigation.ts`** —
   - Every `resolveWorkflowNavigationTarget()` href now always carries
     `?workflowStep=<id>` (in addition to `?planId=` where applicable),
     so the same panel mounted on the destination page can recognize and
     confirm "you arrived here as part of today's guided workflow" —
     context preserved across the navigation with zero new state store.
   - New `resolveStepLearnEntry(stepId)` reuses
     `lib/learn/moduleLearnRegistry.ts` **verbatim** (Sprint 11, zero new
     lesson content) to point Beginner Mode's Learn trigger at the
     closest real, already-existing lesson for the *current* step
     (Research → `research-trading`, Trade Planning → `ai-trade-plan`,
     Trade Journal → `trading-journal`) instead of only ever showing the
     generic "trading-engine" path overview. Every other step honestly
     falls back to that same generic trigger Sprint 1 already shipped —
     never a fabricated topic.

3. **`components/coach/AiTradingCoachPanel.tsx`** — the same one panel,
   extended with:
   - **First-time onboarding** (#1) — a dismissible welcome callout,
     Beginner Mode only, gated by a `localStorage` flag
     (`ai-trading-coach-onboarding-dismissed`). No new backend table: no
     existing store tracks "has this user seen the coach before," and a
     purely cosmetic first-visit cue doesn't warrant a new migration —
     the disclosed limitation is that dismissal is per-device, not
     synced across devices (see Known Issues).
   - **Mark Complete / Skip** (#2, #8 — see the defect above).
   - **Resuming today's session** (#3) — a one-line "Resuming today's
     session — X of Y steps already done" banner, computed from the same
     `completedApplicableCount` Sprint 1 already returns; no new state.
   - **Real waiting-state explanations** (#4) — `step.waitingReason`
     rendered under any not-started step.
   - **Professional No-Trade alternative actions** (#5) — once a No-Trade
     reason is declared, two buttons ("Review Trading Journal," "Browse
     Learning Centre") route to the already-existing `/trading-journal`
     and `/learn` pages — never a new destination, never pressuring
     execution.
   - **Contextual Beginner-Mode Learn trigger** (#6) via
     `resolveStepLearnEntry()` — shown instead of, never alongside, the
     generic fallback trigger.
   - **`?workflowStep=` context banner** (#7) — "Continuing today's
     workflow: {Step Label}" on whichever destination page the user was
     smart-navigated to; silently absent for a plain direct visit or an
     unrecognized query value (never a fabricated label).
   - **Accessibility** (#9) — `aria-label` on the progress bar and the
     step list, `role="list"` on the step list, `aria-current="step"` on
     the active step row, `aria-hidden` on decorative status icons.

4. **New E2E spec** — `artifacts/e2e/tests/ai-trading-coach-guided-workflow.spec.ts`
   (#10) — a real, signed-up user: sees the onboarding welcome on the
   Command Centre, dismisses it, confirms Morning Brief is the honest
   first step, clicks **Mark Complete** and confirms the workflow
   genuinely advances (real progress, no longer "Morning Brief"), clicks
   **Start**, and confirms the navigation truly crosses pages carrying
   `?workflowStep=<the real next step>` — with the *same* coach panel
   present there too, showing the context-preservation banner echoing
   that same step. A smoke-level proof, matching this E2E suite's own
   established bounded-scope discipline (Phase 6, Sprints 69/70) — not a
   full 11-step walkthrough, which would require actually running a
   scan/creating research/a trade plan/a decision review. **Deliberately
   does not hardcode which specific step becomes primary after Morning
   Brief** — a fresh e2e user's very first Command Centre visit triggers
   this platform's own pre-existing, previously-documented auto-seed
   behavior (`serverState.ts`'s `ensureSeedTrades()`, first disclosed at
   Phase 6 Sprint 69 for `/portfolio-ai`), so the "fresh" account can
   legitimately already carry 3 real seeded trades — confirmed directly
   against the test database during this sprint's own validation — and
   the coach panel is *correct*, not buggy, to reprioritize Position
   Monitoring/Trade Journal ahead of a fresh scan when real open-position
   data exists (a Sprint 1 behavior, already unit-tested). The test
   asserts real progress and real cross-page context preservation
   instead, which is the genuine, environment-agnostic proof this
   sprint's own workflow fix needs.

## What was explicitly NOT touched

- No second AI Coach framework, Learning Centre, Workflow Automation
  Engine, Scanner, Research system, Trade Planner, Decision Engine,
  Execution Centre, Portfolio, or Trade Journal.
- No new backend route, database migration, or schema change of any
  kind — this sprint is 100% frontend.
- No trading calculation, pricing/probability logic, or execution
  safeguard was touched — `execution.ts`, `optionsMath.ts`, `risk.ts`,
  `autoExecution.ts`, `autoAdjustment.ts` all remain zero-line diff.
- The Achievement system (`computeAchievements()`, defined in Sprint 1)
  was **not** wired into the panel this sprint — it isn't one of this
  sprint's 10 named focus areas, and fully wiring it needs real
  cross-day historical totals (total scans run, total journal entries,
  consecutive disciplined days, etc.) that no existing endpoint currently
  returns — a genuinely larger, separate piece of work, deliberately out
  of scope here rather than rushed. See Known Issues.

## Known issues

1. **Onboarding dismissal is per-device (`localStorage`), not synced
   across devices or sessions.** A user who dismisses the welcome
   callout on one browser will see it again on another. This was a
   deliberate, disclosed choice — a purely cosmetic first-visit cue does
   not, on its own, justify a new backend table/migration; if this proves
   to matter in practice, promoting the flag into the existing
   `ai_trading_coach_preferences` table (Sprint 1, one row per user,
   already durable) is a one-column, low-risk follow-up for a future
   sprint.
2. **The Achievement system remains defined but unwired** (see above) —
   not a regression, a disclosed, deliberate scope boundary for this
   sprint.
3. **`?workflowStep=` is read but not re-validated against the panel's
   own current primary step** — it's purely a confirmation banner ("you
   arrived here for X"), never used to gate or auto-advance anything, so
   a stale/mismatched value (e.g., the user already completed that step
   via a different path before the destination page finished loading)
   only ever affects that one line of copy, never the workflow's actual
   state.
4. **Pre-existing, unrelated backend test failure (not fixed, per
   explicit instruction to only fix genuine Sprint 2 regressions):**
   `artifacts/api-server/src/lib/tradeAdjustmentPreview.test.ts`'s "Roll
   Forward" scenario (6 tests) fails deterministically, both inside the
   full suite and run in isolation. Confirmed via `git diff --stat main`
   that neither this test file nor its implementation
   (`tradeAdjustmentPreview.ts`) has any diff from Sprint 2 — logically
   impossible for a purely-frontend sprint to have caused it. Most likely
   a date-relative fixture issue in that module's own options-expiration
   logic (the same general category CLAUDE.md's own Version 1.0.0
   finalization pass previously disclosed fixing elsewhere as
   "date-drift"), but the root cause was not investigated further since
   fixing an unrelated Engine 3 (options paper-trading) module is outside
   this sprint's scope.
5. **One genuine test-authoring bug in this sprint's own new E2E spec,
   found and fixed during validation, not a production bug:** the first
   draft hardcoded "Market Scan" as the expected step after completing
   Morning Brief. A real Command Centre visit for a genuinely fresh user
   triggers the pre-existing `ensureSeedTrades()` auto-seed (confirmed via
   a direct query against the test database: the e2e user had 3 real
   trades), so the coach panel *correctly* recommends Position Monitoring
   instead — its own already-shipped, already-unit-tested "reprioritize
   an open position ahead of a fresh scan" behavior (Sprint 1). Fixed by
   asserting real progress (no longer "Morning Brief") and real
   cross-page context preservation generically, instead of a hardcoded
   step id — the correct, environment-agnostic proof.
6. **Rotating, single-spec E2E flakiness under this sandboxed session's
   own resource constraints (⚠️ environment, not Sprint 2):** across 3
   full E2E runs (2-worker, 2-worker, and fully serial
   `--workers=1`), a different pre-existing, zero-diff spec failed each
   time — `cross-engine-daily-report.spec.ts`, then `engine1-investing.spec.ts`
   and separately `engine2-trading.spec.ts` (both failing on the exact
   same "signed-up but redirected to /login" symptom in different runs),
   then `cross-engine-command-center.spec.ts` — never the same file
   twice, and never this sprint's own spec after its one real fix was
   applied. This session's own environment had already independently
   crashed the local Postgres instance once earlier in this sprint under
   full-parallel backend-test load (confirmed via `Connection refused`
   and the Postgres log showing an unclean shutdown with no corresponding
   "stopping" entry), directly evidencing this sandbox's real resource
   constraints (4 CPUs) rather than a code defect. Not fixed, per the
   explicit instruction not to change application behaviour to work
   around infrastructure limitations.
