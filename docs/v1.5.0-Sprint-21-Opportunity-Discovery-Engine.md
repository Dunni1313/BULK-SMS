# v1.5.0, Sprint 21 — Institutional Opportunity Discovery Engine

> Built and named **"Opportunity Pipeline"** in code. See §1 below for why —
> this is a disclosed naming-collision decision, not an oversight.

Sprint 21's own mandate is explicit: this is not another scanner, not
another watchlist, not another Research module. It is the disciplined
**front door** to the platform — the place every institutional workflow
should begin, by discovering, capturing, and prioritising opportunities
that already exist in signals the platform has already computed elsewhere.

---

## 0. TL;DR

- **New backend:** one small persistence table (`investing_opportunity_pipeline_items`)
  and a thin CRUD route (`routes/opportunityPipeline.ts`), plus a tiny pure
  helper module (`lib/opportunityPipeline.ts`) for the pipeline-stage
  vocabulary and deterministic "what's next" text. No new scoring formula,
  no new external data provider, no new LLM call.
- **New frontend:** a pure composition layer
  (`src/lib/opportunityPipeline.ts` + `useOpportunityPipeline.ts`) that
  reads six already-existing signal sources and turns them into one
  reusable `DiscoveredOpportunity` shape, plus a new page
  (`/opportunity-pipeline`) and a new Command Centre panel.
- **Zero new external data providers.** Every discovered opportunity traces
  to a signal an existing engine already computed this session — Market
  Intelligence, the Value Watchlist's own target-crossing check, stale
  research notes, Portfolio & Risk Intelligence's weakest factor, and the
  Knowledge Graph's emerging themes.
- **The AI Discovery Coach is deterministic, not an LLM call** — it explains
  why an opportunity surfaced, cites the exact evidence, checks it against
  held symbols, and states what research is still missing. It never
  recommends buying or selling and never predicts market direction, which
  is verified directly by test assertions.
- Protected files (`execution.ts`, `optionsMath.ts`, `risk.ts`,
  `autoExecution.ts`, `autoAdjustment.ts`) are untouched — confirmed via
  `git diff --stat` before this sprint's commit.

`routes/opportunityDiscovery.ts` / `pages/OpportunityDiscovery.tsx` /

## 2. Opportunity model

One reusable entity, in two forms:

**`DiscoveredOpportunity`** (frontend-only, computed fresh on every load,
never persisted) — the raw candidate before a user has decided it's worth
tracking:

```ts
interface DiscoveredOpportunity {
  id: string;               // stable, source-derived (e.g. "market-intelligence:earnings:AAPL:today")
  title: string;
  category: OpportunityCategory;
  origin: string;           // "which existing system supplied this" — always a real, named source
  evidence: string[];       // the actual facts behind the idea — never fabricated
  relatedAssets: string[];
  relatedSectors: string[];
  priority: "low" | "medium" | "high";
}
```

**`OpportunityPipelineItem`** (backend-persisted, once a user chooses to
"Capture into Pipeline") — everything above, plus pipeline-tracking state:

```ts
interface OpportunityPipelineItem {
  id: number;
  title, category, origin, evidence, relatedAssets, relatedSectors, priority; // as above
  stage: PipelineStage;              // see §3
  stageLabel: string;                // human label, computed fresh, never persisted
  nextRecommendedAction: string;     // deterministic, never a trading signal
  linkedNotebookId: number | null;   // reserved for a future, deeper Research Workspace link
  relatedResearchSymbol: string | null;
  createdAt, updatedAt, archivedAt: string | null;
}
```

Every category maps 1:1 onto a real origin: `watchlist_event`,
`economic_release`, `earnings`, `corporate_action`, `portfolio_gap`,
`sector_development`, `macro_change`, `knowledge_graph_relationship`,
`previously_researched`, `research_update_needed`.

**Fields named in the sprint spec but not yet independently populated,
disclosed honestly rather than silently invented:** "Related Strategies"
and "Related Playbooks" are not separate stored fields on this sprint's
`OpportunityPipelineItem` — `relatedAssets`/`relatedSectors` are populated
directly from the discovery sources, and a captured item's own connections
to strategies/playbooks/journal entries are reachable today via the
Knowledge Graph itself (every `relatedAssets` symbol is a real
`company:{SYMBOL}` node, and the Knowledge Graph's own traversal already
reaches strategies/journal/research from there — see §5). Adding dedicated,
independently-stored `relatedStrategies`/`relatedPlaybooks` arrays on the
pipeline item itself is a natural, disclosed future extension (§7), not
implemented this sprint to avoid a second, parallel copy of relationships
the Knowledge Graph already owns.

## 3. Pipeline (workflow integration)

Seven stages, exactly as specified, defined once in
`lib/opportunityPipeline.ts` (backend) and mirrored in `openapi.yaml`'s
`OpportunityPipelineStage` enum:

```
discovered → screening → research-candidate → research-in-progress
           → research-complete → strategy-candidate → archived
```

Each stage has a deterministic, computed-fresh-on-every-read "next
recommended action" (`nextRecommendedActionFor()`) — never persisted, so it
can never drift stale relative to the item's current stage, and never a
buy/sell instruction:

| Stage | Next recommended action |
|---|---|
| Discovered | Review the evidence and decide whether this is worth screening further. |
| Screening | Check the affected assets/sectors against your existing Watchlists and Portfolio & Risk Intelligence signals before committing research time. |
| Research Candidate | Promote to Research In Progress and open (or continue) a Research Workspace notebook for the affected asset(s). |
| Research In Progress | Continue building out the research notebook; mark Research Complete once your thesis is documented. |
| Research Complete | Decide whether this research supports a Strategy Candidate, or archive it if it no longer applies. |
| Strategy Candidate | Review in the Strategy Framework/Workbench — this pipeline never recommends a specific strategy. |
| Archived | No further action — this opportunity has been archived. |

**Research handoff, without a second notebook:** once an item reaches
`research-candidate` with at least one related asset, the page shows an
"Open Research Workspace →" link straight into `/stock-analyst?symbol=X` —
the existing Research Workspace. No notebook, research artifact, or
research-note row is created by this sprint's own code; the pipeline only
links into the workflow that already exists.

## 4. Command Centre integration

`InstitutionalCommandCentre.tsx` gained a new **Opportunity Pipeline**
panel, positioned directly after the existing Market Intelligence panel,
reusing the same `useOpportunityPipeline()` hook the full page uses (no
second data-fetch, no duplicated composition logic). Four concise sections,
each capped at 3 items with an honest empty-state message:

- **New opportunities** — the most recent discovered-but-not-yet-captured
  candidates.
- **High-priority candidates** — captured items still active with
  `priority: "high"`.
- **Research awaiting initiation** — captured items sitting at
  `research-candidate` (promoted, not yet started).
- **Recently archived ideas** — the most recently archived captured items.

A "View all →" link takes the user to the full `/opportunity-pipeline`
page. "Emerging themes" (also named in the spec) is intentionally not
duplicated as its own Command Centre section this sprint — Market
Intelligence's own existing panel on the same Command Centre page already
surfaces emerging themes from the Knowledge Graph; adding a second, near-
identical section on the same screen would be exactly the kind of
duplication the sprint spec warns against.

## 5. Knowledge Graph integration

Every opportunity connects to the *existing* Knowledge Graph's own
`company:{SYMBOL}` node — no new node type, no new isolated record.

A genuinely new, small, reusable helper,
`relatedResearchStrategiesLessons(graph, symbol)`, was added to
`src/lib/knowledgeGraph.ts` this sprint:

```ts
export function relatedResearchStrategiesLessons(graph, symbol): {
  research: RelatedEntity[];
  strategies: RelatedEntity[];
  lessons: RelatedEntity[];
}
```

This was extracted from logic that already existed, inline, inside
`marketIntelligence.ts`'s own per-item enrichment (Sprint 20) — the exact
same "extract on the second real consumer" precedent this codebase already
follows for `classifyMarginOfSafety()`/`historyConsistencyScore()`.
`marketIntelligence.ts` was refactored to call the new shared helper
instead of its own inline loop, and its own 56 existing tests (across
`marketIntelligence.test.ts` + `knowledgeGraph.test.ts`) pass unmodified,
proving the refactor is behavior-preserving.

`fromEmergingThemes()` reads the Knowledge Graph's own already-computed
`emergingThemes` output (Sprint 20) directly — one `knowledge_graph_relationship`
opportunity per theme, never a new theme-detection algorithm.

## 6. AI Discovery Coach

`buildOpportunityCoachNarrative(opportunity, heldSymbols)` — a small, pure,
deterministic function (`src/lib/opportunityPipeline.ts`, frontend). Given
one discovered opportunity, it produces:

```ts
interface OpportunityCoachNarrative {
  whySurfaced: string;              // names the real origin
  evidence: string;                 // restates the real evidence list
  affectedHoldings: string;         // checks relatedAssets against heldSymbols
  additionalResearchNeeded: string; // names the next pipeline step
}
```

It **never** calls an LLM, never fabricates a claim not already present on
the opportunity object, never recommends buying or selling, and never
predicts market direction. This is directly verified by a dedicated test
(`opportunityPipeline.test.ts`) asserting the narrative text contains no
buy/sell/predictive language, and by the page-level test proving the
narrative panel only ever shows text already present on the opportunity's
own `evidence`/`origin`/`relatedAssets` fields.

## 7. Future extension points (explicitly deferred, not implemented this sprint)

- **Additional opportunity sources with no new external provider:**
  `lib/portfolioEventRisk.ts` and `lib/monitoringEngine.ts` both compute
  signals that could become dedicated Opportunity Pipeline sources in a
  future sprint (today, their overlapping signals are already reachable via
  Market Intelligence's `earnings`/`corporate_action` categories, so adding
  them directly would risk double-counting the same event).
- **Dedicated `relatedStrategies`/`relatedPlaybooks` persisted fields** on
  `OpportunityPipelineItem` itself, rather than relying on the Knowledge
  Graph's own traversal from `relatedAssets` — would let a captured item
  cite a *specific* strategy/playbook it was screened against, not just the
  ones reachable transitively.
- **A genuinely new external data provider** (the sprint spec explicitly
  rules this out for now) — e.g. real-time corporate-action feeds or a real
  news/sentiment provider — would slot into `fromCategoryX()`-shaped
  functions following the exact same pattern established this sprint,
  without changing the `DiscoveredOpportunity`/`OpportunityPipelineItem`
  shape at all.
- **AI CIO orchestration (Sprint 22):** the Opportunity Pipeline's own
  "why did this surface / what evidence exists / what's next" structure is
  designed to be one of several modules a future AI Chief Investment
  Officer orchestration layer coordinates, not replaces.
