# v1.5.0, Sprint 14 — Institutional Execution & Lifecycle Manager

## Non-negotiable, stated up front

**The platform does not execute trades and never will.** There is no
order-routing feature anywhere in this codebase, and this sprint adds none.
Execution stays entirely with the user's own external broker (Alpaca or
otherwise). What this sprint builds is the orchestration layer that
manages the *lifecycle* of every investment/trade decision — before and
after that manual, external execution.

## What this is

Sprint 13 (Decision Workflow) tracks a decision's *readiness*. This sprint
picks up exactly where that leaves off and tracks what happens next:

```
Research → Notebook → Strategy → Trade Plan → Decision Workflow
  → Execution (External Broker) → Open Position → Trade Management
  → Trade Journal → Performance Review → Portfolio → Continuous Learning
```

Concretely, this sprint ships:

1. **`lib/tradeLifecycle.ts`** — the reusable lifecycle engine. Given a
   Trade Plan, its already-computed Decision stages/score (Sprint 13), a
   resolved "linked execution" (the real trades/trading-positions row the
   plan became), and its Journal entry, it derives one of **11 pipeline
   stages** (Ideas → Research → Planning → Decision Ready → Ready to
   Execute → Open Position → Managing → Closed → Journal Pending →
   Reviewed → Archived), plus Previous Stage, Next Stage, Completion %,
   Open Risk, Time in Trade, Outstanding Tasks, Journal Status, Performance
   Status, and Learning Status — every field the approved scope named.
2. **A reusable "Ready to Execute" stage** — `buildExecutionPackage()`
   generates a professional summary (Instrument, Direction, Entry, Stop,
   Targets, Position Size, Risk, Decision Score, Strategy, Notes) from the
   plan's own already-documented sections, never fabricating a value the
   plan doesn't have.
3. **`pages/ExecutionLifecycleManager.tsx`** (`/execution-lifecycle`) — a
   Pipeline board (11 kanban-style columns) plus a per-trade detail panel:
   the lifecycle summary, the Execution Package (when ready), Position
   Management, the AI Trade Manager, Continuous Learning, and an Archive
   action.
4. **Workflow validation, enforced by construction, not a separate check**
   — a plan can only reach "Ready to Execute" once its Decision Score is
   "Well-Prepared" *and* its checklist is `readyForEntry`; it can only
   become "Open Position" once genuinely marked executed; "Reviewed" only
   once a real journal entry has a real lesson learned; "Archive" is
   disabled everywhere between Open Position and Journal Pending inclusive
   — you cannot skip past unresolved portfolio impact.
5. **Command Centre integration** — a new "Execution Pipeline" card
   (trades requiring action, open positions, execution-ready count,
   pipeline bottleneck, recent completions) plus two new Workflow Panel
   stages ("Open Position"/"Trade Management"), all reusing the same
   `useTradeLifecyclePipeline()` hook, never a second computation.
6. **Platform Journey stepper integration** — `PlatformJourneyNav.tsx`
   grows from 10 to 12 stages, inserting "Open Position" and "Trade
   Management" between "Execute (external broker)" and "Trade Journal,"
   both linking to the new page.

## Lifecycle architecture

### Pipeline stage derivation (`computeTradeLifecycle`)

```
if archived or cancelled           → "archived" (outcome flag distinguishes the two)
else if a real linked execution exists (not detailUnavailable):
  if closed:
    no journal entry               → "closed"
    journal entry, no lesson yet   → "journal-pending"
    journal entry with a lesson    → "reviewed"
  else (open):
    < 1 day since open             → "open-position"
    >= 1 day since open            → "managing"
else if marked executed but no resolvable linked row → "open-position" (detailUnavailable: true)
else (pre-execution):
  DecisionScore.label "Well-Prepared" + checklist ready  → "ready-to-execute"
  DecisionScore.label "Well-Prepared" (checklist not ready) → "decision-ready"
  DecisionScore.label "Developing"    → "planning"
  DecisionScore.label "Just Started" + truly empty plan → "ideas"
  otherwise ("Early Stage", or "Just Started" with content) → "research"
```

Every branch reuses an already-computed signal (`DecisionScore.label`,
`checklistProgress.readyForEntry`, a real trade/position row's own
`status`/dates) — no new scoring formula for the pre-execution half of the
pipeline at all.

### LinkedExecution — the real trade/position a plan became

`useTradeLifecycle.ts` resolves a plan's `executedTradeRef` (a loose
string reference, Sprint 10's own established pattern) against the real
data source for that plan's `coachId`:

- **`options`** → the `trades` table (via `useListTrades()`), reading
  `status`/`openDate`/`closeDate`/`maxLoss` (open risk)/`currentPnl`
  (unrealized while open, realized once closed).
- **`trading`** → the `trading_positions` table (via
  `useListTradingPositions()`), reading `status`/`entryDate`/`exitDate`,
  and computing open risk as `|entryPrice − stopPrice| × quantity` when a
  stop is set — honestly `null` otherwise, never fabricated. Realized P&L
  is computed from `entryPrice`/`exitPrice`/`side`/`quantity` once closed.
  **Unrealized P&L for an open trading position is honestly `null`** — no
  live price feed is reused here, and inventing one would be a fabrication
  this module's whole design explicitly avoids.
- **`investing`** → **always `detailUnavailable: true`.** No discrete
  per-trade row exists anywhere in this codebase for a buy-and-hold
  investing position — Portfolio Construction/the Value Watchlist track
  *holdings*, not discrete trade events with an open/close lifecycle. An
  executed investing plan is honestly placed at "Open Position" (meaning
  "position tracked, no further pipeline detail available") and simply
  waits for the user to archive it manually — it never progresses through
  Managing/Closed/Journal Pending/Reviewed, since those stages describe an
  event (a close) that genuinely doesn't exist for this asset class in
  this codebase today. This is a disclosed, deliberate scope decision, not
  an oversight.

### Journal Status and the "Reviewed" gate

A closed trade's Journal Status is derived purely from whether a real
`journal_entries` row references it (matched the same way
`useDecisionWorkflow.ts`'s own `ReviewContext` already does — loose string
comparison against `executedTradeRef`) and whether that row's
`lessonLearned` field is non-empty. **"Reviewed" specifically requires a
real, non-empty lesson learned** — a journal entry auto-created on trade
close (the options engine's own `tradeClose.ts` behavior, pre-existing)
sits at "Journal Pending" until the user adds real reflection, matching
the sprint's own explicit distinction between logging a trade and actually
reviewing it.

### Execution Package

`buildExecutionPackage()` reads the plan's already-existing sections
(`entry_zone`, `stop_loss`, `target_1/2/3`, `position_size_notes`,
`maximum_risk`, `personal_notes`) plus the Decision Score and linked
Strategy title — every field the approved scope named. A field the user
never filled in reads honestly as `null` (rendered "Not specified" in the
UI), never a fabricated value.

### AI Trade Manager

`STAGE_GUIDANCE` is a small, deterministic reference table (one entry per
pipeline stage) covering exactly what the approved scope asked for: what
should happen now, why, institutional best practice, common mistakes, and
a checklist before progressing. This is static, disclosed reference
content — it is not AI-generated, and it never claims to be. The page's
actual free-form AI interaction is `AskCoachLauncher`, the platform's one
real AI Coach, with a stage-aware suggested question — no second, duplicate
AI system was built.

## Workflow validation

Enforced structurally, not via a separate validation layer that could
drift out of sync with the pipeline logic itself:

- **No Trade Plan → cannot become Decision Ready.** Trivially true — a
  "Decision" in this codebase IS a Trade Plan (Sprint 13's own design); the
  pipeline has nothing to classify without one.
- **Decision incomplete → cannot become Ready to Execute.** The
  `ready-to-execute` branch only fires when `DecisionScore.label ===
  "Well-Prepared"` *and* `checklistProgress.readyForEntry === true`.
- **Execution details missing → cannot become Open Position** in the full
  sense — a plan marked executed without a resolvable linked trade/position
  is honestly flagged `detailUnavailable: true` and its Outstanding Tasks
  list explicitly says "Confirm and log the full execution details for
  this position," rather than silently pretending full detail exists.
- **Journal incomplete → cannot become Reviewed.** Structurally
  impossible — "reviewed" is only ever assigned when a real, non-empty
  `lessonLearned` exists.
- **Portfolio impact incomplete → cannot Archive.** `canArchive` is
  `false` for every stage between `open-position` and `journal-pending`
  inclusive; the Archive button on the page is disabled with the real
  reason shown, and `updateTradePlan()` is never even called while blocked.

## Future broker integration points

None of this sprint's design blocks a future, explicitly-approved live
broker integration — but none is implemented, hinted at, or half-built
here either:

- `LinkedExecution` is already a normalized shape independent of its
  source (`options-trade`/`trading-position`/`investing-holding`) — a
  future live-broker sync could populate the exact same shape from a real
  Alpaca (or other) position feed without changing `tradeLifecycle.ts`'s
  own stage-derivation logic at all.
- `executedTradeRef`/`executedAt` on Trade Plans (Sprint 10's own design)
  are already the intended hook for "this plan became this real order" —
  a future automated fill-confirmation flow could populate them
  programmatically instead of the current manual entry field, again with
  zero change to the lifecycle engine itself.
- The currently-`null` unrealized P&L for open trading positions is a
  named, disclosed gap (no live price feed reused) — the natural extension
  point once a market-data feed is wired into this part of the app.

None of the above is scheduled or promised for a specific future sprint —
they are simply the seams this design already leaves open, consistent with
this codebase's own "never fabricate a capability that doesn't exist"
discipline.
