# v1.5.0 Sprint 9 — AI Strategy Builder

Branch: `v1.5.0-sprint-09-ai-strategy-builder` (stacked on
`v1.5.0-sprint-08-ai-research-notebooks`)

## What this sprint adds

**AI Strategy Builder** — a reusable, structured trading/investing playbook
that users can create, refine, version, and reuse across every trade or
thesis, positioned as the platform's central institutional playbook engine.
Built on top of Sprint 6's conversation memory, Sprint 7's AI Workspaces,
and Sprint 8's AI Research Notebooks, for the same three conversational AI
Coaches (Trading, Investing, Options). Portfolio has no conversational
coach (an exhaustive Sprint 3 finding) and has nothing registered here.

A strategy carries a title, description, strategy type, asset class, folder,
tags, favourite/archive state, lifecycle status (Draft/Active/Retired), and
17 named structured sections spanning market context through AI notes,
attachments, research links, and references back to Research Notebooks/AI
Conversations. Every edit — a top-level field change or any section
create/delete — appends a new, immutable version; restoring a prior version
never rewrites history, it applies that version's own snapshot and appends a
brand-new version of its own. 17 starter templates (Trend Following through
Growth Investing) seed a new strategy's initial sections; the architecture
is designed so an 18th template is a one-line application-code addition,
never a schema migration. Ten AI features (summarise, suggest improvements,
detect missing sections, compare two strategies, generate a setup checklist,
generate a trade-prep checklist, generate an executive summary, find similar
strategies, generate learning notes, highlight risks) are all explicit,
user-triggered actions — the AI remains advisory only, never generating
autonomous trading decisions.

This is a user-facing productivity feature built entirely on top of Sprints
6/7/8 — it does not touch trading logic, investing logic, options
calculations, the execution engine, the risk engine, prompts, tool
permissions, authentication, broker integrations, or Portfolio Coach.

## Architecture

### Backend

- **Reuse, not duplication.** Per the approved scope ("reuse Workspace
  architecture, introduce only the minimum schema required for Strategies /
  Strategy versions / Strategy sections, avoid duplicate storage"), a
  strategy section referencing a notebook, conversation, or uploaded file
  never re-stores that data — it only points at the already-existing
  `ai_notebooks`/`ai_coach_conversations`/`ai_workspace_files` row.
- **Exactly three new tables** (migration `042_ai_strategies.sql`) — the
  minimum required for Strategies / Strategy sections / Strategy versions,
  per the approved scope's own explicit instruction:
  - `ai_strategies` — one row per strategy: `user_id` (FK, `ON DELETE
    RESTRICT`, universal convention), `workspace_id` (nullable FK, `ON
    DELETE SET NULL`, mirroring `ai_notebooks.workspace_id`'s Sprint 8
    precedent — detach-not-destroy), `coach_id`, `title`, `description`,
    `strategy_type`/`asset_class`/`folder` (all **free text, not DB
    enums/CHECK constraints**, so new strategy types/folders never require a
    schema change), `status` (application-validated against
    `["draft","active","retired"]`), `pinned`, `archived`, `tags` (array),
    `current_version` (int, default 1), timestamps.
  - `ai_strategy_sections` — **one kind-discriminated table covering all 17
    named sections**, matching this codebase's own established free-text-
    discriminator convention (e.g. `ai_notebook_notes.kind`,
    `investing_filing_analysis.filing_type`): 14 singleton "qualitative"
    kinds (Market Context, Setup, Checklist, Entry, Stop, Targets, Risk,
    Position Size, Trade Management, Exit Rules, Invalidation, Common
    Mistakes, Psychology Notes, AI Notes) plus 3 many-per-strategy
    "reference" kinds (Attachments, Research Links, Notebook References).
    Every row carries 3 nullable, real-FK-typed reference columns
    (`ref_notebook_id`/`ref_conversation_id`/`ref_file_id`, all `ON DELETE
    SET NULL`) — the route layer, not the DB, decides which ref a given
    kind is expected to carry. Singleton-ness for the 14 qualitative kinds
    is enforced via a **partial unique index**
    (`UNIQUE (strategy_id, kind) WHERE kind NOT IN ('attachment',
    'research_link', 'notebook_reference')`).
  - `ai_strategy_versions` — a full, immutable snapshot log: `strategy_id`,
    `version` (monotonic per strategy, `UNIQUE(strategy_id, version)`),
    `snapshot` (jsonb — a complete copy of every top-level field plus every
    section at that moment, independent of the sections table's own current
    mutable state), `change_summary` (nullable), `author_user_id` (FK,
    `RESTRICT`), `created_at`.
- **Reference-kind mapping, resolved at the route layer:**
  - `"attachment"` → `refFileId` (an existing `ai_workspace_files` row from
    an associated workspace) **or** freehand `content` (name/URL text) —
    "references only," matching `ai_workspace_files`' own Sprint 7 precedent
    (no upload infrastructure exists anywhere in this codebase).
  - `"research_link"` → `content` only (a plain URL/text link).
  - `"notebook_reference"` → `refNotebookId` **or** `refConversationId` —
    the approved scope's own "Strategies may link to Research Notebooks
    [and] AI Conversations" requirement, folded into this one named section
    kind rather than inventing a 4th kind/table.
- **Versioning philosophy: append-only, never rewrite.** `recordInitialVersion()`
  writes version 1 immediately after creation; `bumpVersion()` appends a new
  version and advances `current_version` on every subsequent content edit
  (a top-level field change via `PATCH`, or any section create/delete via
  `POST`/`DELETE .../sections[...]`) — `pinned`/`archived`/`workspaceId`-only
  changes never bump the version, mirroring Sprint 8's own "favourite/archive
  don't count as content edits" precedent. Restoring a prior version applies
  that version's own snapshot to the live rows, then calls `bumpVersion()`
  again with an auto-generated `"Restored to version N"` summary — the
  restored-from version row itself is never modified.
- **Deterministic (never an LLM call) analysis.** "Detect Missing Sections"
  and "Find Similar Strategies" are both honestly, exactly computable from a
  strategy's own already-saved sections/tags/type/asset-class, so
  `lib/strategyAnalysis.ts` implements them with zero LLM involvement —
  `detectMissingSections()` checks which of the 14 qualitative kinds have
  real, non-whitespace content; `findSimilarStrategies()` scores structural
  overlap (shared `strategyType` = 50pts, `assetClass` = 20pts, `coachId` =
  10pts, shared tags = up to 20pts), never a fabricated "semantic
  similarity" claim.
- **Strategy templates are pure application data, not a database concept.**
  `lib/strategyTemplates.ts`'s `STRATEGY_TEMPLATES` array holds all 17
  named templates (Trend Following, Mean Reversion, Breakout, Pullback,
  Scalping, Swing Trading, Position Trading, Covered Calls, Cash Secured
  Puts, Iron Condor, Iron Butterfly, Calendar Spread, Vertical Spread,
  Wheel Strategy, Dividend Strategy, Value Investing, Growth Investing),
  each with an honestly-labelled "starting point" description and a handful
  of pre-filled qualitative sections — applying a template only seeds a new
  strategy's initial content; the user is expected to refine every section
  for their own style before relying on it. Adding an 18th template is a
  one-line array addition, never a migration, directly satisfying the
  approved scope's "architecture must allow additional templates later
  without schema changes" instruction.
- **New route file** `routes/aiStrategies.ts` — full CRUD for strategies
  plus their nested sections/versions, template listing, a compare
  endpoint (deterministic + AI), deterministic analysis endpoints, and 9 AI
  action endpoints, mounted alongside (not replacing)
  `routes/aiWorkspaces.ts`/`routes/aiCoachConversations.ts`/
  `routes/aiNotebooks.ts`. Deliberately kept outside the OpenAPI/orval typed
  contract and validated via the same small, hand-written plain-validation
  functions Sprint 6/7/8 established (avoiding the zod-dependency-conflict
  risk those sprints' own validation disclosed). `GET /ai-strategies/compare`
  and `POST /ai-strategies/compare/ai` are registered *before* the generic
  `GET/PATCH/DELETE /ai-strategies/:id` routes, to prevent Express from
  matching the literal string `"compare"` as an `:id` param value — the same
  route-collision class this monorepo's own history (a prior, unrelated
  sprint's disclosed fix) has already documented once.
- **`routes/aiNotebooks.ts` gained one additive, zero-behavior-change
  export:** its private `loadOwnedNotebook()` ownership-check helper is now
  exported so `routes/aiStrategies.ts` can reuse it verbatim when validating
  a notebook-reference section, instead of duplicating the same check —
  mirroring Sprint 8's own precedent of exporting `loadOwnedConversation()`
  for exactly this reason.
- Every list/read/write is scoped by `(user_id, coach_id)` for strategies,
  and transitively via strategy ownership for sections/versions — the same
  isolation discipline Sprint 6/7/8 established. 404, never a separate 403,
  for both "doesn't exist" and "isn't yours."

### Frontend

- `src/lib/ai-coach/strategiesApi.ts` — plain-fetch client for
  `/ai-strategies[...]`, mirroring `notebooksApi.ts`'s own established
  pattern. Every AI-narration endpoint returns its own differently-named
  field server-side (`summary`/`improvements`/`executiveSummary`/
  `comparison`/`learningNotes`/`riskHighlights`) — this client layer
  normalizes all of them to a single `{text, source}` shape
  (`StrategyNarration`) so callers never have to remember which field name
  goes with which action.
- `src/lib/ai-coach/useAiStrategies.ts` — the strategy-memory hook for one
  coachId (optionally scoped to a single workspace), mirroring
  `useAiNotebooks.ts`'s own shape: list (with folder/status/search/sort
  filters), active-strategy selection + its own fetched detail, create
  (from scratch or from a template)/update/pin/archive/delete, section
  upsert/delete, version history + restore, deterministic missing-sections/
  similar-strategies loaders, and the 8 explicit AI-narration/checklist
  actions.
- `src/lib/ai-coach/useStrategyTemplates.ts` — a tiny shared hook fetching
  the static, cross-coach template registry once per page, avoiding
  duplicated fetch-on-mount logic across all 3 coach pages.
- Nine reusable components, per the approved scope:
  - `StrategySidebar.tsx` — search, folder/status filters, an "include
    archived" toggle, an inline "New Strategy" create form (title + either
    a starter template or a free-text strategy type + optional folder), and
    `StrategyList`'s own list rendering.
  - `StrategyList.tsx` — the pure list-rendering component (loading/empty/
    populated), kept separate from the sidebar so a future strategy-
    browsing surface can reuse it without the sidebar's own search/create/
    filter plumbing.
  - `StrategyCard.tsx` — a single strategy's summary card (title, strategy
    type/asset class/folder, status badge, tags, pin/archive state,
    version).
  - `StrategyHeader.tsx` — shown once a strategy is selected: inline
    title/description/strategy-type/asset-class/folder/status editing
    (bumps `currentVersion`), pin/archive/delete, and a version badge that
    opens version history.
  - `StrategyEditor.tsx` — the strategy's own content: the 14 qualitative
    sections (each independently inline-editable), attachments (freehand
    text or a workspace-file reference), research links (multiple, plain
    URLs), and notebook/conversation references (driven by whatever the
    caller's own page already has on hand — never fetched independently).
  - `StrategyChecklist.tsx` — a small, generic, reusable checklist-
    generation component (explicit "Generate" button, honest unavailable
    state, locally-checkable items never persisted back to the server) —
    used 3 times inside `StrategySummaryPanel` (setup checklist, trade-prep
    checklist, review questions), kept standalone so any future surface
    needing a titled, generatable checklist can reuse it directly.
  - `StrategySummaryPanel.tsx` — the strategy's AI actions panel: a
    deterministic missing-sections completeness strip (loaded once, never
    re-polled), the 5 prose narration actions (summarise/suggest
    improvements/executive summary/learning notes/risk highlights), and the
    3 checklist-shaped actions via `StrategyChecklist`.
  - `StrategyComparisonView.tsx` — an A/B strategy picker plus a
    deterministic section-by-section side-by-side view and an explicit
    "Generate AI comparison" button — owns only the picker UI and
    rendering, never fetches its own data.
  - `StrategyEmptyState.tsx` — a thin, strategy-flavoured wrapper reusing
    Sprint 7's own `WorkspaceEmptyState` directly, per the approved scope's
    "reuse Workspace and Notebook components wherever possible" instruction
    — no new empty-state logic was written.
- **Integration into all 3 coach pages** (`Assistant.tsx`,
  `TradingResearch.tsx`, `StockResearch.tsx`), each following the pattern
  already established for that page's own Notebooks area:
  - `Assistant.tsx` (Options): the existing "Conversations" / "Notebooks"
    toggle gained a third option, "Strategies," swapping the entire
    left-column-plus-main-panel to the new strategy browser — a "Compare"

  - `TradingResearch.tsx` / `StockResearch.tsx` (Trading / Investing): a
    second collapsible "Show/Hide strategies" toggle sits below the

## Data model

```
ai_strategies
  id, user_id (FK→users, RESTRICT), workspace_id (FK→ai_workspaces, SET NULL, nullable),
  coach_id, title, description (nullable),
  strategy_type, asset_class (nullable), folder (nullable),
  status ("draft"|"active"|"retired", default "draft"), pinned, archived,
  tags (text[]), current_version (int, default 1), created_at, updated_at

ai_strategy_sections
  id, strategy_id (FK→ai_strategies, CASCADE),
  kind (17 values — see Architecture above),
  content (nullable),
  ref_notebook_id (FK→ai_notebooks, SET NULL, nullable),
  ref_conversation_id (FK→ai_coach_conversations, SET NULL, nullable),
  ref_file_id (FK→ai_workspace_files, SET NULL, nullable),
  created_at, updated_at
  UNIQUE (strategy_id, kind) WHERE kind NOT IN ('attachment', 'research_link', 'notebook_reference')

ai_strategy_versions
  id, strategy_id (FK→ai_strategies, CASCADE), version (int),
  snapshot (jsonb — full top-level fields + all sections at that moment),
  change_summary (nullable), author_user_id (FK→users, RESTRICT), created_at
  UNIQUE (strategy_id, version)
```

## Strategy lifecycle

1. **Create** — a strategy is created scoped to a coach, either from
   scratch (a manual `strategyType`) or from one of 17 templates (which
   also seeds a handful of initial qualitative sections), optionally
   associated with a workspace of the same coach (validated: a Trading
   strategy can never be filed under an Investing workspace). Version 1 is
   recorded immediately.
2. **Refine with AI** — the user fills in sections manually and/or uses any
   of the 10 AI features to summarise, get improvement suggestions, detect
   what's missing, generate a setup/trade-prep checklist, generate an
   executive summary, find similar strategies, generate learning notes, or
   highlight risks — every action explicit, none run automatically, none
   overwrites a section on its own (the user always decides what to save).
3. **Organise** — favourite (pin) it, archive it (hidden from the default
   list, still retrievable with `includeArchived=true`, restorable), file it
   under a folder, tag it, and set its lifecycle status (Draft → Active →
   Retired).
4. **Version history** — every content edit (a top-level field change, or
   any section create/delete) appends a new, immutable version with a
   timestamp, author, and optional change summary. Any prior version can be
   inspected in full (its own complete snapshot) or restored — restoring
   always appends a brand-new version, never rewrites history.
5. **Compare** — two strategies can be compared side by side, section by
   section (deterministic), or via an AI-generated narrative comparison
   (explicit, user-triggered).
6. **Reuse later** — every strategy, its sections, and its full version
   history persist indefinitely; deleting its parent workspace detaches
   (never destroys) it, so a curated playbook already built is never lost
   by a workspace cleanup.
7. **Delete** — deleting a strategy cascades its own sections/versions; the
   notebooks/conversations/files it merely referenced are completely
   unaffected.

## AI integration

Nine explicit, user-triggered POST endpoints (plus 2 deterministic GET
endpoints for the never-an-LLM-call features), each reading the strategy's
own already-saved content and reusing `coachLLM.ts`'s existing narration
machinery — **none of these run proactively, on a schedule, or auto-save
their own output.** The AI never generates autonomous trading decisions; it
only narrates, suggests, and drafts checklists a human reviews.

- **`POST /ai-strategies/:id/ai/summarize`** — summarises the strategy via
  `narrateStrategySummary()`. Honest fallback text (mentions section count)
  when the LLM is unavailable.
- **`POST /ai-strategies/:id/ai/suggest-improvements`** — via
  `narrateStrategyImprovements()`, whose grounding context includes the
  deterministic missing-sections list, so its honest fallback names exactly
  which sections to fill in when the LLM is unavailable.
- **`POST /ai-strategies/:id/ai/executive-summary`** — via
  `narrateStrategyExecutiveSummary()`.
- **`POST /ai-strategies/:id/ai/learning-notes`** — via
  `narrateStrategyLearningNotes()`.
- **`POST /ai-strategies/:id/ai/risk-highlights`** — via
  `narrateStrategyRiskHighlights()`, whose honest fallback specifically
  flags a missing risk/stop section as a significant gap when detected.
- **`POST /ai-strategies/:id/ai/setup-checklist`** — via a new
  `generateStrategySetupChecklist()`, reusing the established
  `aiCoreComplete` + JSON-extraction pattern (generalized from Sprint 8's
  own `generateNotebookExtractionList` into a shared
  `generateJsonListExtraction()` helper, since the original was never
  exported and safe to generalize). Returns `{available: false, checklist:
  []}` — never a fabricated list — whenever the LLM is unavailable or the
  response can't be parsed.
- **`POST /ai-strategies/:id/ai/trade-prep-checklist`** — the same pattern
  via `generateStrategyTradePrepChecklist()`.
- **`POST /ai-strategies/:id/ai/review-questions`** — the same pattern via
  `generateStrategyReviewQuestions()`.
- **`POST /ai-strategies/compare/ai`** — an AI narrative comparison of two
  strategies via `narrateStrategyComparison()`.
- **`GET /ai-strategies/:id/missing-sections`** and
  **`GET /ai-strategies/:id/similar`** — the two deterministic, never-an-
  LLM-call features (see Architecture above).

## Privacy

- Every strategy, section, and version is scoped to `(user_id, coach_id)`
  and enforced at the query level — a different user, or the same user's
  strategy under a different coach, never appears in any list or detail
  response. 404, never a separate 403, for both "doesn't exist" and "isn't
  yours" (matching Sprint 6/7/8's own established discipline).
- Referencing a notebook, conversation, or file requires the caller to
  already own it (via `loadOwnedNotebook()`/`loadOwnedConversation()`/the
  file's own parent workspace's ownership) — a strategy section can never
  reference another user's data.
- Every AI endpoint only ever sends the requesting user's own strategy
  content to the LLM — no cross-user or cross-strategy data ever enters a
  single AI call.

## A disclosed, honest technology limitation: no fabricated similarity/AI judgment where a deterministic answer exists

"Detect Missing Sections" and "Find Similar Strategies" were deliberately
built as pure, deterministic functions rather than LLM calls, since both are
honestly, exactly computable from a strategy's own already-saved data — an
LLM call here would risk an inconsistent or fabricated-sounding judgment for
something that has one correct, checkable answer. This mirrors this
codebase's own established discipline (documented across its own project
history) of never using an LLM where a deterministic computation is honestly
possible.

## Future roadmap

- A real rich-text/WYSIWYG section editor, once a specific library is
  chosen and approved (this codebase has no such library today — the same
  disclosed limitation Sprint 8 already flagged for notebook notes).
- Trade Planner, Trading Journal, Backtesting, Portfolio AI, and Market
  Scanner integrations — the data model (workspace association, notebook/
  conversation references) was deliberately designed with these in mind,
  per the approved scope's "Future Ready" instruction, but none of them are
  built this sprint.
- A dedicated "Shared" folder/visibility tier (today's `folder` field is
  free text a user sets for their own organisation only — no cross-user
  sharing exists anywhere in this feature).
- Bulk "apply a template's sections to an existing strategy" action (today
  a template only seeds sections at creation time).
