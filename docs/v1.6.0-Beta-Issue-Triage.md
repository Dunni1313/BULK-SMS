# Version 1.6 — Beta Issue Triage

**Type:** Documentation and product-planning exercise. No application code
was written or modified to produce this document. Written directly on the
already-checked-out `v1.6.0-ux-polish-phase-1` branch.

**Purpose:** define severity levels and target response times for
anything a beta tester reports that isn't purely a UX/wording/navigation
observation (those flow through `docs/v1.6.0-Beta-Operations-Guide.md`
Part B's own categorization and weekly-synthesis process instead). This
document exists specifically for the **Bugs** category from that process
— genuine defects, not preference or clarity feedback — plus the rare
case where a UX finding is severe enough to need an immediate, out-of-
cycle response rather than waiting for weekly synthesis.

**This is a beta-scale process, not a 24/7 SRE on-call rotation.** A
5–8-person beta (`docs/v1.6.0-Beta-Operations-Guide.md` §A.1) does not
need, and should not simulate, enterprise incident-response
infrastructure — the response times below reflect a small, realistically-
staffed beta operation, not a production SLA.

---

## 1. Severity Levels

### Critical

**Definition:** the platform is unsafe to keep in testers' hands as-is —
data loss, a genuine cross-account tenant-isolation leak, or any evidence
of the automation engine behaving in a way its own guardrails/kill switch
should have prevented (even though this beta runs SIMULATED-only with no
real capital at risk — a guardrail failure is still a Critical finding
about the platform's own correctness, independent of the dollar amount
behind it in this specific deployment).

**Concrete examples, grounded in this actual platform:**
- Tester A can see Tester B's trades, journal entries, watchlist, or
  settings.
- A sign-up or sign-in failure that locks a tester out entirely with no
  recovery path.
- The automation scheduler executing or closing a position that its own
  configured guardrails (position caps, daily loss limits) or the kill
  switch itself should have blocked.
- A database migration or deployment that causes data loss for any real
  beta account.
- A §2.3 genuine trust concern from `docs/v1.6.0-Beta-Success-Metrics.md`
  (a tester who is no longer sure whether an action was real or
  simulated) is treated as Critical for triage purposes even though it
  reads, superficially, like a UX finding — trust in that distinction is
  foundational, not cosmetic.

**Target response time: same day, within hours of detection.** Disarm the
kill switch immediately (`docs/Operations-Handbook.md` §6.1) as the first
action for anything in the automation-guardrail category, before any
further diagnosis — this is never the wrong first move. For a tenant-
isolation finding, follow `docs/v1.6.0-Beta-Deployment-Plan.md` §4's own
rollback guidance.

**Escalation:** the project owner is notified immediately, regardless of
time of day — a Critical finding does not wait for the next scheduled
check-in. Anything requiring a fix to a protected file (`execution.ts`,
`optionsMath.ts`, `risk.ts`, `autoExecution.ts`, `autoAdjustment.ts`)
still requires the same explicit, separately-approved, maximum-scrutiny
process `CLAUDE.md` rule 2 has required throughout this project's
history — a beta incident is not an exception to that rule, exactly as
`docs/Incident-Response-Runbook.md` §3 step 5 states identically for the
production case.

### High

**Definition:** a real defect that blocks a tester from completing a core
journey (`docs/v1.6.0-Beta-Testing-Guide.md`'s own 8 journeys), but
without the safety/data-integrity dimension that makes something
Critical.

**Concrete examples:**
- A page crashes or shows a blank/broken state for a normal, expected
  action (not an edge case the tester deliberately went looking for).
- A trade plan, journal entry, or watchlist entry a tester creates
  silently fails to save, with no error shown.
- The AI Trading Coach panel or a core workflow surface stops rendering
  entirely for a real account.
- A genuinely new (not already listed in
  `docs/v1.6.0-Known-Limitations.md`) navigation dead-end that leaves a
  tester with no way to proceed or return.

**Target response time: within 1 business day.** Diagnose against
`docs/Incident-Response-Runbook.md`'s own general workflow (§3 of that
document) if the symptom resembles a monitored condition
(`GET /api/monitoring/status`); otherwise a direct code-level
investigation.

**Escalation:** flagged to the project owner within the same day it's
confirmed High (not necessarily immediately, unlike Critical); a fix
proceeds through the normal, existing per-change approval process this
project has followed since Sprint 1 — one change, reviewed, approved,
deployed, smoke-tested (`docs/v1.6.0-Beta-Deployment-Plan.md` §5) before
resuming beta activity on the affected surface.

### Medium

**Definition:** a real defect, but one with a workaround, affecting a
secondary path rather than a core journey, or affecting only a specific
input/edge case rather than the general flow.

**Concrete examples:**
- A specific, unusual symbol or input combination produces an incorrect
  (but not data-corrupting) result on a research or analysis page.
- A secondary page (not one of the 8 core journeys) has a genuine bug.
- A cosmetic rendering issue that doesn't block understanding or action
  (distinct from Clarity feedback, which isn't a bug at all — see
  `docs/v1.6.0-Beta-Operations-Guide.md` §B.1).

**Target response time: within the beta week it was reported** (i.e.,
addressed by the following Friday synthesis at the latest,
`docs/v1.6.0-Beta-Operations-Guide.md` §B.4) — not same-day, but not left
until the beta ends either.

**Escalation:** included in the weekly synthesis summary; a fix is
proposed to the project owner as part of that same weekly review rather
than out-of-cycle.

### Low

**Definition:** a real, confirmed defect with negligible practical impact
— a tester would reasonably describe it as "I noticed this, but it didn't
actually stop me."

**Concrete examples:**
- A number formatted with one extra decimal place than intended.
- A tooltip or label with a minor typo.
- An animation or transition that looks slightly off but doesn't affect
  comprehension or action.

**Target response time: logged for post-beta backlog.** Not fixed during
the beta window itself, consistent with `docs/v1.6.0-Beta-Operations-Guide.md`
§B.4's own instruction not to iterate live against a moving target beyond
genuine Critical/High-severity response.

**Escalation:** none required beyond the normal weekly log — these
accumulate for a future, non-urgent cleanup pass.

### Enhancement

**Definition:** not a defect at all — a feature request, an
improvement-on-working-behavior suggestion, or "I wish it also did X,"
per `docs/v1.6.0-Beta-Operations-Guide.md` §B.1's own Feature Requests
category.

**Concrete examples:** anything captured under Part B §B.1's "Feature
requests" row — by definition, this severity level is the destination for
that entire category, not a distinct set of examples.

**Target response time: not actioned during the beta.** Per the explicit
instruction governing this entire phase ("we are learning, not adding
features," restated at the top of this beta phase's own kickoff), no
Enhancement-level item is implemented during the beta window, regardless
of how many testers request it independently.

**Escalation:** logged, and routed toward future roadmap planning
(alongside this platform's existing `docs/Version-2-Roadmap.md`-style
process) once the beta itself concludes — never actioned mid-beta, even
by a single small, "obviously good" change, since even a small mid-beta
feature addition would contaminate the week-over-week comparability this
beta's own success metrics rely on (`docs/v1.6.0-Beta-Success-Metrics.md`).

## 2. Severity Comparison Table

| Severity | Response time | Fixed during beta? | Escalation |
|---|---|---|---|
| Critical | Same day (hours) | Yes, immediately | Project owner notified immediately; kill switch disarmed first if automation-related |
| High | Within 1 business day | Yes | Project owner flagged same day; normal approval process |
| Medium | Within the beta week | Yes | Included in weekly synthesis |
| Low | Not during beta | No — logged | Weekly log only |
| Enhancement | Not during beta | No — logged for post-beta | Routed to future roadmap planning |

## 3. Triage Workflow

1. **Every item tagged "Bugs"** in the daily review
   (`docs/v1.6.0-Beta-Operations-Guide.md` §B.3) is immediately assessed
   against §1 above by the operator — this happens the same day it's
   reported, even though the *fix* for a Medium/Low item may not happen
   until later.
2. **When in doubt between two adjacent severities, triage to the higher
   one first**, and downgrade only after a closer look confirms the lower
   severity is genuinely correct — the cost of briefly over-responding to
   a Medium item as if it were High is far lower than the cost of
   under-responding to a real High/Critical item.
3. **Anything Critical or High halts unmoderated beta activity on the
   specific affected page/flow** (not the whole platform, unless the
   finding is itself platform-wide, e.g. a sign-in failure) until a fix is
   deployed and re-smoke-tested (`docs/v1.6.0-Beta-Deployment-Plan.md`
   §5) — communicate this honestly to the affected tester(s) rather than
   letting them keep hitting a known-broken flow.
4. **A fix for any severity still follows this project's own,
   already-established release discipline** — one change, one commit, one
   approval, deployed and smoke-tested, exactly as
   `docs/Production-Rollout-Plan.md` §5 describes for every release; a
   beta hotfix is a deployment like any other, not an exception to that
   process.
5. **Cross-check every new Bugs item against `docs/v1.6.0-Known-Limitations.md`
   before triaging it as brand-new** — several categories of "bug-shaped"
   report (an "Insufficient data" message, a market-closed blocked state,
   the two Trade Plan systems' own non-interoperation) are, per that
   document, intentional, honest platform behavior, not defects. Confirm
   the specific report doesn't differ from the already-disclosed pattern
   (e.g., the *disambiguation text itself* being missing or wrong would be
   a genuine new Medium/High finding even though the underlying two-system
   architecture is not) before dismissing it.
