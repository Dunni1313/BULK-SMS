# v1.5.0 — Sprint 2: AI Coach Framework

**Status:** Complete. Branch `v1.5.0-sprint-02-ai-coach-framework`, based
directly on `v1.5.0-sprint-01-ai-coach-consolidation` (PR #21, still open
by design — not merged). This sprint's own PR targets the Sprint 1 branch,
not `main`.

**Scope discipline:** purely architectural. No trading logic, investing
logic, options calculations, execution engine, order routing, risk engine,
authentication, or database schema was touched. Every existing coach
surface's user-visible behaviour is identical before and after this sprint
— proven by running each refactored surface's own pre-existing test suite
unmodified (or with only a mechanical, disclosed, non-behavioral assertion
update — see §7).

---

## 1. Why this sprint exists

Sprint 1 (v1.5.0) fixed naming and removed one dead component, but left
the underlying "AI Coach" implementations untouched. A full audit at the
start of this sprint found the exact same conversational state machine —
question input, an in-flight optimistic bubble, streamed-delta
accumulation, an abort-controller-backed Stop button, an honest error
turn, retry — hand-duplicated **six times** across the frontend, plus the
same validate → resolve-context → 404-or-narrate → respond/stream shape
hand-duplicated **twice** on the backend. Every specialist coach the
Blueprint's Engine 1/2/3 roadmap still names (Investing AI Coach, Portfolio
AI Coach, Options AI Coach, and whatever comes after) would otherwise have
paid that same duplication cost a seventh and eighth time.

This sprint extracts the load-bearing, genuinely-shared pieces of that
duplication into a small, reusable framework — without changing what any
existing coach does, says, or looks like.

## 2. Architecture overview

```
Backend (artifacts/api-server)
  lib/aiCoachAskHandler.ts        ← shared Express route-handler factory
      ├── routes/tradingCoach.ts      (uses it)
      └── routes/aiTradingCoach.ts    (uses it)

Frontend (artifacts/ravish-trading)
  src/lib/ai-coach/
      types.ts                   ← shared CoachTurn type
      useCoachConversation.ts    ← shared conversation-engine hook
      CoachSuggestionChips.tsx   ← shared suggestion-chip renderer
      ├── pages/TradeWorkspace.tsx              (uses the hook)
      ├── pages/MarketStructureWorkbench.tsx     (uses the hook)
      ├── pages/TradePlanningStudio.tsx          (uses the hook)
      ├── pages/LiquidityWorkbench.tsx           (uses the hook)
      ├── components/coach/TradingCoachWorkspace.tsx  (uses the hook)
      └── pages/Assistant.tsx                    (uses the hook)
```

The framework is deliberately **thin and composition-based**, not a new
runtime or a rewrite of `coachLLM.ts`/`@workspace/ai-core` (Sprint 9's
already-shipped narration core, which this sprint does not touch at all).
It captures exactly the duplication that was real and provable, and no
more — every abstraction below corresponds to code that existed in at
least two places before this sprint and now exists in one.

## 3. Backend: the shared "ask" handler factory

### `lib/aiCoachAskHandler.ts`

Both existing "ask a coach a free-form question" routers
(`routes/tradingCoach.ts`'s `/trading/coach/ask[/stream]` and
`routes/aiTradingCoach.ts`'s `/trading-coach/ask[/stream]`) independently
hand-wrote the identical shape:

1. Validate the request body against a zod schema.
2. Resolve the calling user's id.
3. Resolve whatever context the coach needs (fetching related domain data);
   404 if the referenced resource doesn't exist.
4. Either call a synchronous `narrate*()` and respond with JSON, or open
   an SSE channel (`meta` → `delta`× N → `done`/`error`) and call the
   matching `narrate*Stream()`.
5. Optionally persist the exchange and/or run a side effect once answered.

`createCoachAskHandlers<TBody, TContext>(config)` captures this shape once.
It takes:

| Config field | Purpose |
|---|---|
| `bodySchema` | zod-like schema with `.safeParse()` |
| `resolveUserId(req)` | resolves the acting user |
| `resolveContext(userId, body)` | returns `{context, fallback}` or `null` (→ 404) |
| `notFoundMessage?` | optional override for the 404 body |
| `narrate` / `narrateStream` | the domain-specific `coachLLM.ts` functions, unchanged |
| `responseSchema` | validates the outgoing JSON response |
| `onBeforeAnswer?` / `onAfterAnswer?` | side effects (e.g. persisting a message) |
| `streamErrorLogMessage` | the `req.log.error` message on a stream failure |

...and returns `{ ask, askStream }` — two ready-to-mount Express
handlers. Both existing routers now build one `createCoachAskHandlers`
config object each and mount `.ask`/`.askStream` directly; every
domain-specific function they call (`buildTradeCoachContext`,
`tradeCoachFallback`, `buildUnifiedCoachContext`, `persistMessage`, the
`narrate*`/`narrate*Stream` functions themselves) is completely unchanged.

**Result:** the SSE-plumbing/validation/404 boilerplate exists in one
place; a third, fourth, or fifth coach route (Investing/Portfolio/Options)
becomes one `createCoachAskHandlers({...})` call instead of ~80 lines of
hand-written Express glue.

Covered by `lib/aiCoachAskHandler.test.ts` (11 tests) against a hand-rolled
fake Express req/res — validation failure, context-resolution 404,
successful ask, successful stream (meta/delta/done), a mid-stream error, and
the before/after-answer hooks.

## 4. Frontend: the shared conversation engine

### `src/lib/ai-coach/useCoachConversation.ts`

The genuinely load-bearing piece of this sprint. Before this sprint, this
exact state machine was hand-duplicated six times:

- `components/coach/TradingCoachWorkspace.tsx` (the dockable "AI Trading
  Assistant")
- `pages/Assistant.tsx` (the original Options Engine "AI Assistant")
- `pages/TradeWorkspace.tsx`'s embedded deterministic-coach panel
- `pages/MarketStructureWorkbench.tsx`'s embedded panel
- `pages/TradePlanningStudio.tsx`'s embedded panel
- `pages/LiquidityWorkbench.tsx`'s embedded panel

The last four were byte-for-byte identical (same state variable names,
same handler shape, same `POST /trading/coach/ask/stream` endpoint) aside
from cosmetic strings. The first two share a fuller state machine (an
`AbortController`-backed Stop button, a distinct honest error-turn flag,
retry-last-question, and a server-persisted message list the hook itself
never needs to know about).

`useCoachConversation(options)` is deliberately **endpoint/body/answer-
shape agnostic** — `endpoint`, `buildRequestBody`, and `extractAnswer` are
all caller-supplied — so every existing coach's own wire format is served
unmodified. It owns:

- `question` / `setQuestion` — the composer input
- `history` — every completed turn (a page with server-persisted history
  simply never reads this)
- `pendingQuestion` / `streamingAnswer` / `isStreaming` — the in-flight bubble
- `stopped` — set by an explicit user-initiated abort
- `erroredReply` — set on a genuine mid-stream/server error
- `send(question?)` / `submit(e)` / `stop()` / `retry()` / `reset()`

It always maintains **both** representations of a failure — an appended
`history` turn (the wording the four embedded panels already rendered) and
the distinct `erroredReply` flag (`TradingCoachWorkspace`/`Assistant.tsx`'s
own dedicated error-turn convention) — so every existing consumer keeps
working from the one shared hook without either behaviour changing.

`reset()` was added specifically to preserve
`TradingCoachWorkspace.tsx`'s pre-existing `handleClearConversation()`
behaviour (clearing `pendingQuestion`/`streamingAnswer`/`stopped`/
`erroredReply` without touching `history` or aborting an in-flight
request) byte-for-byte.

Covered by `useCoachConversation.test.ts` (18 tests via `renderHook`):
send/submit, empty/disabled no-ops, delta accumulation, default and
custom `extractAnswer`, history append on success and on error, stop
leaving the partial answer visible, retry re-sending the last question,
`onAnswered` firing only on success, `buildRequestBody` being
re-evaluated fresh on every call, and `reset()`'s exact field-clearing
behaviour.

### `src/lib/ai-coach/CoachSuggestionChips.tsx`

A small, genuinely new (not duplicated-then-extracted) generic
"suggestion card" component: a row of clickable, pre-filled-question
chips. Modeled on `TradingCoachSuggestedPrompts.tsx` (which is left
completely untouched — it still owns its own `trading-coach-suggested-
prompt*` test ids and its own passing test suite) so a future specialist
coach can import this shared building block directly instead of
hand-rolling another copy. Covered by 5 new tests
(`CoachSuggestionChips.test.tsx`): empty-render, per-suggestion chip
rendering with the default test id, `onSelect` firing with the exact
suggestion text, the disabled no-op, and a caller-supplied test-id prefix.

### `src/lib/ai-coach/types.ts`

`CoachTurn { question: string; answer: string }` — the one shared shape
every coach's completed-turn history uses.

## 6. Adding a future coach — what it now takes

**Backend:** one `createCoachAskHandlers({ bodySchema, resolveUserId,
resolveContext, narrate, narrateStream, responseSchema })` call plus
whatever domain-specific `resolveContext`/`narrate*` functions the new
coach genuinely needs (which would have to exist regardless).

**Frontend:** one `useCoachConversation({ endpoint, buildRequestBody })`
call in the new coach's component, rendering `coach.question` /
`coach.history` / `coach.pendingQuestion` / `coach.streamingAnswer` /
`coach.isStreaming` / `coach.stopped` / `coach.erroredReply` and wiring
`coach.submit` / `coach.stop` / `coach.retry` to the existing composer UI.
A suggested-prompts row can reuse `CoachSuggestionChips` directly.

This is the concrete reduction in "minimal code to add a new AI Coach"
the sprint's design goals asked for.

## 7. Remaining duplication (deliberately not touched this sprint)

- **`TradingCoachSuggestedPrompts.tsx`** still exists as its own
  domain-specific component rather than a thin wrapper over
  `CoachSuggestionChips`. Left alone to avoid any regression risk to its
  own passing test suite for a single current consumer; a future cleanup
  sprint could turn it into a wrapper with zero behaviour change.
- **Prompt/system-prompt text and per-domain narration logic**
  (`coachLLM.ts`'s `narrate*`/`narrate*Stream` functions, and each
  route's own `resolveContext`/context-building helpers) are intentionally
  untouched — they are genuinely domain-specific (Trading vs. the
  original Options coach vs. whatever Investing/Portfolio/Options AI
  Coach eventually need) and Sprint 9 already centralised the actually
  shared narration/disclaimer core (`@workspace/ai-core`).
  `useCoachConversation`/`createCoachAskHandlers` sit one layer above that
  — they never duplicate or reimplement any of it.
- **Layout/shell components** (`TradingCoachHeader`,
  `TradingCoachContextPanel`, `TradingCoachMessages`,
  `TradingCoachComposer`, `TradingCoachDisclaimer`) remain
  `TradingCoachWorkspace`-specific presentational components. They were
  read in full during this sprint and found to already take fully generic
  props (no Trading-specific business logic inside them) — a future coach
  could reuse them as-is or via thin renames, but doing so wasn't required
  to satisfy this sprint's "keep behaviour identical" mandate and was left
  for a future, purpose-built extraction once a second full-featured
  ("Tier A") coach actually needs them.

## 8. Future extension points

- A generic message-list renderer (analogous to `TradingCoachMessages`)
  could be extracted into `src/lib/ai-coach/` once a second Tier-A coach
  needs one, following the exact "extract on the second real caller"
  precedent this sprint itself followed for `CoachSuggestionChips`.
- `createCoachAskHandlers` could grow an optional rate-limiting or
  auth-scoping hook if a future coach needs one, without changing any
  existing caller's config shape (new fields would be optional).
- `useCoachConversation`'s `history` is currently unbounded in memory;
  a future coach with very long conversations could add an optional
  `maxHistory` trim — not needed by any existing consumer today.
