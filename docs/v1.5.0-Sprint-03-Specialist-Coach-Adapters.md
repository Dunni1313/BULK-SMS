## 1. Sprint objective

Connect the platform's specialist AI Coaches to the shared AI Coach
Framework Sprint 2 built (`useCoachConversation()` on the frontend,
`createCoachAskHandlers()` on the backend), converting each into a thin,
configuration-driven adapter while preserving its existing specialist
prompts, data context, and behaviour exactly.

## 2. Investigation — what actually exists

Before writing any code, every candidate "AI Coach" surface in the
codebase was read, not assumed. This surfaced a genuine architectural
finding that reshaped the sprint's actual scope (see §3).

### 2.1 The real free-form chat coaches

Only three surfaces in the entire codebase are genuine, multi-turn,
free-form Q&A conversations (question input → streamed answer →
persisted/local history → retry/stop where applicable) — the shape
`useCoachConversation()` exists to serve:

| Coach | Page | Endpoint | Backend narration |
|---|---|---|---|
| Trading AI Coach | `TradingResearch.tsx`'s embedded "AI Trade Coach" panel (Phase 3, Sprint 47/48) | `POST /trading/coach/ask/stream` | `narrateTradeFreeform`/`Stream` |
| Investing AI Coach | `StockResearch.tsx`'s "Ask the AI Investment Analyst" panel (Phase 2, Sprint 30) | `POST /stock-analyst/value-research/ask/stream` | `narrateValueFreeform`/`Stream` |
| Options AI Coach | `Assistant.tsx` (labeled "AI Assistant" since Sprint 1's naming consolidation; still the Options Engine's own specialist coach domain) | `POST /ai/chat/stream` | mode-dispatched across several `narrate*` functions + deterministic templates |

A fourth, related surface — `TradingCoachWorkspace.tsx` ("AI Trading
Assistant," the unified cross-engine coach, `/trading-coach/ask/stream`) —
was already migrated onto the shared hook in Sprint 2 and is **not** one of
this sprint's four named targets; it is a distinct, superset domain (see
Sprint 1's own disambiguation of "Trading AI Coach" vs. "AI Trading
Coach").

Every other "Coach"-branded surface in the codebase (`TradingAICoach.tsx`,
`InstitutionalAICoach.tsx`, `PortfolioAnalyst.tsx`, and the ~15
`GET .../coach[/:topic]` deterministic explanation routes across the
Institutional-X-Engine composition tier) is confirmed, by direct reading,
to have **no question input, no conversation history, and no LLM call at
all** — they are per-topic explanation/evidence-explorer pages, a
structurally different pattern this sprint does not touch.

### 2.2 The Portfolio gap — a genuine finding, not an oversight

**No conversational "Portfolio AI Coach" exists anywhere in this
codebase.** `PortfolioAI.tsx` has exactly two LLM-narration triggers —
Market Briefing narration (`POST /briefing/stream`) and Report Comparison
narration (`POST /reports/compare-narration/stream`) — and both are
**one-shot "click to narrate" buttons**: no question input, no
back-and-forth, no retry/stop loop. This was confirmed exhaustively before
any code was written: every `streamCoach(` call site in the frontend was
enumerated and read, every `router.(get|post)(...)` route with "coach" or
"ask" in its path was grepped across the entire backend, and
`institutionalMentor.ts`/`portfolioAnalyst.ts` were confirmed to have zero
LLM/streaming capability of any kind.

**Explicit project-owner decision:** do not invent a conversational
Portfolio coach this sprint. Sprint 3 is a refactoring sprint, not a
feature-development sprint — building a true multi-turn "Portfolio AI
Coach" would mean creating new product functionality (a question input, a
history list, a retry loop) that does not exist today, which the sprint's
own "do not invent new product behaviour" instruction rules out. The two
existing Portfolio narration buttons were **not touched, not wrapped,
not converted, and not given a new UI or endpoint** — they remain exactly
as they were before this sprint, confirmed by a zero-line diff on
`PortfolioAI.tsx`.

**Documented for a future feature sprint:** Portfolio currently exposes
one-shot AI narration rather than a conversational coach. Creating a
conversational Portfolio Coach is a real, well-scoped, but genuinely new
feature — it is intentionally deferred, not solved here.

## 5. The specialist coach adapter contract

`CoachConfig<TParams>` (`src/lib/ai-coach/types.ts`) — a plain, declarative
object every specialist coach now defines exactly once:

| Field | Purpose |
|---|---|
| `id` | Unique id, e.g. `"trading"` \| `"investing"` \| `"options"` |
| `displayName` | Human display name, e.g. "Trading AI Coach" |
| `description` | One-line description of what the coach answers and what grounds it |
| `capabilities` | The specialist-only data/analysis this coach is grounded in — documents context/tool isolation |
| `endpoint` | The SSE streaming endpoint path, unchanged from the coach's own pre-existing endpoint |
| `buildRequestBody(question, params)` | Builds the request body — the coach's own "context provider" |
| `isDisabled?(params)` | True while sending should be blocked (e.g. no symbol chosen) |
| `errorMessage?` | The honest failure-turn text; falls back to the shared hook's own default when omitted |
| `starterPrompts?(params)` | Optional canned starter questions, derived from the coach's own params |

`useSpecialistCoach(config, params, options?)`
(`src/lib/ai-coach/useSpecialistCoach.ts`) is the one place a config
actually gets wired into `useCoachConversation()` — it reads
`config.endpoint`/`config.buildRequestBody`/`config.isDisabled`/
`config.errorMessage` and returns the exact same
`UseCoachConversationResult` every existing consumer already expects.
A specialist coach page calls this once instead of constructing its own
inline `useCoachConversation({...})` options object — "what this coach
answers" (the config) is now separate from "how a conversation is
streamed/retried/stopped" (the shared hook), matching the sprint's own
"Each specialist coach should define only what is unique to that coach"
design goal.

Fields deliberately **not** added to the contract, and why:
- **System prompt** — prompts are server-owned (`coachLLM.ts`'s
  `*Freeform*` functions and mode-dispatch templates); a frontend config
  restating them would risk drifting out of sync with the real prompt.
  `description`/`capabilities` document what grounds the coach instead.
- **Available tools (as function-calling tools)** — no coach in this
  codebase performs LLM tool-calling; `capabilities` is the honest,
  accurate equivalent (a documented list of the specialist data each
  coach's context is built from).
- **Empty-state content / access-permission rules** — empty-state copy
  stays page-specific JSX (tightly coupled to each page's own layout);
  access is uniform across all three coaches (session-scoped via
  `getScopedUserId`, no per-coach variation), so forcing it into the
  config would be a field with one constant value everywhere — exactly
  the kind of "force domain-specific logic into a generic abstraction"
  the sprint's own instructions warn against.

## 6. Coaches migrated

### 6.1 Trading AI Coach
- **Backend:** already on `createCoachAskHandlers()` since Sprint 2 — zero
  backend change this sprint.
- **Frontend:** `TradingResearch.tsx`'s embedded "AI Trade Coach" panel
  (the page's own deprecated-but-still-functional "legacy inline
  assistant") now calls `useSpecialistCoach(tradingCoachConfig, { symbol
  })`. `tradingCoach.config.ts` declares `capabilities: ["market-structure",
  "multi-timeframe", "liquidity", "regime", "probability",
  "trading-risk"]`, `isDisabled: !symbol`, and starter prompts
  interpolating the current symbol.
- **Preserved exactly:** endpoint (`/trading/coach/ask/stream`), request
  body (`{symbol, question}`), disabled-without-symbol behaviour, error
  wording, every `data-testid`.

### 6.2 Investing AI Coach
- **Backend:** `routes/stockAnalyst.ts`'s `/value-research/ask` and
  `/value-research/ask/stream` now build on `createCoachAskHandlers()`,
  mirroring Sprint 2's `tradingCoach.ts`/`aiTradingCoach.ts` conversions —
  `resolveContext` rebuilds the value-research report and returns
  `{context: buildFreeformContext(report), fallback: freeformFallback(report,
  question)}`, honestly 404ing for an unknown symbol exactly as before.
  `narrate`/`narrateStream` are `narrateValueFreeform`/
  `narrateValueFreeformStream` passed through unchanged.
- **Frontend:** `StockResearch.tsx`'s "Ask the AI Investment Analyst"
  panel now calls `useSpecialistCoach(investingCoachConfig, { symbol:
  report.symbol })`. `investingCoach.config.ts` declares `capabilities:
  ["company-research", "valuation-fundamentals", "investment-committee"]`.
- **Preserved exactly:** endpoint, request body (`{symbol, question}`),
  response shape (`{answer, answerSource}`), 404 behaviour, error wording,
  every `data-testid`.

### 6.3 Options AI Coach
- **Backend:** `routes/ai.ts`'s `/ai/chat[/stream]` was deliberately left
  **untouched**. Direct inspection found it mode-dispatches across several
  distinct `narrate*()` functions plus deterministic templates and bakes
  message persistence directly into the route with its own `{id, message,
  createdAt}` response shape — a genuinely different shape from the single
  `narrate`/`narrateStream`-pair contract `createCoachAskHandlers()`
  captures. Forcing it into that factory would mean distorting the shared
  abstraction to fit one domain-specific case, which the sprint's own "do
  not force domain-specific logic into generic abstractions" instruction
  rules out.
- **Frontend:** `Assistant.tsx` (already on `useCoachConversation()` since
  Sprint 2, but with inlined literals) now calls
  `useSpecialistCoach(optionsCoachConfig, { mode, level })`.
  `optionsCoach.config.ts` declares `capabilities: ["greeks",
  "probability-of-profit", "expected-value", "trade-explanation", "quiz"]`.
- **Preserved exactly:** endpoint, request body (`{message, mode, level}`),
  the mode==="auto" → undefined translation, every `data-testid`.

### 6.4 Portfolio — intentionally unchanged
See §2.2. Zero code touched in `PortfolioAI.tsx`, `routes/portfolioAI.ts`,
or anywhere else in the Portfolio domain.

## 8. Context isolation and tool isolation

Proven directly, not just asserted, by `useSpecialistCoach.test.ts`:

- Every coach's `id` and `endpoint` are unique (`toBe` a `Set` of size 3).
- No two coaches' `capabilities` arrays are equal.
- Each coach's `capabilities` list is checked against every other coach's
  domain-specific terms and asserted to never contain them (e.g. Trading's
  capabilities never include `"greeks"` or `"valuation-fundamentals"`).
- Two different coaches' hook instances (Trading + Investing) never share
  `question`/`history`/`streamingAnswer` state — a completed Trading turn
  never appears in the Investing coach's own history.
- Two instances of the **same** coach config with different params (e.g.
  Trading AI Coach for AAPL vs. Trading AI Coach for TSLA) never leak state
  into each other — proving isolation holds per-instance, not just
  per-config.
- Each coach's own `buildRequestBody` only ever reads its own declared
  `TParams` shape — `tradingCoach.config.ts` never imports
  `OptionsCoachParams`, etc. (enforced structurally by TypeScript's own
  generic constraint, confirmed by a clean typecheck).

## 9. Compatibility considerations

- Zero routes removed, renamed, or given a new request/response shape.
- Zero database schema or migration changes.
- Zero `openapi.yaml` changes — the two ask/stream SSE endpoints were
  already, and remain, deliberately outside the OpenAPI/orval contract
  (matching the codebase's own established precedent that orval only
  models single-shot JSON responses).
- The only observable frontend difference anywhere: `streamCoach()` is now
  always called with an `AbortSignal` as its 4th argument for the Trading
  and Investing Ask panels (previously never passed by either) — the same
  harmless difference already disclosed and accepted in Sprint 2's own
  report, since neither panel exposes a Stop button the signal could ever
  trigger.

## 14. Recommended Sprint 4 extension points

1. **A conversational Portfolio AI Coach**, if the project owner decides
   this is worth building as new product functionality — would need its
   own backend `/portfolio/coach/ask[/stream]` route (or similar),
   grounded in account/holdings/exposure data, following the exact
   `createCoachAskHandlers()` + `CoachConfig` pattern this sprint
   established for the other three.
2. **A shared message-list renderer**, extracted once a second full
   history-rendering surface (beyond `TradingCoachWorkspace.tsx`) needs
   one — following this sprint's own "extract on genuine second need"
   discipline (the same precedent `CoachSuggestionChips` set in Sprint 2).
3. **Wiring `starterPrompts`/`capabilities` into the actual rendered UI**
   — all three configs now declare real, tested starter-prompt logic, but
   no page's JSX renders them yet (each page's own existing suggested-
   prompt UI, where one exists, remains unchanged this sprint, per the "no
   functional changes" mandate). A future sprint could render
   `config.starterPrompts(params)` via the existing `CoachSuggestionChips`
   component for a genuine, disclosed UX improvement.
