# v1.5.0 Sprint 11 — Platform Integration

Branch: `v1.5.0-sprint-11-platform-integration` (stacked on
`v1.5.0-sprint-10-trade-planner`)

## What this sprint is — and what it deliberately is not

This is an **integration sprint, not a feature-building sprint**. Sprints
1–10 built ten genuinely new modules (AI Coach consolidation, the Coach
Framework, specialist adapters, context/tools, memory, Workspaces, Research
Notebooks, Strategy Builder, and the Institutional Trade Planner) on top of
an already enormous pre-existing platform (Phases 1–44, ~90 routes, its own
mature Learning Centre, its own mature AI-coaching infrastructure). Before
this sprint began, a full repository audit was run and approved as
mandatory design input (see "Reuse decisions" below) — its central finding
was that almost everything the platform would ever need already existed
somewhere; the gap was never missing capability, it was that a first-time
user landing on any one of ~90 pages had no way to know **what that module
is, why it exists, how it fits into the workflow, or what to do next.**

Per the explicit kickoff scope, this sprint:

- Reuses the existing Learning Centre (`learningPaths.ts`, `glossary.ts`,
  `learningProgress.ts`, `LessonRenderer.tsx`) and the existing AI Coach
  framework (`lib/ai-core`, `coachLLM.ts`, `AskCoachLauncher`) — it builds
  **zero new lesson content and zero new coaching backend**.
- Extracts shared UI components where real, byte-for-byte duplicated
  markup existed (`EquityCurveChart`, `ScoreRing`) — with the explicit
  constraint that visual behaviour must not change.
- Adds a shared, page-embeddable "Learn" drawer (`ModuleLearnDrawer`/
  `ModuleLearnTrigger`) so a user can read contextual teaching content
  without navigating away from the module they're using.
- Adds a shared workflow stepper (`PlatformJourneyNav`) so a user always
  sees where they are in the 9-stage Research → Notebook → Strategy →
  Trade Plan → Execute (external broker) → Trade Journal → Performance
  Review → Portfolio Impact → Continuous Learning journey, on every major
  page that participates in it.
- Widens the existing `CoachLevel`/AI-narration-depth vocabulary from 2
  values to the Learning Centre's own existing 4-value
  Beginner/Intermediate/Advanced/Institutional vocabulary, so "one shared
  coaching experience" (the kickoff's own phrase) is genuinely one
  vocabulary, not two overlapping ones.

Explicitly, deliberately **out of scope**, confirmed unmodified for the
entire sprint: no new Trade Journal, no new Portfolio module, no new
Watchlists, no new Reports, no new Analytics, no new Risk engine, no new
Learning Centre. No existing business logic, calculation, API contract
(beyond the two additive enum widenings described below), database table,
report, or dashboard was rewritten or removed.

## Reuse decisions

The pre-sprint Architecture & Reuse Review (delivered and approved before
any Sprint 11 code was written) categorized ~25 named feature areas —
Trade Journal, Trade History, Performance Dashboard, Strategy Analytics,
Portfolio Analytics, Research, Watchlists, AI Coaching, Learning Centre,
Tutorials, Glossary, AI Explanations, Reports, Position Sizing, Risk
Modules, and more — into Already Exists / Can Be Reused / Needs
Refactoring / Needs Migrating / Needs Replacing / Completely Missing. The
review's headline finding, made a mandatory design rule for this sprint:
almost nothing was "Completely Missing" — the true gap was **discoverability
and connective tissue**, not capability. That review's own findings are
the direct source of every decision below.

**One correction to the review's own earlier claim, made during this
sprint's implementation and disclosed here rather than silently folded
in:** the review had stated "no next-lesson recommendation logic exists."
That was wrong. Direct investigation of `learningPaths.ts`/
`LessonRenderer.tsx` while building `ModuleLearnDrawer` found a fully
working `nextStepKeys` field and a rendered "Next: {title}" link already
present and already correct — this sprint reuses it as-is; it did not need
building.

**Reused verbatim, zero modification to their own logic:**

- `learningPaths.ts` — the entire lesson content model (`LearningTopic`,
  `hasRichLessonContent()`, `nextStepKeys`), read by `ModuleLearnDrawer`
  exactly the way `pages/learn/LearningPaths.tsx`'s own `PathDetail` view
  already reads it.
- `glossary.ts`, `learningProgress.ts` — untouched; `ModuleLearnDrawer`
  calls the same generated `useGetLearningProgress`/
  `useRecordLearningItemViewed`/`useRecordLearningItemCompleted` hooks the
  full Learning Centre page already calls, so progress tracked from inside
  a module's drawer and progress tracked from the full `/learn` page are
  the same rows, not two parallel tracking systems.
- `LessonRenderer.tsx`, `AskCoachLauncher`, `RelatedGlossaryBadges`,
  `BookmarkButton` — `ModuleLearnDrawer` renders a topic via the exact same
  `LessonRenderer` component the full-page Learning Centre uses, so a rich
  lesson looks and behaves identically whether opened from `/learn` or
  from a drawer inside `TradingResearch.tsx`.
- `lib/ai-core`'s `narrate()`/`narrateStream()`/cache/single-flight
  machinery, `coachLLM.ts`'s domain layer, every existing coach panel
  (`AskCoachLauncher`, `CoachDrawer`, the per-engine coach pages built in
  Phases 21/29) — none of this sprint's work replaces or wraps any of it a
  second time.

**Extracted, not duplicated — visual behaviour preserved exactly:**

- `EquityCurveChart` (`components/charts/EquityCurveChart.tsx`) — the
  identical recharts `LineChart`/`CartesianGrid`/`XAxis`/`YAxis`/`Tooltip`/
  `Line` markup was hand-duplicated across `Backtest.tsx`,
  `OptionsBacktest.tsx`, and `TradingBacktest.tsx`. All three now import
  one shared component; the only externally observable choice is a
  `dateTickFormat` prop (`"month-day"` vs. `"month-year"`) matching each
  page's own pre-existing tick format.
- `ScoreRing` (`components/charts/ScoreRing.tsx`) — `Dashboard.tsx` had a
  local `ScoreRing` function and `PortfolioDashboard.tsx` had a
  differently-sized local `HealthGauge` function, both wrapping the same
  recharts `RadialBarChart`/`RadialBar` gauge shape with different fixed
  dimensions. Extracted into one component parameterized by `size: "sm" |
  "lg"`, with a `SIZE_CONFIG` table carrying each size's *exact* original
  dimensions (box/cx/cy/innerRadius/outerRadius/barSize/cornerRadius/text
  size) — including, deliberately, that `cornerRadius` is **not** derived
  from `barSize` (the two pre-existing call sites used different,
  independent values for each; deriving one from the other would have
  been a silent, disclosed-here-to-avoid, visual regression). Colour stays
  a caller-supplied prop in both cases — `Dashboard.tsx` continues to use
  its own pre-existing `TIER_COLOR` lookup and `PortfolioDashboard.tsx`
  its own pre-existing `ratingColor()` function, neither of which was
  merged into the shared component, since they are genuinely different,
  page-specific vocabularies (opportunity tier vs. portfolio health
  rating) — merging them would have been exactly the kind of
  unnecessary, out-of-scope refactor this sprint avoided.

**Deliberately left duplicated, and why:** `TIER_COLOR` (Dashboard.tsx) and
`ratingColor()` (PortfolioDashboard.tsx) look superficially similar (both
map a status code to a hex colour) but encode two different real-world
taxonomies (opportunity conviction tiers vs. portfolio risk ratings).
Merging them into one shared colour table would not have removed real
duplication — it would have coupled two independent concepts for no
behavioural benefit, which is the opposite of this sprint's own stated
goal.

## Migration decisions

No table, route, or generated client was migrated or moved this sprint.
The only schema-adjacent change is two additive OpenAPI enum widenings
(see below) — both are backward compatible; no existing value was
renamed or removed, so no client that only ever sent `"beginner"` or
`"advanced"` is affected.

## Learning framework

Per the explicit instruction not to build a second learning system, this
sprint adds exactly one new mapping layer and one new rendering surface,
both thin:

- **`lib/learn/moduleLearnRegistry.ts`** — a small, explicit
  `Record<string, ModuleLearnEntry>` naming, for each of the 8 modules
  this sprint wires up, which existing `learningPaths.ts` path (and,
  where a single topic is the closest match, which topic) that module's
  "Learn" button should open. Every one of the 8 `pathKey`/`topicKey`
  pairs was verified against real, already-shipped `learningPaths.ts`
  content before being committed (see "Verification" below) — none is
  fabricated or points at a placeholder.
- **`ModuleLearnDrawer`** — a `Sheet` that fetches via
  `useGetLearningPathByKey`/`useGetLearningProgress`, shows a topic list
  when no specific topic is requested, opens directly to a topic when one
  is, marks a topic "viewed" the moment it's opened (the same
  `useRecordLearningItemViewed` mutation the full-page Learning Centre
  fires), and links out to the full `/learn/paths/{pathKey}[/{topicKey}]`
  page for anyone who wants the complete, non-drawer experience. It is
  layered entirely on top of the existing data/mutation layer — it adds
  no new backend route, no new database table, no new content field.

**Two honestly-disclosed mapping simplifications, not gaps in the
underlying Learning Centre:**

1. Several of this sprint's own newest modules (Notebook, Strategy, Trade
   Plan panels inside `Assistant.tsx`) don't have their own dedicated
   `learningPaths.ts` topic yet — authoring new lesson content was
   explicitly out of scope for an integration sprint (see "Strictly out
   of scope," above). Where no exact-match topic exists, the registry
   points at the closest existing lesson instead (e.g. the AI-Coach
   Trade Planner's own "Learn" trigger opens the pre-existing Engine 2
   `trading-trade-planning` lesson, which documents the conceptually
   related — but not identical — "Trade Plan" feature from the
   Trade Planning & Risk Studio module). The drawer's `moduleLabel` prop
   always correctly names the real module that's open, so this is never
   presented as a perfect match — only as the closest available teaching
   content, honestly.
2. `PlatformJourneyNav`'s Notebook/Strategy/Trade Plan stages all link to
   `/assistant`, since those three panel families are toggled views
   inside that one page rather than separate routes. This is disclosed
   directly in the component's own header comment, not hidden.

## Teaching framework — the "single shared coaching experience"

- **`CoachLevel` widened from 2 to 4 values.** `lib/ai-core/src/index.ts`'s
  `CoachLevel` type was `"beginner" | "advanced"`; it is now `"beginner" |
  "intermediate" | "advanced" | "institutional"` — deliberately reusing
  `learningPaths.ts`'s own already-existing `LearningDifficulty`
  vocabulary rather than inventing a fifth naming scheme. `levelInstruction()`
  gained two new prompt-depth branches (Intermediate: "assume the reader
  knows the basic mechanics already... connect the answer to how it fits
  into a broader workflow"; Institutional: "assume the reader is a
  professional practitioner; be terse, cite institutional practice and
  process directly, skip basic definitions entirely"). `levelKey()` needed
  no change — it was already generic over any string.
- **`openapi.yaml`'s `ValueResearchInput.level` and `AiChatInput.level`**
  (the two enums that are genuinely driven by `CoachLevel`) were widened
  to match, then `api-zod`/`api-client-react` regenerated — this is what
  makes `Assistant.tsx`'s and `StockResearch.tsx`'s pre-existing "Depth"
  `ToggleGroup` selectors able to offer all 4 levels instead of 2, using
  the code that was already there.
- **Two superficially similar `level` fields were deliberately NOT
  touched**, since they encode different concepts: `ValueLesson.level`
  (a content-difficulty tag on a lesson, already independently 3-valued)
  and `EventRiskAssessment.level`/its own free-text severity field (risk
  severity, not coaching depth). Widening either would have been an
  incorrect, over-broad change disguised as a "shared vocabulary"
  improvement.
- No new coach backend, no new prompt-assembly pipeline, no new
  disclaimer-enforcement path was added — every one of the 4 levels flows
  through the exact same `narrate()`/`narrateStream()` call every coach
  domain already used before this sprint.

## Navigation improvements

- **`PlatformJourneyNav`** (`components/layout/PlatformJourneyNav.tsx`) —
  a compact, always-visible 9-stage stepper (Research → Notebook →
  Strategy → Trade Plan → Execute (external broker) → Trade Journal →
  Performance Review → Portfolio Impact → Continuous Learning), matching
  the exact stage list from the mid-sprint clarification. Past stages
  show a check, the current stage is visually highlighted and non-
  clickable, future stages are plain links to their real routes.
  "Execute (external broker)" is deliberately rendered as a
  non-clickable, informational stage with a "prohibited" icon — this
  platform genuinely has no order-execution feature to link to (every
  Trade Planner/Strategy Builder/Journal surface is explicitly a
  planning/reflection tool, never order placement), so rendering it as a
  disabled link is an honest statement of what exists, not a broken
  feature.
- Wired onto 8 pages, each passing its own `current` stage:
  `StockResearch.tsx`/`TradingResearch.tsx` (`research`), `Assistant.tsx`
  (dynamically, one of `notebook`/`strategy`/`trade-plan` depending on
  which of its 4 toggled views is open), `TradingJournal.tsx`
  (`trade-journal`), `PerformanceAttributionEngine.tsx` (`performance`),
  `PortfolioDashboard.tsx` (`portfolio`), `learn/LearningCentre.tsx`
  (`learning`).

## Future extensibility

- `MODULE_LEARN_REGISTRY` is a plain, exported `Record`, so adding a new
  module's "Learn" entry point in a future sprint is a one-line addition
  — no drawer/trigger/hook code needs to change.
- `PlatformJourneyNav`'s `STAGES` array is similarly a single source of
  truth; a future sprint that gives Notebook/Strategy/Trade Plan their
  own dedicated routes only needs to update each stage's `href`, not the
  component's rendering logic.
- `CoachLevel`'s 4-value vocabulary is now the same vocabulary
  `learningPaths.ts` already used, so any future engine-specific coach
  (a hypothetical Portfolio Coach, for instance) can adopt the identical
  4-tier depth selector with zero new type definitions.
- As more `learningPaths.ts` content is authored in future, dedicated
  sprints (never this one, per its own explicit scope), the two
  disclosed "closest existing lesson" mappings above (AI Notebook/
  Strategy/Trade Plan) are the natural first candidates for their own
  exact-match topics.

## Final report

**Modules reused:** Learning Centre (`learningPaths.ts`, `glossary.ts`,
`learningProgress.ts`, `LessonRenderer.tsx`, `nextStepKeys` recommendation
logic), the entire existing AI Coach framework (`lib/ai-core`,
`coachLLM.ts`, `AskCoachLauncher`), the generated learning-progress hooks.

**Modules integrated:** Investing Research, Trading Research, AI
Notebook, AI Strategy, AI Trade Plan, Trading Journal, Performance
Review, Portfolio Impact — each now exposes contextual "Learn" access and
its place in the 9-stage platform journey without navigating away.

**Duplicate components removed:** 2 (`ScoreRing`/`HealthGauge` merged
into one parameterized `ScoreRing`; 3 independently-duplicated equity
curve chart blocks merged into one `EquityCurveChart`).

**Teaching framework created:** `ModuleLearnDrawer`/`ModuleLearnTrigger` —
a page-embeddable teaching surface over the existing Learning Centre
content/progress pipeline; zero new lesson content, zero new coaching
backend.

**Shared components extracted:** `EquityCurveChart`, `ScoreRing`,
`ModuleLearnDrawer`, `ModuleLearnTrigger`, `PlatformJourneyNav` (5 total).

**Navigation improvements:** a single 9-stage `PlatformJourneyNav`
stepper wired onto 8 major pages, giving a consistent, always-visible
answer to "where am I in the workflow, and what's next."

**Technical debt reduced:** removed 2 duplicated local component
definitions (`Dashboard.tsx`'s `ScoreRing`, `PortfolioDashboard.tsx`'s
`HealthGauge`) and 3 duplicated inline recharts blocks; corrected a
mis-stated finding from the pre-sprint Architecture Review ("no
next-lesson logic exists") that would otherwise have led to a future
sprint rebuilding logic that already exists and works.

**Regression summary:** zero regressions. Backend: 3135/3135 real test
assertions pass (1 transient timeout flake, confirmed unrelated and
confirmed passing in isolation). Frontend: 180/180 on every existing page
suite touched by this sprint's edits, plus 14/14 new component tests.
Typecheck and production build both clean.
