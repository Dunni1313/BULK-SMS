# v1.5.0, Sprint 16 — Institutional Workflow Automation Engine

## Non-negotiable, stated up front

**This is not an automation platform. This is not auto-trading.** This
sprint connects every existing module — built across Sprints 8-15 plus the
platform's already-existing Alerts & Notifications infrastructure (Phase 4,
Sprint 56) and Monitoring Engine (Phase 16) — into one unified workflow
queue. Every recommendation is a link plus a plain-English explanation.
**Nothing here places a trade, executes a broker action, or performs a
hidden automation.** Every task requires the user to click through to the
real, already-built module page to act.

## What this is

```
Research → Notebook → Strategy → Trade Plan → Decision Workflow
  → Execution Package → Trade Closed → Journal → Performance
  → Portfolio & Risk Intelligence → Continuous Learning
```

Concretely, this sprint ships:

1. **`lib/workflowAutomation.ts`** — the reusable Task Engine. Given
   already-fetched data from every connected module, it derives up to 8
   named workflow automations, each producing zero or more `WorkflowTask`
   records with a **Pending / In Progress / Waiting / Completed /
   Dismissed** status, and every task carries the 4 transparency fields
   the approved scope requires: `trigger`, `originatingModule`, `reason`,
   `suggestedOutcome`.
2. **`lib/useWorkflowAutomation.ts`** — hook orchestration, mirroring
   `useTradeLifecycle.ts`'s/`usePortfolioRiskIntelligence.ts`'s own
   established pattern exactly.
3. **`lib/workflow-dismissals.ts`** — client-side dismissal persistence
   (localStorage), mirroring `lib/sidebar-preferences.ts`'s own
   established pattern. A dismissal is scoped to the exact task id (e.g.
   `trade-closed-to-journal:42`), never the whole automation type — see
   "Workflow Rules" below.
4. **`pages/WorkflowAutomationEngine.tsx`** (`/workflow-automation-engine`)
   — the full Task list, an AI Workflow Coach panel, an "Automatic
   Connections" card documenting the 2 automations that need no task at
   all, and per-task dismiss/action buttons.
5. **Command Centre integration** — a new "My Workflow" card surfacing
   Recommended Next Tasks, Blocked Workflows, Items Awaiting Review,
   Upcoming Portfolio Review, Learning Recommendation, and Recently
   Completed Actions, reusing the exact same `useWorkflowAutomation()`
   hook the full page uses — never a second, duplicate computation.
6. **`lib/workflowReminders.ts`** (backend) — the one genuinely new
   server-side detection this sprint adds, wired into the platform's
   already-existing Alerts & Notifications pipeline (see "Notifications"
   below).

## Task Engine

### The 8 automations

| # | Automation | Trigger source | Status derivation |
|---|---|---|---|
| 1 | Research → Notebook | Zero notebooks exist anywhere | Always `pending` — see "Honest simplifications" below |
| 2 | Notebook → Strategy | ≥1 notebook, 0 non-archived strategies, per coachId | `pending` |
| 3 | Strategy → Trade Plan | An `active` (approved) Strategy with no Trade Plan referencing its `strategyId` | `pending`, or `completed` if a real link was created in the last 7 days |
| 4 | Trade Plan → Decision | `TradeLifecycleRecord.currentStage` | `ideas`→pending, `research`/`planning`→in-progress, `decision-ready`→waiting |
| 5 | Decision → Execution Package | `currentStage === "ready-to-execute"` | `pending`, or `completed` if executed in the last 7 days |
| 6 | Trade Closed → Journal | `currentStage` | `closed`→pending, `journal-pending`→in-progress, `reviewed` (recent)→completed |
| 7 | Portfolio Risk Changed → Review | Sprint 15's own `PortfolioHealthScore`/`RiskIntelligenceReport` | `pending` only when genuinely elevated AND `confidenceLevel !== "Low"` (see below) |
| 8 | Learning Weakness → Practice | Sprint 15's own `weakestAvailableFactor()` | `pending` when the weakest factor scores below 45 and has a real lesson mapped |

### Automatic connections — deliberately not tasks

Two of the sprint's own named automation arrows are honestly documented,
not modeled as dismissible tasks:

- **Journal completed → Update Performance.** Trade Performance/Performance
  Analytics are computed live from real trades on every page load — there
  is no manual "update" step anywhere in this codebase to automate.
- **Performance updated → Refresh Portfolio Intelligence.** Sprint 15's
  Health Score/Risk Intelligence are likewise computed live on every page
  load — no manual "refresh" step exists.

Inventing a task for a step that doesn't exist would itself be a
fabrication — `AUTOMATIC_CONNECTIONS` in `lib/workflowAutomation.ts`
documents both transparently instead, and the page/Command Centre card
both render them in a dedicated, clearly-labeled section.

### A real bug caught and fixed during implementation

The first draft of automation #7 (Portfolio Risk → Review) fired for a
**brand-new user with zero data anywhere** — `computePortfolioHealthScore()`
(Sprint 15) honestly returns `overall: 0, label: "Poor"` when nothing is
available, by design (never fabricating a fake "good" score for missing
data) — but that same honest zero was being misread by this sprint's own
automation as "genuinely elevated risk," recommending a portfolio review
with nothing real to review. Fixed by requiring
`portfolioHealth.confidenceLevel !== "Low"` before this automation can
fire — an empty portfolio has 0 of 12 available factors and therefore
`confidenceLevel: "Low"` by construction, correctly excluding it. Caught
by this sprint's own Command Centre test suite before commit, not shipped.

### Honest simplifications, disclosed

- **"Research completed" has no discrete event anywhere in this codebase**
  — browsing a Value Research/Trading Research/Options page is never
  logged. Automation #1 is a standing starter recommendation (shown only
  while the user has zero notebooks across every engine), not a literal
  event-triggered task.
- **A dismissal never silently suppresses a future, different
  recommendation.** Every task id is scoped to the exact entity (e.g.
  `trade-closed-to-journal:42`, not `trade-closed-to-journal`) —
  dismissing today's reminder for Trade Plan 42 has zero effect on Trade
  Plan 43's own, later, genuinely new reminder.
- **"Recently Completed" is bounded to 7 days**, reusing each entity's own
  real `updatedAt` timestamp — never an unbounded permanent history this
  module was never built to persist.

## AI Workflow Coach

`buildWorkflowCoachNarrative()` mirrors `buildDecisionCoachNarrative()`'s
(Sprint 13) and `buildPortfolioCoachNarrative()`'s (Sprint 15) own
established pattern exactly: a deterministic template built from an
already-computed task's own fields — `summary`, `whyItMatters` (the
task's own `reason`), `ifIgnored`, `institutionalBestPractice`,
`recommendedNextAction` (the task's own `suggestedOutcome`). This is
static, disclosed reference content, never AI-generated, and never claims
to be. The page's real free-form AI interaction is `AskCoachLauncher`, the
platform's one real AI Coach — no second, duplicate AI system was built.

## Command Centre integration

The new "My Workflow" card reuses `useWorkflowAutomation()` directly —
the exact hook backing the full page — surfacing every field the approved
scope named: Recommended Next Tasks (top 3 pending), Blocked Workflows
(all waiting), Items Awaiting Review (top 3 in-progress), Upcoming
Portfolio Review, Learning Recommendation, and Recently Completed Actions
(top 3). No pre-existing Command Centre card or Workflow Panel stage
changed in content — this is purely an additive card.

## Notifications

`lib/workflowReminders.ts`'s `evaluateJournalReminders(userId)` is the
**only** genuinely new server-side detection this sprint adds. It is
wired into `lib/notifications.ts`'s own already-existing
`evaluateAndPersistAlertsForUser()` Promise.all (one more entry alongside
`evaluateWatchlistAlerts`/`evaluateRiskAlerts`/the Phase 16 Monitoring
Engine's own two evaluators), reusing:

- The exact same `persistAlertCandidates()` dedup-by-`dedupKey` bookkeeping
  every other alert type already uses.
- The exact same 5-minute `startAlertsScheduler()` tick (Phase 4, Sprint
  56) — zero new scheduler infrastructure.
- The exact same `platform_notifications` table and `NotificationBell`
  delivery surface.

**Why only journal reminders became a real, async push notification, and
not the other 7 automations:** Notebook/Strategy/Trade Plan/Decision/
Execution have no backend "event" concept at all (they only ever exist as
client-fetched data), and Portfolio Risk/Learning Weakness are already
adequately covered as in-app Task Engine recommendations, visible the
moment the user opens the app. A closed trade with no journal entry is
different: it is real server-side state (`trades`/`journal_entries`), and
the entire value of the reminder comes from surfacing it even when the
user isn't actively on the page — the same reasoning Sprint 56 itself
already used for watchlist/risk alerts. Pushing a notification for every
one of the other 7 automations would clearly violate the approved scope's
own "No marketing notifications. No spam." instruction.

`evaluateJournalReminders()` reuses the exact "last 20 closed trades
checked against which journal entries reference them" computation already
established in 3 different frontend files
(`useWorkflowSnapshot.ts`/`useTradeLifecycle.ts`/
`InstitutionalCommandCentre.tsx`) — a straightforward server-side port,
never a new formula. One new `AlertType` value, `journal_entry_pending`,
was added to `lib/alertTypes.ts`.

## Workflow rules — transparency, enforced structurally

- Every `WorkflowTask` carries all 4 required fields
  (`trigger`/`originatingModule`/`reason`/`suggestedOutcome`) — a task is
  never rendered without all four (proven by a dedicated regression test).
- No task ever executes anything on click — every `actionHref` is a plain
  navigation to an already-existing page; the user always takes the real
  action themselves on that page.
- Dismissal is always a conscious, per-item action, scoped to the exact
  entity id — never a blanket mute of an entire automation type.
- The AI Workflow Coach's own "what happens if ignored" text is honest:
  for a `waiting` task, it explicitly says the item stays blocked until
  its named precondition resolves — it never claims something will
  silently auto-resolve.

## Learning integration

Every task whose underlying signal already carries a real, pre-verified
lesson recommendation (from Decision Workflow, Execution Lifecycle, or
Portfolio Risk Intelligence) surfaces a "Learn" button directly on its own
task card via the existing `ModuleLearnTrigger`/`ModuleLearnDrawer`
(Sprint 11) — never a new lesson-recommendation table.

## Future extensibility

None of this sprint's design blocks a future, explicitly-approved
enhancement — but none is implemented, hinted at, or half-built here
either:

- A real "in-progress" signal for automations #2/#3 (partial notebook/
  strategy content) could be added the moment a genuine partial-progress
  field exists for those entities — today they are binary (exists or
  doesn't).
- A server-side "research completed" event would need a genuine new
  research-session-tracking capability this codebase doesn't have —
  automation #1 stays an honest standing tip until that exists.
- Additional automations reusing the same `WorkflowTask` shape can be
  added to `computeWorkflowTasks()` without touching any existing
  automation's own logic — each is an independent, composable function.

None of the above is scheduled or promised for a specific future sprint —
they are simply the seams this design already leaves open.
