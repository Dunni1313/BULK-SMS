# v1.5.0 Sprint 8 — AI Research Notebooks

Branch: `v1.5.0-sprint-08-ai-research-notebooks` (stacked on `v1.5.0-sprint-07-ai-workspaces`)

## What this sprint adds

**AI Research Notebooks** — a structured knowledge space inside a Workspace
where users can collect, organise, and refine AI-generated research over
time. Built on top of Sprint 6's conversation memory and Sprint 7's AI
Workspaces, for the same three conversational AI Coaches (Trading,
Investing, Options). Portfolio has no conversational coach (an exhaustive
Sprint 3 finding) and has nothing registered here.

A notebook groups: rich-text notes (honestly plain text — see below), AI
summaries, key findings, action items, references, saved AI responses, and
links to already-existing conversations/uploaded file references. It never
duplicates conversation or file storage — it only links to it.

This is a user-facing productivity feature built entirely on top of Sprints
6/7 — it does not touch trading logic, investing logic, options
calculations, the execution engine, the risk engine, prompts, tool
permissions, authentication, broker integrations, or Portfolio Coach.

## Architecture

### Backend

- **Reuse, not duplication.** Per the approved scope ("reuse Workspace
  storage where possible, do not duplicate conversation storage"), a
  notebook never re-stores a conversation or an uploaded file — it only
  references an already-existing `ai_coach_conversations`/
  `ai_workspace_files` row via a link table.
- **Three brand-new tables** (migration `041_ai_notebooks.sql`) — the
  minimum required for Notebooks / Notebook notes / Notebook links, per the
  approved scope's own explicit instruction:
  - `ai_notebooks` — one row per notebook: `user_id` (FK, `ON DELETE
    RESTRICT`, universal convention), `workspace_id` (nullable FK, `ON
    DELETE SET NULL`), `coach_id`, `title`, `description`, `pinned`
    (favourite), `archived`, `tags` (array), `version` (basic version
    history — see below), timestamps.
  - `ai_notebook_notes` — one table discriminated by `kind` (`note` |
    `summary` | `finding` | `action_item` | `reference` |
    `saved_response`) rather than six separate tables, matching this
    codebase's own established free-text-discriminator convention (e.g.
    `ai_workspace_notes.kind`, `investing_filing_analysis.filing_type`).
  - `ai_notebook_links` — one table for both "linked conversations" and
    "linked uploaded files," discriminated by `link_type` (`conversation` |
    `file`), with two nullable target-id columns and a DB-level `CHECK`
    constraint ensuring exactly one target is populated and matches
    `link_type`. This preserves real referential integrity to both
    `ai_coach_conversations` and `ai_workspace_files` rather than a single
    untyped generic reference.
- **Workspace-association deletion semantics, a deliberate departure from
  Sprint 7's own two precedents:** deleting a notebook's parent workspace
  **detaches, never destroys** the notebook (`workspace_id → NULL`, `ON
  DELETE SET NULL`) — the same "detach, don't destroy" choice Sprint 7 made
  for conversations, not the CASCADE choice it made for files/notes. A
  notebook (title, description, tags, pinned/archived state, its own notes
  and links) is a substantial, curated research artifact, closer in kind to
  a conversation than to a small file-reference row.
- **Notebook-owned children still cascade:** deleting a notebook cascades
  its own `ai_notebook_notes`/`ai_notebook_links` rows (`ON DELETE
  CASCADE`) — they have no meaning independent of the notebook they belong
  to. Deleting a notebook never deletes the conversations/files it merely
  linked to.
- **New route file** `routes/aiNotebooks.ts` — full CRUD for notebooks plus
  their nested notes/links, plus a dedicated content-search endpoint and 4
  AI-action endpoints (see below), mounted alongside (not replacing)
  `routes/aiWorkspaces.ts` and `routes/aiCoachConversations.ts`.
  Deliberately kept outside the OpenAPI/orval typed contract and validated
  via the same small, hand-written plain-validation functions Sprint 6/7
  established (avoiding the zod-dependency-conflict risk those sprints'
  own validation disclosed).
- **`routes/aiCoachConversations.ts` gained one additive, zero-behavior-
  change export:** its private `loadOwnedConversation()` ownership-check
  helper is now exported so `routes/aiNotebooks.ts` can reuse it verbatim
  when validating a conversation-link request, instead of duplicating the
  same check.
- Every list/read/write is scoped by `(user_id, coach_id)` for notebooks,
  and transitively via notebook ownership for notes/links — the same
  isolation discipline Sprint 6/7 established. 404, never a separate 403,
  for both "doesn't exist" and "isn't yours."

### Frontend

- `src/lib/ai-coach/notebooksApi.ts` — plain-fetch client for
  `/ai-notebooks[...]`, mirroring `workspacesApi.ts`'s own established
  pattern.
- `src/lib/ai-coach/useAiNotebooks.ts` — the notebook-memory hook for one
  coachId (optionally scoped to a single workspace), mirroring
  `useAiWorkspaces.ts`'s own shape: list, active-notebook selection + its
  own fetched detail, search, create/update/pin/archive/restore/delete,
  content search, notes/links CRUD, and the 4 explicit AI actions.
- Seven reusable components, per the approved scope:
  - `NotebookSidebar.tsx` — search, an inline "New Notebook" create form,
    and `NotebookList`'s own list rendering.
  - `NotebookList.tsx` — the pure list-rendering component (loading/empty/
    populated), kept separate from the sidebar so a future notebook-
    browsing surface (e.g. a cross-workspace grid) can reuse it without the
    sidebar's own search/create-form state.
  - `NotebookCard.tsx` — a single notebook's summary card (title,
    description, tags, pin/archive state, note count, version).
  - `NotebookHeader.tsx` — shown once a notebook is selected: inline
    title/description editing (bumps `version`), pin/archive/delete, and
    the dedicated content-search box.
  - `NotebookEditor.tsx` — the notebook's own content: notes (add/list/
    delete, kind-tagged) and linked conversations/files (list/unlink, plus
    a "link an existing one" picker driven by whatever the caller's own
    page already has on hand — never fetched independently).
  - `NotebookSummaryPanel.tsx` — the 4 AI actions (see below) plus their
    rendered results, each with an optional "Save to notebook" action that
    writes the result back as an ordinary note via a separate, explicit
    call.
  - `NotebookEmptyState.tsx` — a thin, notebook-flavoured wrapper reusing
    Sprint 7's own `WorkspaceEmptyState` directly, per the approved scope's
    "reuse existing Workspace... components where appropriate" instruction
    — no new empty-state logic was written.
- **Integration into all 3 coach pages** (`Assistant.tsx`,
  `TradingResearch.tsx`, `StockResearch.tsx`), each following the pattern
  already established for that page's own Workspace/Conversation area:
  - `Assistant.tsx` (Options): a "Conversations" / "Notebooks" toggle swaps
    the entire left-column-plus-main-panel between the existing chat UI and
    the new notebook browser — the two views' own state is independent;
    switching never tears down or resets the other.
  - `TradingResearch.tsx` / `StockResearch.tsx` (Trading / Investing): a
    collapsible "Show/Hide research notebooks" toggle reveals the notebook
    browser as a peer section alongside the existing conversation view,
    matching each page's own established collapsible-panel convention
    (`TradingResearch.tsx`'s "legacy inline assistant," `StockResearch.tsx`'s
    "Ask the AI Investment Analyst" panel).

## Data model

```
ai_notebooks
  id, user_id (FK→users, RESTRICT), workspace_id (FK→ai_workspaces, SET NULL, nullable),
  coach_id, title, description (nullable), pinned, archived,
  tags (text[]), version (int, default 1), created_at, updated_at

ai_notebook_notes
  id, notebook_id (FK→ai_notebooks, CASCADE),
  kind ("note"|"summary"|"finding"|"action_item"|"reference"|"saved_response"),
  content, created_at

ai_notebook_links
  id, notebook_id (FK→ai_notebooks, CASCADE),
  link_type ("conversation"|"file"),
  conversation_id (FK→ai_coach_conversations, CASCADE, nullable),
  file_id (FK→ai_workspace_files, CASCADE, nullable),
  created_at
  CHECK: exactly one of conversation_id/file_id is set, matching link_type
```

## Notebook lifecycle

1. **Create** — a notebook is created scoped to a coach, optionally
   associated with a workspace of the same coach (validated: a Trading
   notebook can never be filed under an Investing workspace).
2. **Collect** — the user saves research into it over time: writes plain-
   text notes under any of the 6 kinds, links existing conversations
   (validated: same coach, owned by the user), links existing uploaded-file
   references from an associated workspace (validated: same coach via the
   file's own parent workspace), or saves an AI-generated result as a note.
3. **Search** — either the sidebar's own title-only `?search=` filter, or
   the dedicated `GET /ai-notebooks/:id/search?q=` endpoint, which searches
   the notebook's own **note content**, not just its title.
4. **Organise** — favourite (pin) it, archive it (hidden from the default
   list, still retrievable with `includeArchived=true`), or restore it
   (un-archive, via the same `PATCH ... {archived: false}`).
5. **Version history (basic)** — a monotonic `version` integer, bumped only
   when the notebook's own `title`/`description` change via `PATCH`.
   Deliberately **not** a full diffable snapshot-history table — a
   disclosed, minimum-viable mechanism, not a fabricated full history.
6. **Continue later** — every notebook, its notes, and its links persist
   indefinitely; deleting its parent workspace detaches (never destroys)
   it, so research already collected is never lost by a workspace cleanup.
7. **Delete** — deleting a notebook cascades its own notes/links; the
   conversations/files it merely linked to are completely unaffected.

## AI integration

Four explicit, user-triggered POST endpoints, each reading the notebook's
own already-saved content and reusing `coachLLM.ts`'s existing narration
machinery — **none of these run proactively, on a schedule, or auto-save
their own output.** Saving an AI response into the notebook is always a
separate, explicit `POST .../notes {kind: "saved_response", ...}` call the
caller makes afterward (surfaced in the UI as each result's own "Save to
notebook" button).

- **`POST /ai-notebooks/:id/ai/summarize`** — summarises the whole
  notebook via `narrateNotebookSummary()` (new, reuses the shared private
  `narrate()` helper that guarantees `COACH_DISCLAIMER`). Honest fallback
  text when the LLM is unavailable or the notebook has no notes yet — never
  a fabricated summary.
- **`POST /ai-notebooks/:id/ai/merge`** — merges the notebook's own plain
  notes/saved-AI-responses into a single executive summary via
  `narrateNotebookMergedSummary()`. Honest "no notes to merge" message when
  there is nothing to merge.
- **`POST /ai-notebooks/:id/ai/takeaways`** — extracts key takeaways via a
  new `generateNotebookKeyTakeaways()`, reusing the established
  `aiCoreComplete` + JSON-extraction pattern (`narrateJournalReview()`'s own
  precedent). Returns `{available: false, takeaways: []}` — never a
  fabricated list — whenever the LLM is unavailable or the response can't
  be parsed.
- **`POST /ai-notebooks/:id/ai/action-items`** — the same pattern via a new
  `generateNotebookActionItems()`, extracting concrete action items.

"Save an AI response into a notebook" needed no new endpoint — it's already
covered by the generic notes endpoint (`kind: "saved_response"`).

## Privacy

- Every notebook, note, and link is scoped to `(user_id, coach_id)` and
  enforced at the query level — a different user, or the same user's
  notebook under a different coach, never appears in any list or detail
  response. 404, never a separate 403, for both "doesn't exist" and "isn't
  yours" (matching Sprint 6/7's own established discipline).
- Linking a conversation or file requires the caller to already own it
  (via `loadOwnedConversation()`/the file's own parent workspace's
  ownership) — a notebook can never link to another user's data.
- The 4 AI endpoints only ever send the requesting user's own notebook
  content to the LLM — no cross-user or cross-notebook data ever enters a
  single AI call.

## Search

Two distinct, deliberately separate search surfaces:

- **List search** (`GET /ai-notebooks?search=`) — title-only, case-
  insensitive substring match across the user's own notebooks for a given
  coach, mirroring Sprint 7's workspace-list search exactly.
- **Content search** (`GET /ai-notebooks/:id/search?q=`) — searches a
  single notebook's own saved **note content** (case-insensitive substring
  across every note, regardless of kind), the "Search notebook contents"
  feature. Surfaced in the UI via `NotebookHeader`'s own dedicated search
  box.

## A disclosed, honest technology limitation: "rich-text notes"

This codebase has no rich-text/WYSIWYG editor library anywhere (confirmed
via `grep` across `ravish-trading`'s own `package.json` before building
this feature — zero matches for `editor|tiptap|quill|slate|draft-js|
lexical`). "Rich-text notes" is therefore delivered honestly as plain-text,
kind-tagged notes rather than a fabricated rich-text editing experience.
Introducing a full rich-text editor was judged out of this sprint's scope
(a genuinely new, large frontend dependency) and is listed below as a
disclosed future-roadmap item.

## Future roadmap

- A real rich-text/WYSIWYG note editor, once a specific library is chosen
  and approved (out of this sprint's scope, disclosed above).
- Full diffable version history (snapshot-per-edit), upgrading today's
  basic monotonic version counter.
- Bulk "save all conversation messages into a notebook" action.
- Notebook templates (e.g. a pre-structured earnings-review notebook).
- Cross-notebook search (today's search is always scoped to one notebook's
  own content, or one coach's own notebook titles).
