# Version 1.6 — Beta Operations Guide

**Type:** Documentation and product-planning exercise. No application code
was written or modified to produce this document. Written directly on the
already-checked-out `v1.6.0-ux-polish-phase-1` branch.

**Purpose:** how the beta program itself is run, day to day — who's in it,
what they do each week, and how their feedback gets from a tester's
keyboard into a prioritized list a human can act on. Distinct from
`docs/v1.6.0-Beta-Deployment-Plan.md` (the technical environment this
program runs inside) and `docs/v1.6.0-Beta-Success-Metrics.md`/
`docs/v1.6.0-Beta-Issue-Triage.md` (how the feedback this guide collects
gets measured and severity-ranked, respectively).

**Guiding principle, stated once here because it shapes every decision
below:** this program exists to learn whether the platform is genuinely
usable, not to accumulate the largest possible volume of feedback. A
handful of testers who complete real, unprompted sessions and articulate
*why* something confused them are worth more than a large cohort clicking
through a checklist.

---

## Part A — Beta User Program

### A.1 Number of beta users

**Recommended: 5–8 testers.** Reasoning:

- This platform genuinely rewards patience and domain familiarity — the
  original Product Experience Review already established this explicitly
  (`docs/v1.6.0-Product-Experience-Review.md`'s own "Running the sessions"
  guidance). A larger, more casual cohort would produce noise, not signal,
  and would dilute the amount of attention any one tester's session
  actually gets reviewed with.
- At 5–8 testers, every single session can realistically be watched (or
  its recording reviewed) by a human, and every piece of feedback can
  realistically be read individually rather than only aggregated — the
  entire point of §A.4/Part B below is that this stays small enough for
  that to be true.
- 5–8 is enough to see a genuine pattern emerge (the same confusion point
  independently hit by 3+ testers is a much stronger signal than any one
  tester's opinion) without needing statistical-significance-scale
  numbers, which this kind of qualitative usability program was never
  going to reach anyway.
- If, mid-beta, a specific journey or page needs deeper coverage than the
  initial cohort provides, add 1–2 more testers targeted at exactly that
  gap rather than doubling the whole program.

### A.2 User profiles

Recruit testers who match the platform's real intended audience — **people
who already trade or invest in some real capacity**, not general
consumers or engineers evaluating the codebase. A useful spread across the
cohort:

| Profile | Why include them | Target count |
|---|---|---|
| **Active options trader** (income-focused, familiar with spreads/Greeks) | The Options Income Engine's own natural audience; can judge whether Scanner/Strategy/Execution genuinely speeds up or clarifies their existing process. | 2 |
| **Fundamental / long-term investor** (unfamiliar with options) | Tests Engine 1 (Investing) in isolation — does Value Research/Decision/Portfolio Construction stand on its own for someone who never touches Engine 3? | 1–2 |
| **Active swing/day trader** (technical, unfamiliar with fundamentals) | Tests Engine 2 (Trading) in isolation — Trading Research, Market Structure, the AI Trading Coach's own daily workflow. | 1–2 |
| **Someone who trades/invests casually, not full-time** | The platform's own stated ambition is "institutional-grade" — this profile tests whether that depth is still approachable to someone without a professional's daily habit around it, without diluting the cohort's baseline domain literacy. | 1 |
| **A colleague of the project owner with genuine trading/investing credibility, seeing the product for the very first time** | Directly answers Beta Feedback Question #17 ("if you showed this to a colleague...") from the inside — this person effectively *is* that colleague. | 1 |

Every profile above should be a genuine first-time user of this specific
platform — do not recruit anyone who has already seen a screenshot,
walkthrough, or description of it, for the same reason the original
Product Experience Review insisted on a first-time-user lens: familiarity
is exactly what this beta cannot measure around.

### A.3 Onboarding sequence

A single, consistent sequence for every tester, run the same way each
time so results stay comparable across testers:

1. **Invitation (T-3 to T-1 days before their first session).** A short,
   plain message explaining what this is (a usability beta for a paper-
   trading/simulated platform, not a request to risk real money — that
   distinction should be stated explicitly and early, since
   `docs/v1.6.0-Beta-Release-Notes.md`'s own "note on what this platform
   is and isn't" makes clear how central it is), roughly how much time
   to expect (see §A.5), and nothing about how to use the product itself
   — no walkthrough, no screenshots, no feature list. The whole value of
   Journey 1 (First Login, `docs/v1.6.0-Beta-Testing-Guide.md`) depends on
   the tester arriving genuinely cold.
2. **Account creation, unassisted.** The tester signs up on their own,
   with no one watching yet — this is itself part of what's being tested
   (does the sign-up flow, and the sidebar/notification-bell visible even
   pre-authentication, confuse a genuine first-time visitor — a
   specifically-flagged open question in
   `docs/v1.6.0-Beta-Testing-Guide.md` Journey 1).
3. **Session 1 — facilitated, watched, not narrated (see §A.4).** The
   first real, observed session. Run Journeys 1–4 from
   `docs/v1.6.0-Beta-Testing-Guide.md` (First Login through First Trade
   Plan) as the free-form walkthrough, per that document's own "how to
   use this guide" instructions.
4. **Immediately after Session 1:** hand over the Beta Checklist
   (`docs/v1.6.0-Beta-Testing-Guide.md`'s own self-report checklist) —
   filled in from memory, not by re-reading anything.
5. **Session 2, later the same week — facilitated, watched.** Journeys
   5–8 (First Decision Review through First Portfolio Review).
6. **Immediately after Session 2:** hand over the Beta Feedback Questions
   (`docs/v1.6.0-Beta-Feedback-Questions.md`) — the 20 reflective
   questions, deliberately positioned last per that document's own
   sequencing rationale.
7. **Weeks 2+ (see §A.4):** unmoderated, self-directed use — no facilitator
   present, feedback captured via the lightweight process in Part B below
   as it happens, not saved up for a scheduled session.

### A.4 Weekly schedule

A repeatable weekly template, usable for as many weeks as the beta
actually runs (see the Final Report's own duration recommendation — this
guide does not fix a number of weeks itself, since that is a judgment call
for the project owner, not an operational detail):

| Day | Activity |
|---|---|
| **Monday** | New-cohort-member onboarding sessions (if staggering start dates) or, for an already-onboarded cohort, a lightweight "anything from the weekend?" async check-in. |
| **Tuesday–Thursday** | Unmoderated, self-directed real usage — testers use the platform as they naturally would, at whatever cadence suits them, submitting feedback as it happens (Part B). No facilitator watching. |
| **Friday** | Weekly synthesis (Part B, §B.4) — the operator reviews the week's accumulated feedback, checks it against `docs/v1.6.0-Known-Limitations.md` and this week's own emerging patterns, and prepares a short summary for the project owner. |
| **As-needed, any day** | A short, optional 10–15 minute "what tripped you up this week" call with any tester who flagged something the async feedback alone doesn't fully explain — never mandatory, only when async text isn't enough to understand a report. |

The first week of any tester's participation follows §A.3's own onboarding
sequence instead of this general template — the two facilitated sessions
in §A.3 happen once per tester, at the start of their own participation,
not every week.

### A.5 Testing sessions

- **Facilitated sessions (Session 1 and 2, §A.3):** 45–60 minutes each.
  The facilitator watches and takes notes on hesitation, wrong turns, and
  moments of visible confusion — the actual signal, per
  `docs/v1.6.0-Beta-Testing-Guide.md`'s own framing ("a tester who gets
  there after 90 seconds of confusion 'succeeded' by the checklist but
  still surfaced a real UX problem"). The facilitator does not explain
  anything before the tester tries it themselves.
- **Unmoderated usage (weeks 2+):** no fixed session length — testers use
  the platform whenever and for however long suits their own real
  workflow, which is itself more representative of eventual real-world use
  than a scheduled lab session would be.
- **Total expected time commitment per tester across the whole beta:**
  roughly 2–3 hours of facilitated time (§A.3) plus whatever unmoderated
  time each tester chooses to spend — communicate this honestly up front
  so no tester feels an obligation beyond what they've actually agreed to.

### A.6 Feedback cadence

See Part B below for the full process — in summary, feedback flows
continuously (as it happens, never batched by the tester until a
scheduled moment), reviewed daily by the operator, and synthesized weekly
for the project owner. This asymmetry (continuous in, weekly out) is
deliberate: it keeps the friction of *reporting* something as low as
possible for the tester, while keeping the operator's own review rhythm
sustainable and not reactive to every single item in isolation.

## Part B — Daily Feedback Process

### B.1 Categories

Every piece of feedback, from any source (a facilitated session note, an
async message, a Beta Checklist answer, a Feedback Questions response),
gets sorted into exactly one of six categories before anything else
happens to it:

| Category | What belongs here |
|---|---|
| **Navigation** | Couldn't find something; found it via the wrong path; a sidebar/search/link didn't lead where expected. |
| **Workflow** | The sequence of steps across pages didn't feel connected; a handoff between pages (e.g. Decision → Execution) broke the tester's mental model of "what's next." |
| **Clarity** | A page, badge, label, or number was on screen and functioning correctly, but the tester didn't understand what it meant or why it mattered. |
| **Bugs** | Something didn't work as designed — an error, a crash, incorrect data, a broken interaction. Route immediately to `docs/v1.6.0-Beta-Issue-Triage.md`'s severity process (§B.3 below). |
| **Performance** | Something felt slow, laggy, or unresponsive — distinct from a bug (it worked, just not promptly). |
| **Feature requests** | "I wish it also did X." Per `docs/v1.6.0-Beta-Feedback-Questions.md`'s own explicit design, the structured feedback documents deliberately do not solicit these — but testers will volunteer them anyway, and they should be captured, not discarded, just routed differently (§B.4). |

A single piece of raw feedback sometimes spans more than one category
(e.g. "I couldn't find the button, and once I did, I didn't understand
what the badge next to it meant" is both Navigation and Clarity) — tag it
with all categories that genuinely apply rather than forcing a single,
poorer-fit label.

### B.2 Collection

- **During facilitated sessions:** the facilitator's own real-time notes,
  written against the specific journey step being observed (matching
  `docs/v1.6.0-Beta-Testing-Guide.md`'s own per-journey structure), so a
  note can always be traced back to exactly where in the product it
  happened.
- **During unmoderated use:** the lowest-friction channel the cohort will
  actually use — a shared form, a dedicated chat channel, or direct
  messages to the operator, whichever this specific beta's real tooling
  makes easiest. The mechanism matters far less than keeping it genuinely
  low-friction; a tester who has to context-switch into a heavyweight
  ticketing tool to report a 30-second annoyance simply won't.
- **Structured documents:** the Beta Checklist and Feedback Questions
  responses are themselves a batch of categorizable feedback, processed
  the same way as any other item once received.
- Every item, regardless of source, is logged with: the tester (or
  "anonymous" if a tester prefers), the page/journey it happened on, the
  raw description in the tester's own words, and the category tag(s) from
  §B.1 — nothing more elaborate than that is needed at this scale.

### B.3 Daily review

Each day the beta is active, the operator:

1. Reads every new item logged since the previous day's review.
2. For anything tagged **Bugs**, immediately applies the severity
   definitions in `docs/v1.6.0-Beta-Issue-Triage.md` and starts that
   document's own response-time clock — bugs do not wait for the weekly
   synthesis (§B.4).
3. For everything else, checks it against `docs/v1.6.0-Known-Limitations.md`
   — if the item restates something already disclosed there as
   intentionally unfinished, deferred, or something-to-ignore, note it as
   a **confirmation** of an already-known item (still valuable — see
   `docs/v1.6.0-Known-Limitations.md`'s own "what feedback is most
   valuable" ranking, where independent re-confirmation of a genuinely
   uncertain fix (like the Trade Plan disambiguation notes) is explicitly
   called out as useful) rather than logging it as a brand-new finding.
4. Flags anything that looks like it might rise to **Critical** or
   **High** severity (see the Issue Triage document) for immediate
   attention, same day, regardless of what else is on the day's list.

This is a 15–30 minute daily task at this cohort size — it is not meant to
become a formal daily standup or meeting; a single person reading through
a day's worth of items from 5–8 testers is a realistically light load.

### B.4 Weekly synthesis and prioritization

At the end of each week:

1. **Group** the week's items by category (§B.1) and look for repetition
   — the same page or moment flagged by more than one tester independently
   is the single strongest signal this process can produce; a
   single-tester report is still logged and still valuable, but weighted
   differently.
2. **Cross-reference against `docs/v1.6.0-Known-Limitations.md`** once
   more, at the aggregate level this time — did this week's feedback
   confirm, contradict, or add nuance to anything already listed there?
3. **Route feature requests separately** — log them, but do not fold them
   into this beta's own prioritization discussion. Per the explicit
   instruction governing this entire beta phase ("we are learning, not
   adding features"), feature requests are preserved for
   `docs/Version-2-Roadmap.md`-style future planning, never actioned
   during the beta itself.
4. **Produce a short weekly summary for the project owner** — patterns
   observed, any Critical/High items already surfaced mid-week (§B.3),
   and a running tally against the success metrics in
   `docs/v1.6.0-Beta-Success-Metrics.md`.
5. **Do not attempt to fix anything not already explicitly approved**
   during the beta window itself, beyond genuine Critical/High-severity
   bugs per `docs/v1.6.0-Beta-Issue-Triage.md`'s own response-time
   commitments — the beta's purpose is to observe and collect, not to
   iterate live against a moving target; mid-beta changes would also
   contaminate week-over-week comparability of the same journeys across
   different testers.

### B.5 How this feeds into what happens after the beta

The weekly summaries (§B.4) accumulate into the input for a genuine
post-beta prioritization pass — the same spirit as the "Top 10
improvements to consider after beta feedback" already identified in this
document's own companion Final Report, but informed by what was *actually*
observed rather than what was predicted beforehand. This guide does not
itself perform that post-beta pass — it only ensures the raw material for
it exists in an organized, categorized, severity-tagged form by the time
the beta ends.
