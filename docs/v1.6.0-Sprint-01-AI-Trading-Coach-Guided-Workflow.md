# v1.6.0 Sprint 1 — AI Trading Coach Guided Workflow

## What this sprint adds

A single AI Trading Coach that continuously tracks where the user is in
today's daily trading workflow and recommends exactly one next action —
never a menu, never competing suggestions. The coach:

- Answers six questions on every render: **Where am I? What completed?
  What's next? Why? How long? What's after?**
- Tracks an 11-step **Daily Workflow Engine** (Morning Brief → Market Scan
  → Opportunity Review → Research → Trade Planning → Decision & Risk
  Review → Execution Preparation → Execution → Position Monitoring →
  Trade Journal → Daily Review).
- Auto-detects step completion from real, already-computed data wherever
  a real signal exists; never fabricates one.
- Treats **"No Trade" as a valid, disciplined outcome** — a closed
  market, no open positions, and nothing in progress makes the new-trade
  pipeline honestly *not applicable* for the day, never *blocked* or
  *incomplete*.
- Reprioritizes an existing open position or a closed trade awaiting a
  journal entry ahead of a fresh new-trade search.
- Opens the correct, already-shipped page for whichever step is next
  (Smart Navigation), preserving a known trade plan id in the URL where
  the destination page already supports it.
- Introduces the platform's first achievement/competency system, scoring
  disciplined process only — never trade count, execution frequency, or
  platform engagement.

## Mandatory reuse audit — the concise reuse map

Performed via 3 parallel read-only research passes across Scanner + AI
Opportunity Scoring, Order Preview + Position Sizing + portfolio-level
risk, and Alpaca broker integration + Trade Monitor + position-management
UI, followed by a targeted 13-topic hook-inventory pass, before any code
was written.

| Category | Finding |
|---|---|
| **Already exists and reused as-is** | `Scanner.tsx`'s `useGetScannerResults()`; `useOpportunityPipeline()`; `useActiveDecisionSummary()`/`useDecisionWorkflow()` (`DecisionStage`, `DecisionScore`, `StageCompletionStatus`); `useTradeLifecyclePipeline()`/`useTradeLifecycle()` (`TradeLifecycleRecord`, `PipelineStageId`, `JournalStatus`); `useListTradingJournalEntries()`; `getMarketClockStatus()` (`lib/marketCalendar.ts`); `ModuleLearnTrigger`/`ModuleLearnDrawer`/`moduleLearnRegistry.ts`; the `?planId=` deep-link convention (`DecisionWorkflow.tsx`, `ExecutionLifecycleManager.tsx`, `InstitutionalPlaybooks.tsx`); `CoachLevel`/`LearningDifficulty` 4-value vocabulary. |
| **Exists but required integration** | `InstitutionalCommandCentre.tsx`'s existing "Portfolio Intelligence, Learning & Coaching" grid and its own, separately-scoped `WorkflowPanel`/"Your Workflow Today" section (Workflow Automation Engine) — the new coach section was added alongside, never inside or in place of, either. |
| **Exists but required a small extension** | None required a code change to an existing module — every readiness signal was read, not modified. |
| **Genuinely missing (built this sprint)** | The 11-step sequence/status vocabulary itself (a deliberate, justified 6th "steps with states" model — see below); per-user experience level + Beginner Mode persistence (confirmed nowhere else in the codebase, only ephemeral per-page `useState`); per-trading-day workflow completion state; the achievement/competency system (confirmed absent platform-wide). |

**Why a 6th status vocabulary is justified, not a duplicate:** the
codebase already has 5 independent "steps with states" models —
`WorkflowTaskStatus` (Workflow Automation Engine), `PlaybookStageStatus`,
`StageCompletionStatus` (Decision Workflow, one trade plan's own decision
quality), `PipelineStageId` (Trade Lifecycle, pre/post-execution), and
`TradePlanStatus`. None represents "today's whole guided trading day" —
each is either narrower (one trade plan, one lifecycle) or broader/less
sequenced (a general task list). `DailyWorkflowStepStatus` fills that
specific, previously-unfilled gap.

## Naming disambiguation — read this before assuming a collision

This codebase already has two prior, differently-scoped "Trading
Coach"-named surfaces, disclosed here explicitly to prevent a third
collision:

1. `/ai-trading-coach` (`AITradingCoach.tsx`) — a **free-form
   conversational** specialist coach (one of the platform's 3
   `CoachId`s), displayed as "AI Trading Assistant" since v1.5.0 Sprint 1
   renamed it to resolve its own prior collision with #2 below.
2. `/trading-ai-coach` (`TradingAICoach.tsx`, Phase 29) — a
   **deterministic, per-symbol explanation** coach (structure/liquidity/
   regime/risk/session tabs).
3. **This sprint's AI Trading Coach** — a **guided daily-workflow
   tracker**. It never answers open-ended questions and never explains a
   specific symbol's technicals; it only tracks and recommends the one
   next step in today's sequence. It has **no dedicated route** — it is a
   single reusable panel (`AiTradingCoachPanel.tsx`) mounted on existing
   pages, never a new page competing for a similar URL or title.

## Architecture

### Persistence — two brand-new tables, everything else read live

`lib/db/manual-migrations/045_ai_trading_coach.sql`:

- **`ai_trading_coach_preferences`** — one row per user, durable across
  sessions. `experienceLevel` (beginner/intermediate/advanced/
  institutional, matching the platform's existing `CoachLevel`/
  `LearningDifficulty` 4-value vocabulary) and `beginnerModeEnabled`.
  This is the sprint's one genuinely new *durable* persistence need — no
  existing table or Settings field holds it.
- **`ai_trading_coach_daily_state`** — one row per `(userId, tradingDate)`,
  upserted on first read for "today" (mirrors `intelligence_snapshots`'
  own `(userId, snapshotDate)` upsert precedent).
  `completedStepIds`/`skippedStepIds` (jsonb string arrays of
  `DailyWorkflowStepId`) and a nullable `noTradeReason`.
  `tradingDate` is computed in `America/New_York` — the platform's one
  existing "trading day" timezone concept, mirroring
  `lib/marketCalendar.ts`'s own private `ET_TIME_ZONE` constant. No new
  per-user timezone field was introduced.

Neither table stores hidden chain-of-thought, internal model reasoning,
secrets, or a second copy of any trading calculation — every other figure
the panel displays (scanner results, decision score, trade lifecycle
stage, market status) is read live from its own existing module and never
persisted a second time here. Neither table is read or written by the
auto-execution/auto-adjustment engines or their kill switch — this is a
purely advisory, informational surface.

### Backend — `routes/aiTradingCoachWorkflow.ts`

Hand-validated, deliberately kept outside the OpenAPI/orval typed
contract — matching every other AI-coach-family route
(`aiCoachConversations.ts`, `aiWorkspaces.ts`, `aiNotebooks.ts`,
`aiStrategies.ts`, `tradePlans.ts`), avoiding the same zod
dependency-conflict risk Sprint 6 already found and disclosed.

- `GET /ai-trading-coach/state` — bundles preferences + today's daily
  state + live market clock status (`getMarketClockStatus()`, called
  directly, never re-implemented).
- `PATCH /ai-trading-coach/preferences` — `experienceLevel`/
  `beginnerModeEnabled`.
- `PATCH /ai-trading-coach/state` — `completedStepIds`/`skippedStepIds`/
  `noTradeReason` for a given (or today's) trading date.

All scoped via the established `getScopedUserId(req)` pattern.

### Frontend

- **`lib/ai-coach/tradingCoachWorkflow.ts`** — the pure-logic Daily
  Workflow Engine core: `computeDailyWorkflow(signals, progress)`. Takes
  narrow, structurally-typed subsets of already-fetched hook data
  (`WorkflowSignals`) and the persisted daily-state slice
  (`WorkflowDailyProgress`); returns the full 11-step result with exactly
  one `active`/`blocked` step, an evidence-cited `primaryReason`,
  applicable-steps-only progress, and `isDoneForToday`. Also holds
  `computeAchievements()`, the first achievement/competency system in
  this codebase.
- **`lib/ai-coach/tradingCoachNavigation.ts`** — Smart Navigation, mapping
  each of the 11 steps to a real, already-shipped page. Zero new routes.
  `?planId=` is only ever appended for the 3 steps whose destination page
  honestly supports it.
- **`lib/ai-coach/aiTradingCoachApi.ts`** — a plain-fetch client for the
  3 new routes, mirroring `tradePlansApi.ts`'s/`strategiesApi.ts`'s own
  established convention.
- **`lib/ai-coach/useTradingCoachWorkflow.ts`** — the single orchestration
  hook every mounted panel uses. Nests `useGetScannerResults()`,
  `useOpportunityPipeline()`, `useActiveDecisionSummary()`,
  `useTradeLifecyclePipeline()`, `useListTradingJournalEntries()`, and
  this sprint's own state — never re-fetching or recomputing any of
  them, mirroring `usePortfolioRiskIntelligence()`'s own established
  nesting pattern.
- **`components/coach/AiTradingCoachPanel.tsx`** — the ONE reusable panel.
  Mounted, unmodified, on 7 major workflow pages (Scanner,
  OpportunityPipeline, TradingResearch, DecisionWorkflow,
  ExecutionLifecycleManager, TradeExecutionCenter, TradingJournal) plus
  `InstitutionalCommandCentre.tsx`. Responsive/collapsible
  (`collapsible` prop, `false` on the Command Centre where it's already
  the page's own primary content).

### Command Centre integration

A new "AI Trading Coach" section was added to `InstitutionalCommandCentre.tsx`
directly after the existing `DailyBriefingCard` and ahead of the
pre-existing "Your Workflow Today" (`WorkflowPanel`, Workflow Automation
Engine) section — explicitly commented in the source to disambiguate the
two, since `WorkflowPanel` tracks longer-horizon platform tasks, not this
daily guided sequence. No second Command Centre was created.

## Handling the named edge cases

| Scenario | Handling |
|---|---|
| Market closed | The whole new-trade pipeline (Market Scan → Execution) becomes `not-applicable` once nothing is already in progress; the Execution step alone is `blocked` (with an honest, real reason) if something *is* in progress when the market closes mid-flow. |
| No acceptable opportunities / user chooses not to trade | `declareNoTrade(reason)` marks the new-trade pipeline `not-applicable` for the day — never blocked, never penalized in the completion %. |
| Existing open positions | `hasOpenPositionNeedingMonitoring()` reprioritizes Position Monitoring ahead of any fresh new-trade step, regardless of what else is or isn't done today. |
| Monitoring-only day | Same mechanism — Position Monitoring/Trade Journal can become the primary step with zero earlier steps completed. |
| Failed risk review | Decision & Risk Review only auto-completes when the real, already-computed `DecisionScore.label === "Well-Prepared"` — never re-derived, never bypassed. |
| External execution | Execution routes to the existing, protected-logic-backed `/trade-execution-center` — the coach opens it, never bypasses or duplicates its own execution/risk-validation logic. |
| Irrelevant steps | Marked `not-applicable`, excluded from `applicableStepIds` and the completion-% denominator. |

## Explicitly out of scope this sprint (per the approved plan)

No second AI Coach framework, Learning Centre, Workflow Automation
Engine, Scanner, Research system, Trade Planner, Decision Engine,
Execution Centre, Portfolio, or Trade Journal was built. No new strategy
engine, pricing/probability calculation, autonomous trading, or forced
execution was introduced. No existing execution protection was bypassed —
the Execution step only ever opens the existing Trade Execution Center;
it never submits, modifies, or cancels an order itself.
