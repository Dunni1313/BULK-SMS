## 1. Executive Summary

### Current platform maturity

This is now a large, mature, three-engine institutional platform:

- **149 backend `lib/` files** (~55,700 lines, excluding tests) and **77 mounted route modules**.
- **79 top-level frontend pages** across **92 routes**, organized into a **10-group, ~84-item** sidebar navigation (v1.1.0).
- **55 database tables** behind **39 hand-reviewed manual migrations** (`001`–`038`).
- A **20,690-line OpenAPI spec** driving generated Zod validators and a generated React Query client — the entire API surface is typed end-to-end.
- **244 backend test files / 2,867 tests** and **112 frontend test files / 1,294 tests**, both passing cleanly as of the v1.4.0 tag, plus a 5-spec Playwright E2E smoke suite.
- A complete, 15-path, 115-topic **Learning Centre** (v1.4.0, just shipped) with real, live progress tracking honestly distinguished from a (non-existent) certification engine.
- **Zero `TODO`/`FIXME`/`XXX` markers** anywhere in application source — a genuinely clean, disciplined codebase by that measure.

The platform has grown through an unbroken chain of small, disclosed, reuse-first sprints (Phases 1–44, then a further 36 undocumented-by-number phases layered on top per §3a–§3d of `CLAUDE.md`, then the Learning Centre). That discipline shows: almost every later "Institutional X Engine" module explicitly declares itself a "pure composition layer, zero new calculations" over an earlier, already-tested engine, and this review found real, confirmed evidence backing that claim in most cases (see §2.4).

### Strengths

1. **Protected-file discipline holds completely.** `execution.ts`, `optionsMath.ts`, `risk.ts`, `autoExecution.ts`, `autoAdjustment.ts` remain the untouched, load-bearing core of the Options Income Engine across every phase reviewed here — no sprint in this platform's history has quietly drifted into modifying them.
2. **A real, working shared-infrastructure layer exists and is used.** `getScopedUserId()` (73 call sites), `recordAuditEvent`, `lib/ai-core`, `getMarketDataProvider()`, and the Phase 4 rate-limiting/monitoring middleware are genuine single-source abstractions, not aspirational ones.
3. **Honest SIMULATED-vs-LIVE and deterministic-vs-LLM labeling is pervasive**, not just in the Learning Centre — it is a load-bearing product principle the whole platform follows (confirmed: `lib/ai-core` has exactly 2 real consumers — `coachLLM.ts` and `investmentCommittee.ts` — and every other "Coach"-named module is honestly deterministic/template-based, matching their own header comments).
4. **Test discipline is strong**: 79/79 top-level frontend pages have a matching test file; the full backend suite is large and, per the most recent v1.4.0 validation runs, reliably clean on a second/serial run.
5. **At least one confirmed, clean example of the platform's own extraction discipline working as intended**: `lib/scenarioEngine.ts` (Phase 39) genuinely imports and wraps `lib/portfolioStressTest.ts` rather than reimplementing it — proof the "reuse, don't duplicate" convention isn't just a header comment.

### Recommended focus for v1.5.0

**This should be a consolidation-and-refinement release, not another net-new-engine release.** The platform has reached the point where most of the *business capability* the user's own candidate list asks for already exists somewhere in the codebase (see §4) — the highest-value work now is closing the gap between "this exists" and "this is easy to find and doesn't confuse the user," plus a small number of genuinely missing capabilities (export, wider AI narration, a live-data path once credentials exist). Building yet another dashboard or coach surface without first addressing the proliferation documented in §2 would make the platform worse, not better.

### 2.3 API structure

The API is fully OpenAPI-driven (`lib/api-spec/openapi.yaml`, 20,690 lines) → generated Zod schemas (`lib/api-zod`) → generated React Query hooks (`lib/api-client-react`). This pipeline is a genuine strength — no hand-maintained client code exists — but its sheer size (77 route modules, and per §5.4's own confirmed history, at least 4 prior sprints hitting the same Orval schema-naming-collision gotcha) means the spec file itself is now a maintenance surface worth watching. Two route registration points exist: `routes/index.ts` (76 routers) plus `health` and `auth` mounted directly in `app.ts` — both confirmed intentional, not an oversight.

### 2.4 Database models

55 tables span every engine. Migration discipline (CLAUDE.md rule 7 — nullable → backfill → enforce, hand-reviewed SQL) has held for all 39 migrations; the two most recent (`037_trading_coach_messages.sql`, `038_learning_centre_bookmarks.sql`) both remain purely additive. No evidence of schema drift or an un-migrated ORM-only table was found.

### 2.5 AI modules — the most important finding of this review

**Only 2 files in the entire codebase actually call a language model**: `coachLLM.ts` (the original Options Engine coach, plus its trade/investing-narration extensions) and `investmentCommittee.ts` (Investing Engine's committee synthesis). Every other "Coach"-branded or "AI"-branded module — `tradingCoach.ts`, `investingCoach.ts`, `institutionalMentor.ts`, and the ~15 `*Coach.ts`/`*Learning.ts` companion pairs across the Phase 13–44 composition tier — is confirmed deterministic and template-based, exactly as their own header comments claim. This is **honest, disclosed architecture**, not a bug — but it means the phrase "AI Coach" is heavily overloaded across this platform between two very different things:
- a small number of genuinely LLM-narrated features (with the enforced `COACH_DISCLAIMER`/`VALUE_DISCLAIMER` safety wrapper), and
- a much larger number of rule-based explanation engines wearing the same "Coach" branding.

This is a real product-clarity question for v1.5.0, not just a technical one (see §4.5).

## 3. Strengths, Technical Debt, and Refactoring Recommendations

### Strengths (recap, see §1 and §2.5)
Protected-file discipline; genuine shared infrastructure; honest deterministic-vs-LLM labeling; strong test coverage; at least one clean extraction-reuse example (`scenarioEngine.ts`).

### Technical debt / duplicate logic (ranked by confirmed evidence)

1. **`performanceAnalytics.ts` (synthetic) vs. `performanceAttribution.ts` (real) — confirmed, concrete duplication.** The synthetic engine predates the real one and remains independently routed. Recommendation: either retire `performanceAnalytics.ts` in favor of the real engine everywhere, or if it's intentionally kept as a demo/onboarding mode for accounts with too few real trades (a plausible legitimate reason — Phase 38's own header cites exactly this as the historical rationale for the real engine's existence), relabel its UI surface explicitly as "Demo Mode" so a user can never mistake synthetic figures for real ones.
2. **Dashboard/landing-page proliferation — confirmed, 8-9 overlapping surfaces.** `Home.tsx`, `CommandCenter.tsx`, `InstitutionalDashboard.tsx`, `ExecutiveDashboard.tsx`, `ExecutiveIntelligence.tsx`, `CrossEngineWorkspace.tsx`, `PortfolioDashboard.tsx`, `PortfolioWorkspace.tsx`, plus the original `Dashboard.tsx` (Options). Several of these pages' own header comments already acknowledge and try to differentiate themselves from the others — direct evidence this is a known, accumulating problem, not a one-off. This is the single highest-value IA cleanup opportunity in the codebase.
3. **Coach surface fragmentation — confirmed, 7 page-level surfaces + 2 drawer components + ~15 backend Coach/Learning file pairs.** Distinct from item 1 (that's data duplication; this is surface-area/branding duplication). The `/trading-ai-coach` vs. `/ai-trading-coach` naming collision (§2.5) is the sharpest example and the easiest to fix cheaply (a rename or a merge, not a rebuild).
4. **`institutionalReporting.ts` at 2,495 lines** — the largest single file in the codebase. Not yet a correctness problem, but a maintainability one; a natural split point exists along its own 12 report types.
5. **`lib/ai-core` is under-leveraged relative to its own stated design goal.** Built in Phase 1 Sprint 9 explicitly "so every future coach (Trading, Investing) can reuse" it, but only 2 of ~20 coach-shaped modules actually do. This is not automatically a defect — deterministic coaches are cheaper, faster, and safer — but it is a genuine strategic fork the roadmap should resolve deliberately (§4.5), not by accretion.
6. **No export/PDF/CSV capability** despite a mature 12-report-type reporting engine (§2.10) — a real gap, not duplication, but flagged here because it's the most "shovel-ready" of the confirmed gaps (the hard composition work is already done; only the export layer is missing).

### Reusable components already available for v1.5.0 work
`components/learn/` (LessonRenderer/KnowledgeCheck/QuizCard), `components/coach/TradingCoachWorkspace` family (the most componentized/decomposed of the coach surfaces — a good template if consolidation proceeds), `lib/trading-format.tsx` / `lib/investing-format.ts`, `lib/ai-core`, `getScopedUserId()`, `recordAuditEvent`, `middlewares/rateLimit.ts`, `systemHealth.ts`.

### Areas that should be refactored *before* new development
Per the strengths/debt findings above, in priority order: (1) the Coach naming collision and Coach/Learning file-pair pattern should be audited for actual code duplication before any new "Institutional X Engine" is added — adding an 19th such module without first understanding whether the ~15 existing Coach/Learning pairs share extractable logic would compound the debt; (2) the dashboard proliferation should be mapped (which page composes which backend routes) before any new cross-engine landing page is proposed, since the user's own candidate list (§4) includes "Executive Command Centre," which likely already substantially exists.

## 6. Release Strategy

### Version sequence
Continue the established `vMAJOR.MINOR.0` sprint-branch convention (`v1.5.0-<short-slug>`), one branch per sprint, matching every prior release in this repository's history. Given v1.5.0's own consolidation focus, expect **more, smaller sprints** than a typical net-new-feature minor version — each Phase 1 item above is independently shippable and should be its own sprint/PR, not bundled.

### Sprint structure
Match the pattern already proven across 60+ sprints in this codebase: (1) mandatory investigation/capability-mapping before implementation, explicitly disclosed in the sprint's own documentation; (2) implementation with zero new calculation/business logic where the work is genuinely composition/consolidation (most of Phase 1); (3) full validation (`typecheck`, backend serial ×2, frontend, build) before every PR; (4) a dedicated `docs/v1.5.0-Sprint-N.md` per sprint, mirroring the Learning Centre's own L1–L2L documentation discipline.

### Testing approach
No change to the existing tooling — Vitest (backend/frontend) + Playwright (E2E, currently 5 specs). For consolidation work specifically (Phase 1 items 1-3), the test bar should be *regression-proof, not just passing*: any page/route removed or redirected needs an explicit test proving the old URL/route degrades honestly (a redirect or a clear "moved" message), never a silent 404, matching this platform's own established "honest degradation" convention.

### Merge strategy
Continue squash-merge per PR (the pattern used for every Learning Centre sprint and confirmed still working for PR #20). Given the IA-consolidation nature of Phase 1, consider requesting an explicit before/after screenshot or route-map diff in each such PR's description — a text diff alone under-communicates the user-facing impact of a page removal/merge.

### Risk mitigation
- **Protected files stay protected.** None of the Phase 1-3 items above require touching `execution.ts`/`optionsMath.ts`/`risk.ts`/`autoExecution.ts`/`autoAdjustment.ts`. If any future-backlog item (Strategy Builder) is ever reopened, CLAUDE.md rule 1/2's maximum-scrutiny process applies without exception.
- **Consolidation work carries real UX risk** (removing/merging a page a user has bookmarked or relies on) — mitigate via redirects, not deletions, for at least one full release cycle.
- **New external dependencies** (a PDF library for export, an email provider for alerts) must clear this repo's own `pnpm-workspace.yaml` supply-chain policy (1-day minimum release age) and should be a named, explicit decision point in whichever sprint introduces them.
- **AI narration expansion (Phase 2 item 6)** must reuse `lib/ai-core`'s existing disclaimer-enforcement pattern without exception, per CLAUDE.md rule 6 — no new narration path may bypass `narrate()`/`narrateStream()`.

## Final Report

### Architecture summary
A mature, three-engine platform (Options Income/Trading/Investing) with a genuinely reused shared platform layer and a large "Institutional X Engine" composition tier built on top of it. The core engines are individually sound and well-layered; the accumulated surface area — 8-9 overlapping dashboards, 7+ coach surfaces, one confirmed duplicated analytics engine — is the platform's real technical debt, not its underlying logic.
