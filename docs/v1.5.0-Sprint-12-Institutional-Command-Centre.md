# v1.5.0 Sprint 12 — Institutional Command Centre

Branch: `v1.5.0-sprint-12-command-centre` (stacked on
`v1.5.0-sprint-11-platform-integration`)

## What this sprint adds

The **Institutional Command Centre** — the platform's new single daily
starting point, mounted at `"/"`. Per the sprint's own explicit
philosophy: "users should no longer think in terms of pages. They should
think in terms of workflow." The page orchestrates the platform's
existing modules (Research, Notebook, Strategy, Trade Plan, Trade
Journal, Performance, Portfolio, Learning) into one screen that answers,
every morning: what should I do today, what opportunities exist, what
trades need attention, what research is unfinished, what lessons should
I continue, what risks currently exist, and what should I review next.

**This sprint introduces zero new business logic, zero new database
tables, and zero new backend calculations.** The only genuinely new code
is a small client-side counting hook (`useWorkflowSnapshot.ts`, discussed
below) that calls already-existing fetch functions and counts their
results — everything else on the page is a direct, unmodified reuse of
an already-shipped generated hook or component.

## A pre-existing naming collision, found and resolved before writing any code

Before starting, direct investigation found this codebase already has
**two** command-center-shaped pages from earlier, unrelated work: `Home.tsx`
(mounted at `"/"`, a personalized, pinnable widget dashboard, from "Phase
10 — Institutional Platform Polish & Control Center") and `CommandCenter.tsx`
(mounted at `"/command-center"`, an Options-Income-Engine-focused executive
view, whose own on-page heading literally read "Institutional Command
Center" — American spelling, no "Centre"). Neither page provides the
9-stage Workflow Panel, cross-engine AI Daily Briefing, or Learning/Coach
panels this sprint's own spec explicitly asks for; both are genuinely
different in shape and purpose from what was requested.

Per the sprint's own "do NOT replace existing modules" instruction, the
resolution follows the **exact precedent this codebase already
established once before** (Home.tsx itself superseded the *original*
CommandCenter.tsx at `"/"` during Phase 10, using a "move, cross-link,
never delete" pattern — confirmed by reading Home.tsx's own header
comment):

1. The new page (`InstitutionalCommandCentre.tsx`) took over `"/"`.
2. `Home.tsx` — completely unmodified in logic, data, or behaviour —
   moved to `"/personal-dashboard"`, relabeled "Personal Dashboard" in the
   sidebar. Every widget, every test, every hook it uses is untouched.
3. `CommandCenter.tsx` — also completely unmodified in logic, data, or
   behaviour — was relabeled "Options Command Center" (both in the
   sidebar and its own on-page `<h1>`) to disambiguate it from the new
   Institutional Command Centre, and its own cross-link copy was updated.
4. All three pages now cross-link to each other, so nothing is
   discoverable-by-accident-only.

This is disclosed here in full because it's the single largest judgment
call this sprint made — not asked for verbatim in the kickoff message,
but a direct, necessary consequence of "do not duplicate existing
functionality" once the pre-existing pages were actually read.

## The one genuinely new logic: `useWorkflowSnapshot.ts`

The Workflow Panel needs "how many notebooks/draft strategies/ready
trade plans exist across all 3 coaches" — no such aggregate endpoint
exists, and building one would mean new backend business logic, which
this sprint's scope explicitly forbids. Instead, `useWorkflowSnapshot()`
calls the **exact same plain fetch functions** `useAiNotebooks`/
`useAiStrategies`/`useTradePlans` already call internally
(`listNotebooks()`/`listStrategies()`/`listTradePlans()` from
`notebooksApi.ts`/`strategiesApi.ts`/`tradePlansApi.ts`, Sprints 7-10),
once per coachId (`investing`/`trading`/`options`), and counts the
results client-side — zero new backend routes, zero re-implemented fetch
logic, deliberately bypassing the heavier CRUD hooks (which carry
selection/editing state meant for their own dedicated editor pages, not
a lightweight dashboard summary). A failed fetch for one coachId degrades
honestly to a zero contribution from that coachId, never a crash, never a
fabricated count (covered by a dedicated test).

"Journal Entries Outstanding" is the other small piece of honest,
disclosed cross-referencing: the last 20 closed options trades checked
against which already-fetched journal entries reference them via the
existing, unmodified `journal_entries.trade_id` loose reference — never a
fabricated count, deliberately bounded rather than an all-time audit.

## Workflow Panel

9 stage cards (Research → Notebook → Strategy → Trade Plan → Execution
(external broker) → Trade Journal → Performance Review → Portfolio →
Learning), each showing a real, reused status detail and a pending-count
badge when non-zero. "Execution (external broker)" is deliberately
non-clickable and carries no count — this platform genuinely has no
order-execution feature, matching Sprint 11's own `PlatformJourneyNav`
precedent for the same stage.

## AI Daily Briefing

`<DailyBriefingCard compact />` — the exact "Today's summary + Narrate My
Day" experience `CrossEngineDailyReport.tsx` already shipped (Phase 5,
Sprint 68), now embedded directly on the Command Centre. `compact` only
suppresses the redundant "Today — {date}" sub-heading, since the page's
own header already establishes the daily framing; the underlying
data/behaviour is byte-for-byte identical to the full page's own card.

## Dashboard layout

Top to bottom: greeting header (time-of-day-aware, using the signed-in
user's real session name/email — never a hardcoded name) → AI Daily
Briefing → Workflow Panel (9 stages) → Quick Actions (7 navigation
shortcuts + the existing global Ask AI Coach launcher) → a 2-column row
(Market Overview | Portfolio Snapshot) → a 2-column row (Learning Panel |
Coach Panel) → Notifications (real alerts + derived workflow action
items) → a fixed advisory-only disclaimer.

## Notifications — one unified feed, not two competing systems

The section merges two sources rather than inventing a new alert engine:
the real, backend-generated `platform_notifications` feed (watchlist
target crossings, risk-cap breaches — Phase 4, Sprint 56) and a
deterministic "Action Items" list computed from the Workflow Panel's own
already-computed pending counts (trade plans ready, strategies awaiting
review, journal entries outstanding). The two are visually distinguished
("Alert" vs. "Action" badges) so a user can always tell which is a
genuine backend-detected alert and which is a page-local workflow
reminder — never presented as the same thing.

## Future extensibility

- `useWorkflowSnapshot()`'s shape (`{loading, notebookCount,
  strategiesDraftCount, tradePlansReadyCount}`) can grow additional
  fields the same way, without touching any caller beyond the page that
  reads the new field.
- `COMMAND_CENTRE_QUICK_ACTIONS` is a plain array; adding an 8th action
  is a one-line change.
- Once Notebook/Strategy/Trade Plan gain their own dedicated routes (a
  disclosed limitation inherited from Sprint 11 — all three currently
  link to `/assistant`), only `PLATFORM_JOURNEY_STAGES`'s own `href`
  fields need to change; the Command Centre's rendering logic doesn't.
- A future sprint could compute "research stage" status from more than
  just watchlist count (e.g. open Research Terminal sessions), without
  changing this page's own `StageStatus` shape.
