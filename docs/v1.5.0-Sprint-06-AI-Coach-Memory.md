# v1.5.0 Sprint 6 — AI Coach Memory

Persistent conversation memory for the three existing conversational AI
Coaches — Trading AI Coach (`TradingResearch.tsx`'s embedded panel), Investing
AI Coach (`StockResearch.tsx`'s "Ask the AI Investment Analyst" panel), and
Options AI Coach (`Assistant.tsx`) — the first user-facing enhancement built
on top of the AI Coach Framework consolidated in Sprints 1–5. Portfolio
remains excluded: it has no conversational coach at all (Sprint 3's own
exhaustive finding, unchanged).

## Architecture

Sprint 6 is a purely additive persistence + UI layer on top of the existing,
unmodified conversation-streaming engine:

```
useSpecialistCoach(config, params, { onAnswered })   <- Sprint 3, UNCHANGED
        │  (built on useCoachConversation() — Sprint 2, UNCHANGED)
        │  onAnswered(turn) fires once per completed Q&A turn
        ▼
useCoachConversations(coachId)                       <- NEW, Sprint 6
        │  owns: conversation list, active conversation's message history,
        │        search term, create/rename/delete/select actions
        ▼
coachConversationsApi.ts                             <- NEW, Sprint 6
        │  plain-fetch client for the new REST surface
        ▼
POST/GET/PATCH/DELETE /coach-conversations[...]      <- NEW, Sprint 6
        ▼
ai_coach_conversations / ai_coach_messages tables     <- NEW, Sprint 6
```

**No existing backend route was modified.** `POST /trading/coach/ask[/stream]`,
`POST /stock-analyst/value-research/ask[/stream]`, and `POST /ai/chat[/stream]`
are byte-for-byte unchanged — their prompts, request/response shapes, and
narration logic are untouched. Persistence is driven entirely from the
frontend: each specialist coach page passes `onAnswered: (turn) =>
conversations.persistTurn(turn)` into `useSpecialistCoach(...)` — the exact,
pre-existing extension point `useCoachConversation.ts`'s own doc comment
already anticipated for "a page whose history is server-persisted."

The new `/coach-conversations` REST surface is deliberately kept outside the
OpenAPI/orval typed contract, mirroring the established precedent for
`coach-stream.ts` (SSE) and `explain-fetch.ts` (a plain-fetch client for an
additive, self-contained route) — this avoided a large, higher-risk codegen
regeneration for a single sprint. Every request body is still fully validated
in `routes/aiCoachConversations.ts` — via small, plain, hand-written checks
rather than a schema library (see the "A dependency-conflict finding" note
below for why zod specifically was avoided here); nothing is unvalidated.

**A dependency-conflict finding, caught during this sprint's own validation,
not anticipated in the pre-implementation plan:** the first draft of this
route validated request bodies with `zod` (mirroring the pattern most other
routes in this codebase use via generated `@workspace/api-zod` schemas).
`api-server` itself has no existing *direct* runtime dependency on `zod` —
only a transitive one through already-generated `@workspace/api-zod`
schemas — so adding one (`"zod": "catalog:"`) caused pnpm to re-resolve the
`zod` version it picks for `openai`'s and `@anthropic-ai/sdk`'s own optional
peer dependency *within `api-server`'s own dependency tree* from `4.4.3` down
to the catalog's `3.25.76`. That shift broke five completely unrelated,
pre-existing coach-LLM-mocking test files (`coach-level.test.ts`,
`coach-slowload.test.ts`, `coachLLM.envMigration.test.ts`,
`coachLLM.freeformPromptLoader.test.ts`,
`managementAnalysis.llmDimensions.test.ts`) — confirmed via a real `pnpm
install` before/after A/B comparison (`git stash` alone doesn't touch
`node_modules`, so an earlier attempt at this same comparison gave a false
"pre-existing" reading; only reinstalling against the reverted lockfile
actually proved the cause). Fixed by removing the `zod` dependency and its
import entirely, replacing the 3 zod schemas with small, equivalent
hand-written validation functions (`parseCreateConversationBody()`,
`parseUpdateConversationBody()`, `parseCreateMessageBody()`) — same
rejection behavior, zero new dependency, zero risk to any other package's
resolved dependency graph. `pnpm-lock.yaml` is now byte-identical to the
pre-Sprint-6 baseline.

## Storage model

Two new tables (migration `039_ai_coach_conversations.sql`), the smallest
schema that satisfies the sprint's requirements — neither pre-existing
message table (`ai_messages`, `trading_coach_messages`) supports grouping
messages into multiple, named, resumable conversations, and
`trading_coach_messages` specifically belongs to the separate, out-of-scope
"AI Trading Assistant" feature (v1.3.0).

**`ai_coach_conversations`** — one row per conversation thread:

| column       | type      | notes                                              |
|--------------|-----------|-----------------------------------------------------|
| `id`         | serial PK |                                                     |
| `user_id`    | uuid      | FK → `users.id`, `ON DELETE RESTRICT`               |
| `coach_id`   | text      | free text, restricted at the app layer to `"trading" \| "investing" \| "options"` |
| `title`       | text      | defaults to `"New conversation"`, auto-derived from the first user message |
| `archived`   | boolean   | default `false`                                     |
| `created_at` | timestamptz | default `now()`                                   |
| `updated_at` | timestamptz | default `now()`, bumped on every new message        |

Index: `(user_id, coach_id, updated_at DESC)` — the exact shape every list
query filters and orders by.

**`ai_coach_messages`** — one row per turn (a user question or an assistant
answer):

| column            | type      | notes                                    |
|-------------------|-----------|-------------------------------------------|
| `id`              | serial PK |                                            |
| `conversation_id` | integer   | FK → `ai_coach_conversations.id`, `ON DELETE CASCADE` |
| `role`            | text      | `"user" \| "assistant"`                    |
| `content`         | text      | the final, already-narrated message text  |
| `created_at`      | timestamptz | default `now()`                          |

Index: `(conversation_id, created_at ASC)` — the correct order to resume and
render a conversation.

`ON DELETE CASCADE` on `conversation_id` mirrors the established
`investing_holdings → investing_portfolios` precedent (Phase 13): a message
has no meaning independent of its conversation, so deleting a conversation
deletes its own messages outright.

## Conversation lifecycle

1. **New conversation** — clicking "New Chat" in the sidebar clears the
   active selection locally; it does **not** eagerly insert a database row.
   A row is created lazily, the first time a turn is actually persisted
   (`persistTurn()`), so idly clicking "New Chat" never clutters a user's
   conversation list with empty, never-used rows.
2. **First message → auto-title** — `POST /coach-conversations/:id/messages`
   checks whether this is the conversation's first message and its title is
   still the default sentinel (`"New conversation"`); if so, it derives a
   title from the message content (whitespace-collapsed, truncated to 60
   characters with an ellipsis) and updates it in the same request.
   "Automatic title generation from first prompt," in one place.
3. **Subsequent turns** — reuse the same conversation (tracked via a ref so
   `persistTurn()` always reads the truly-current selection, even though it
   fires asynchronously well after the render that set it).
4. **Resume** — clicking a conversation in the sidebar (`selectConversation`)
   fetches its messages (`GET /coach-conversations/:id/messages`, ordered
   oldest→newest) and renders them in place of the ephemeral session-only
   history the Trading/Investing panels previously showed.
5. **Rename** — inline edit in the sidebar, `PATCH /coach-conversations/:id`.
6. **Delete** — inline confirm-then-delete in the sidebar,
   `DELETE /coach-conversations/:id`; cascades its own messages. If the
   deleted conversation was active, the panel returns to the blank "new
   chat" state.
7. **Archived flag** — present in the schema and PATCH-able
   (`{archived: true}`), filtered out of the default list
   (`?includeArchived=true` to see archived conversations too) — included
   per the sprint's own explicit data-model requirement, though no dedicated
   "Archive" button was added to the sidebar since only "Delete conversation"
   was named as a UI feature; a hard delete already covers removal.

## Privacy considerations

- **Only the final, already-narrated question/answer text is ever stored.**
  `ai_coach_messages.content` is exactly what a user sees on screen — never
  an internal system prompt, never the grounding/context object a route
  assembles for the LLM, never a tool-execution trace.
- **No secrets are ever stored.** Neither table has any field that could
  hold an API key, session token, or credential.
- Proven by a dedicated backend test
  (`aiCoachConversations.route.test.ts`, "only the literal role/content a
  caller provides is ever stored") asserting the persisted row's own column
  set is exactly `{id, conversationId, role, content, createdAt}` — nothing
  more.
- Deleting a user still `RESTRICT`s (not cascades) on `ai_coach_conversations
  .user_id → users.id`, matching every other user-scoped table's
  established convention — a user's conversation history is not silently
  destroyed as a side effect of some other operation touching `users`.

## Isolation model

Every list/read/write is scoped by **both** `user_id` and `coach_id`
together:

- `GET /coach-conversations?coachId=X` filters
  `and(eq(userId), eq(coachId, X))` — a Trading conversation can never be
  listed under Investing or Options, and vice versa, for any pair.
- Every conversation row is created with a fixed `coach_id` at creation time
  (never mutable via `PATCH`), so a conversation can't "migrate" between
  coaches after the fact.
- Message/rename/delete endpoints are gated by `(id, userId)` ownership
  alone (matching this codebase's universal ownership-scoping convention
  since Sprint 7) — `coachId` is the **listing** filter, not a second access
  gate, since a conversation's `coach_id` is fixed and never
  cross-coach-guessable in practice. This distinction is explicitly
  documented and tested (`aiCoachConversations.route.test.ts`).
- Proven directly by a dedicated test: creating one conversation per coach
  for the same user, then asserting each coach's own list contains
  exactly its own conversation and no other coach's.
- Standard tenant isolation (a different user's conversation is a 404, not a
  403, for both "doesn't exist" and "isn't yours") is proven the same way
  every route in this codebase has been proven since Sprint 7.

## UI

New reusable `ConversationSidebar` component
(`src/lib/ai-coach/ConversationSidebar.tsx`), mounted identically by all
three specialist coach pages:

- **New Chat** button.
- **Search** input, filtering the visible list by title (case-insensitive,
  server-side via `?search=`).
- **Conversation list** — title, relative "last updated" time
  (`date-fns`' `formatDistanceToNow`), active-conversation highlight
  (`data-active="true"`).
- **Rename** — inline edit-in-place (pencil icon → text input → check/cancel).
- **Delete** — inline confirm-in-place (trash icon → check/cancel), no modal
  dialog needed for a first-cut shared component.

Each of the three coach pages was updated to:

1. Call `useCoachConversations(coachId)` alongside its existing
   `useSpecialistCoach(...)` call, wiring `persistTurn` into the latter's
   already-supported `onAnswered` option.
2. Render `ConversationSidebar` next to the chat panel.
3. Render the active conversation's persisted `activeMessages` (a flat
   user/assistant message list) instead of the coach hook's own ephemeral,
   session-only `history` array — plus the still-live `pendingQuestion` /
   `streamingAnswer` / `erroredReply` in-flight bubble from
   `useSpecialistCoach`, unchanged.

For the **Options AI Coach** (`Assistant.tsx`) specifically: this page
already had server-persisted history via the pre-existing, unmodified
`useGetAiMessages()` (a flat, ungrouped list backed by `ai_messages`). That
hook and the underlying `POST /ai/chat[/stream]` route are left completely
untouched and still write to `ai_messages` as a disclosed, harmless side
effect — the page's UI now reads exclusively from the new, conversation-
grouped store instead, which is the sole source of truth for the new
sidebar/resume experience going forward.

## Future enhancements

Not built this sprint, deliberately out of scope:

- A dedicated "Archive" button in the sidebar (the `archived` flag and its
  `PATCH`/`?includeArchived=` support already exist; only the UI affordance
  is missing).
- Per-coach conversation limits / auto-pruning of old empty conversations.
- Full-text search across message content (today's search only matches
  conversation titles).
- Folding the new `/coach-conversations` REST surface into the formal
  OpenAPI/orval contract, once a broader routes-contract sprint makes that
  worthwhile.
- Migrating the Options AI Coach's legacy `ai_messages` rows into the new
  `ai_coach_conversations`/`ai_coach_messages` model (today the old table is
  simply no longer read by the UI, not backfilled).
