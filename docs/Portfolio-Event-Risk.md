# Earnings & Event Risk Portfolio Overlay

This document covers the Earnings & Event Risk Portfolio Overlay as it
exists after the **Earnings & Event Risk Portfolio Overlay** sprint. It
is a companion to `docs/Alpaca-Paper-Trading-Architecture.md` §4.12,
which covers the same sprint at a higher level alongside the rest of the
Alpaca integration — read that document for the broader architectural
context.

---

## 1. What this is

A dedicated, read-only overlay, `/event-risk`, that shows every current
open position together with its own upcoming earnings, dividend, and
macro-event risk before its own expiration — and a portfolio-wide
summary of that exposure.

**Every event and risk-level figure reuses this platform's existing
event-risk engine unchanged. No execution logic was modified. No broker
writes occur. No orders are submitted. Event guidance is informational
only.** Every one of these is true by construction, not just by
convention, and is proven by this sprint's own test suite (see §7).

---

## 2. Investigation finding that shaped this sprint's whole design

Before writing any code, this sprint investigated `lib/eventRisk.ts` (the
existing, unmodified event-risk engine `execution.ts` and
`autoExecution.ts` already consult) and `optionsMath.ts`'s own
`EventRiskEvent`/`EventRiskType`/`EventRiskLevel` types in full. This
sprint's own request text lists "FDA decisions" and "product launches" as
example event categories — **neither has any data source anywhere in
this codebase.** `eventRisk.ts`'s own header comment describes itself as
"a deterministic, simulated economic/market event calendar" covering
exactly 7 categories:

| `EventRiskType` | Generated by |
|---|---|
| `earnings` | A per-symbol simulated earnings date, derived from `getSnapshot()`'s own `earningsInDays`. |
| `dividend` | A per-symbol simulated quarterly ex-dividend date, for a fixed set of dividend-paying symbols (`SPY`, `QQQ`, `IWM`, `AAPL`, `MSFT`, `NVDA`, `META`). |
| `fomc` | A formulaic monthly FOMC-meeting calendar (8 months/year, 3rd Wednesday). |
| `cpi` | A formulaic monthly CPI-release calendar (2nd Thursday). |
| `jobs` | A formulaic monthly nonfarm-payrolls calendar (1st Friday). |
| `economic` | A formulaic monthly PCE/retail-sales-style calendar (4th Thursday). |
| `news` | Defined in the type union and scored in `eventRisk.ts`'s own penalty table, but **never actually generated by any function** — a recognized-but-currently-inert category. |

Per this sprint's own explicit "do not invent new event models"
instruction, **FDA decisions and product launches are never fabricated.**
The API response's own `unsupportedEventCategories` field discloses this
gap directly, rather than silently omitting it — the frontend renders it
as its own "Event Categories" card, always visible.

## 3. Backend: `GET /portfolio/event-risk`

New files this sprint, both purely additive:
- `artifacts/api-server/src/lib/portfolioEventRisk.ts` —
  `buildPortfolioEventRiskOverlay(userId, now?)`.
- `artifacts/api-server/src/routes/portfolioEventRisk.ts` — the one new
  route.

`eventRisk.ts`, `optionsMath.ts`, `execution.ts`, `optionsMath.ts`,
`risk.ts`, `autoExecution.ts`, and `autoAdjustment.ts` are **not
modified** by this sprint — confirmed via `git diff --stat` at every
checkpoint.

**`lib/positionSizing.ts`'s `TradeRow` gained one additive field,
`expiration: string | null`** (populated in `currentOpenTrades()`),
because the shared row shape reused since the Trade Adjustment sprint
didn't previously carry it — needed here so `getEventRiskForSymbol()`
can be called with each position's own real expiration window. The 2
downstream synthetic-`TradeRow`-construction sites this change touched
(`positionSizing.ts`'s own `syntheticTradeRow()` and
`tradeAdjustmentPreview.ts`'s own `afterTradeRow`) were updated to
populate it from their own ticket's real `expiration` field — a
mechanical fallout from extending a shared type, the same pattern this
project's own history repeatedly documents, confirmed behavior-preserving
by both files' own pre-existing test suites passing unmodified.

### 3.1 Request

No request body — a plain `GET`, reading the calling user's own current
open portfolio (via `tenantScope.ts`'s established `getScopedUserId()`).

### 3.2 Response shape (abbreviated)

```
{
  positions: [{
    tradeId, symbol, strategy, quantity, portfolioWeightPct, expiration,
    eventStatus: "has_events" | "no_events" | "expiration_unknown",
    primaryEvent: EventRiskEvent | null,
    events: EventRiskEvent[],
    riskLevel: "none" | "low" | "medium" | "high",
    riskGuidance: "monitor" | "consider_review" | "consider_adjustment" | "no_immediate_event_risk",
    riskGuidanceLabel: string,
    confidence: "scheduled" | "simulated_estimate" | null,
    eventSource: "SIMULATED",
    lastUpdated: string,
  }],
  summary: {
    totalPositions, positionsWithEvents, positionsWithoutEvents, highRiskCount,
    within1Day, within3Days, within7Days, within14Days,
    aggregateExposurePct,
    highestRiskPosition: { tradeId, symbol, riskLevel } | null,
  },
  accountValue, credentialsConfigured, brokerConnected, lastBrokerCheckAt,
  eventRiskEnabled: boolean,
  unsupportedEventCategories: [{ category, label, reason }],
  generatedAt: string,
}
```

**Always returns `200`** — an empty portfolio honestly returns a
zeroed-out summary, never a fabricated 404 or error.

## 4. Per-position assessment — direct reuse, zero new risk logic

For every open position with a known expiration, `assessPosition()`
calls **`getEventRiskForSymbol(symbol, strategy, expiration, now,
enabled: true)`** — the exact same function `execution.ts` and
`autoExecution.ts` already call for their own event-risk gating,
unmodified. Its returned `EventRiskAssessment.events` (already sorted
soonest-first by the reused function itself) and `.level` are used
directly.

**`enabled: true` is deliberately always passed**, regardless of the
user's own `settings.eventRiskEnabled` toggle: that setting controls
whether event risk *blocks* trade execution/AutoPilot — a different
concern from whether this read-only analysis page is allowed to show
real event data. The response's own `eventRiskEnabled` field surfaces
the current setting value so the UI can disclose this distinction, but
never gates visibility on it.

**Quantity** is derived from the position's own stored legs via the
exact one-line technique the Trade Adjustment sprint already established
(`Math.max(1, ...legs.map(l => l.quantity || 1))`) — not a new
derivation.

**Portfolio weight** = `maxLoss ÷ accountValue × 100`, a genuine
percentage of the account, matching every other sprint's own established
`pctOfAccount` convention.

**Primary event** = `events[0]` (already soonest-first from the reused
engine) — the single event shown in the table's own Event Type/Date/Days
Remaining columns; the full list remains available for any position with
more than one.

**Risk Guidance** is a pure, exhaustive label mapping over the existing
`EventRiskLevel` enum — zero new risk scoring:

| `EventRiskLevel` | Guidance code | Label |
|---|---|---|
| `high` | `consider_adjustment` | Consider Adjustment |
| `medium` | `consider_review` | Consider Review |
| `low` | `monitor` | Monitor |
| `none` | `no_immediate_event_risk` | No Immediate Event Risk |

**These labels are purely informational.** No adjustment, order, or
execution action is ever triggered by this page — there is no submit
action anywhere on it.

**Confidence** is a disclosed classification of the primary event's own
*source shape*, not a fabricated new signal: market-wide macro events
(FOMC/CPI/jobs/economic) are generated on a formulaic, calendar-style
schedule → `"scheduled"`; symbol-specific events (earnings/dividend) are
derived from a per-symbol seeded estimate, not a real provider feed →
`"simulated_estimate"`.

**Event source** is always `"SIMULATED"` — there is no live
earnings/dividend/macro-calendar provider wired up anywhere in this
codebase, matching `eventRisk.ts`'s own header self-description exactly.

**A position with no `expiration` on record** (a defensive edge case —
every real position this platform can open always has one) honestly
reports `eventStatus: "expiration_unknown"` and `riskLevel: "none"`
rather than fabricating an assessment window.

## 5. Portfolio Summary

- **Positions with/without events**, **high-risk count** — straight
  counts over the per-position `eventStatus`/`riskLevel` fields.
- **Within 1/3/7/14 days** — counts **positions** (not raw events) whose
  own primary event's `daysAway` falls within each window.
- **Aggregate portfolio event exposure** — the sum of `portfolioWeightPct`
  across only the positions that carry at least one event — a genuine %
  of the account, not a raw dollar figure.
- **Highest-risk position** — the position with the greatest
  `EventRiskLevel` rank (`high` > `medium` > `low` > `none`), ties broken
  by the soonest primary event; honestly `null` when nothing in the
  portfolio carries any event risk at all.

---

## 6. Past events — never fabricated, honestly filtered by the reused engine

`eventRisk.ts`'s own `pushIfInWindow()`/`earningsEvent()`/`nextDividend()`
already filter out any event whose `daysAway < 0` — **the existing
engine never returns a past event, for any caller, including this
sprint's own.** This sprint's test suite proves this directly (every
event's `daysAway >= 0`, including for a defensively-constructed position
whose own expiration date has already passed) rather than merely
asserting it.

---

## 7. What this sprint did not change

- `eventRisk.ts`, `optionsMath.ts`, `execution.ts`, `risk.ts`,
  `autoExecution.ts`, `autoAdjustment.ts` — zero-line diff.
- `getEventRiskForSymbol()`/`assessEventRisk()` — unmodified, called
  as-is.
- No database migration.
- No broker write operations of any kind.
- No execution recommendation is ever generated — Risk Guidance labels
  are purely informational text, never wired to any adjustment/order
  action.
