# v1.5.0 General Availability (GA) Readiness — Sprint 23

This document is the GA companion to `docs/v1.5.0-Release-Candidate.md`
(Sprint 22). Per this sprint's own explicit scope, the RC document was
treated as the single source of truth for what needed resolving — no
additional work beyond its own findings was invented. This sprint resolved
every Critical/High item the RC review actually raised, standardised
error-state coverage on the RC's own highest-value flagged pages, ran a
security review, validated the platform's core end-to-end workflow chain,
and re-ran full validation.

## 1. Resolved blockers (this sprint)

| RC finding | Severity | Resolution |
|---|---|---|
| `portfolioEventRisk.test.ts` medium-risk macro-only event date-drift failure | High (real, deterministic pre-existing test failure) | **Fixed.** Verified the failure still reproduced against the current date. Root cause: the test's hardcoded event date had drifted into a different days-until-event bucket since the test was written — the same category of bug `docs/V1-Test-Resolution-Report.md` already resolved once before. Added a second, independently-verified frozen clock (`FROZEN_MEDIUM_MACRO_CLOCK`) scoped only to that one describe block, verified via a throwaway probe script before writing the fixture. No production risk-bucketing logic was changed. |
| `portfolioDashboard.test.ts` single-position `deltaSharePct` failure (expected `100`, received `0`) | High (real, deterministic pre-existing production bug, not just a test bug) | **Fixed.** Confirmed the underlying bug: a single position's own share of the portfolio's total absolute delta was falling back to a hardcoded `0` when that position's own net delta happened to be exactly `0` (a delta-neutral structure, e.g. an iron condor). A lone position is honestly 100% of the portfolio's own delta-risk concentration by definition, so `deltaSharePct` for a 1-position portfolio is now correctly `100` even when that position's delta nets to zero. The pre-existing 2+-position all-delta-neutral fallback (untested, unverified edge case) was deliberately left unchanged to avoid introducing new, unverified behavior beyond the one concrete, verified bug. |
| Error-state coverage gap (RC §6: "only ~44 of 86 sampled pages check `isError`") | Medium (UX, not a functional bug) | **Partially resolved, by design.** The RC itself disclosed that closing this gap in full means touching dozens of pages, out of a "polish, don't rebuild" sprint's own safe scope. This sprint closed the 3 highest-traffic pages in the RC's own named core-workflow chain that had a readily composable single error signal: `MarketIntelligence.tsx`, `OpportunityPipeline.tsx`, `PortfolioRiskIntelligence.tsx` — each backed by a composition hook (`useMarketIntelligence`, `useOpportunityPipeline`, `usePortfolioRiskIntelligence`) that was extended with a new `isError: boolean` field (OR'd across every underlying fetch it composes), then wired to an honest error banner on the page (`Couldn't load ... right now. Try refreshing the page.`) using the exact convention already established in `ExecutiveDashboard.tsx`. Remaining pages are disclosed below in §2, not silently dropped. |
| Icon-only buttons without accessible names (Sprint 22 audit finding) | Low–Medium (accessibility) | Already resolved in Sprint 22 — re-verified still correct this sprint, no regression. |
| N+1 query patterns (Sprint 22 audit finding) | Medium (performance) | Already resolved in Sprint 22 — re-verified still correct this sprint, no regression. |

No other Critical or High items were listed in the RC document's Known
Limitations (§6) or Production Readiness Checklist (§7) — every ⚠️ row in

- **`learningPaths.ts` size**, **duplicate CRUD stacks**
  (`journal.ts`/`tradingJournal.ts`, `tradePlans.ts`/`tradingTradePlans.ts`),
  and **`routes/backtest.ts`'s legacy fabricated-statistics path alongside

  disclosed as deliberate, non-urgent technical debt, not functional bugs.
  **Not GA blockers.**
- **A hand-copied hook pattern** across ~9 composition hooks — unchanged

  **Not a GA blocker.**

## 3. End-to-end workflow validation

The RC's own named core workflow chain — **Opportunity → Research →
Notebook → Strategy → Trade Plan → Decision → Execution Package → Trade
Journal → Portfolio → Learning** — was walked end-to-end this sprint:

- **Opportunity → Research**: `OpportunityPipeline.tsx` surfaces captured
  opportunities from Market Intelligence/Watchlists; each links out to
  `ResearchTerminal.tsx` (deep-linkable by symbol via `?symbol=`) rather
  than duplicating research UI — confirmed no dead link, no duplicated
  research logic.
- **Research → Notebook**: `ResearchTerminal.tsx`'s Notes tab and the
  Notebook system (`aiNotebooks.ts`/`notebooksApi.ts`) are the same
  underlying notebook entities referenced across Strategy/Trade Plan
  context-building (`buildNotebookContext()`, fixed for an N+1 pattern this
  sprint in Sprint 22) — confirmed a notebook created from Research surfaces
  correctly when later referenced from a Strategy or Trade Plan.
- **Notebook/Research → Strategy**: `StrategyWorkbench.tsx`/
  `StrategyFramework.tsx` both reference the same underlying
  `aiStrategies.ts`/`tradingStrategyFramework.ts` entities; strategy
  sections can cite a notebook/conversation by id — confirmed the link
  target resolves and does not 404.
- **Strategy → Trade Plan**: `tradePlansApi.ts`'s trade plans reference an
  optional `strategyId`; `TradeWorkspace.tsx` and
  `PortfolioRiskIntelligence.tsx`'s What-If Analysis both correctly filter
  to `status !== "draft"`/Ready-to-Execute plans only — confirmed a
  plan created from a Strategy correctly appears in both.
- **Trade Plan → Decision**: `DecisionEngine.tsx`/`decisionEngine.ts`
  consumes trade-plan-derived context (readiness, checklist completion)
  when building a decision snapshot — confirmed no orphaned reference.
- **Decision → Execution Package**: `InvestmentCommitteeWorkbench.tsx`'s
  memo generator (`investmentMemo.ts`) and `ExecutionLifecycleManager.tsx`
  both read from the same decision-snapshot/trade-plan data — confirmed a
  plan marked "Ready to Execute" is reachable from the Execution &
  Lifecycle Manager without a dead end.
- **Execution Package → Trade Journal**: executing/marking a trade plan
  executed sets `executedTradeRef`/`executedAt` on the trade plan record;
  `Journal.tsx`/`TradeHistory.tsx` reference trades by the same id space —
  confirmed the reference resolves.
- **Trade Journal → Portfolio**: `TradeHistory.tsx`/`Performance.tsx`'s
  realized-trade data and `PortfolioRiskIntelligence.tsx`/
  `PortfolioDashboard.tsx`'s live-position data are correctly kept
  separate (closed vs. open) with no double-counting — confirmed via
  existing test fixtures and code review (not modified this sprint).
- **Portfolio → Learning**: every workflow page's "Learn More" / AI Coach
  entry points resolve to a real `learningPaths.ts` topic key (this was
  the exact class of gap Phase 5/9 of prior sprints already closed and
  Sprint 21 extended with 4 new topics) — confirmed no broken
  `pathKey`/`topicKey` reference introduced this sprint.

**Broken-link audit (static, repo-wide):** every `href="/..."` literal
across `pages/`/`components/` (71 distinct paths) was diffed against every
registered `<Route path="...">` in `App.tsx` (101 routes, including the
`:pathKey`/`:topicKey` dynamic families under `/learn/paths/...`). One
apparent mismatch (`/learn/paths/platform-basics`) was confirmed to be a
false positive — it correctly matches the registered dynamic route
`/learn/paths/:pathKey`. **Zero genuinely broken internal links found.**

No dead ends or confusing transitions were found in the chain above. The
one disclosed friction point is the error-state gap in §2 — a failed fetch
on an unfixed page degrades quietly rather than routing the user
somewhere unexpected, so it is a quality issue, not a broken-workflow
issue.

## 4. Security review

Performed per this sprint's explicit Phase 4 checklist (Authentication,
Authorisation, Protected routes, Sensitive API endpoints, Role
assumptions, Environment configuration, Secrets handling). **No new
security system was introduced; this was a verification pass only.**

- **Authentication.** Real, session-based authentication (Better-Auth,
  Phase 1 Sprint 6) remains in place and unmodified. `REQUIRE_AUTH`
  correctly gates whether `requireAuth` is mandatory on business routes;
  confirmed, matching the RC's own disclosure, that it still defaults to
  unset/`false` — every unauthenticated request falls back to the shared
  legacy-owner identity rather than being rejected. **This is a deliberate,
  documented Phase 1 rollback switch, not a new finding** — re-confirmed
  present and correctly documented in `.env.example`. **Operational
  action required before any real multi-tenant GA deployment: set
  `REQUIRE_AUTH=true`** — carried into the deployment checklist below as a
  blocking pre-launch step, not a code change.
- **Authorisation / tenant isolation.** Every user-scoped route continues
  to resolve `getScopedUserId(req)` and scope its own queries by
  `userId`; the existing `tenantIsolation.test.ts`/`auth.test.ts` IDOR
  sweeps were not modified and were re-run clean as part of this sprint's
  final validation (§6). No new user-scoped table or route was added this
  sprint, so no new isolation surface exists to verify.
- **Protected routes / role assumptions.** `requireAdmin` (Phase 11, the
  first and only role-based check in this codebase) is used in exactly one
  route file, `routes/ops.ts` (the Operations Dashboard) — confirmed no
  other route relies on an undocumented role assumption, and confirmed
  `requireAdmin` still correctly distinguishes "no session" (401) from
  "authenticated but wrong role" (403), with no self-service
  admin-promotion endpoint anywhere in the codebase.
- **Sensitive API endpoints / secrets handling.** Traced the full
  Alpaca-credential path: `readAlpacaCreds()` (`alpacaProvider.ts`) always
  reads the true secret half (`ALPACA_API_SECRET`) from the server's own
  environment — it is **never** persisted to the database and **never**
  returned by any API response, confirmed by the settings schema (only a
  single `alpaca_api_key` text column exists — there is no
  `alpaca_api_secret` column anywhere) and by the frontend's own explicit
  user-facing disclosure text in `Settings.tsx` ("The API secret is never
  stored here... never displayed or returned by any endpoint"), which is
  accurate. The one value that *is* both stored and echoed back via
  `GET /settings` is the non-secret Alpaca Key ID half (`alpacaApiKey`) —
  by itself insufficient to authenticate to Alpaca's API (both halves are
  required together), returned only to the same authenticated, tenant-scoped
  user who saved it, and rendered in a password-masked (`type="password"`)
  input on the settings page for edit purposes — the same low-risk,
  common "show my own previously-saved integration key" pattern used
  throughout the industry, not a cross-tenant leak. This matches, and does
  not contradict, the RC's own "Security spot-check ... ✅ no issue found."
  **No fix required; no new finding raised.** The existing
  `recordAuditEvent()` discipline (Phase 1 Sprint 10) — which logs only
  changed field *names*, never values, specifically because `settings`
  includes `alpacaApiKey` — remains intact and unmodified.
- **Environment configuration.** `.env.example` was reviewed line-by-line;
  every variable is named-and-documented with no live secret values
  present, consistent with CLAUDE.md's own "no secret values in code,
  commits, or conversation" rule. No gaps found — rate limiting, CORS,
  auth, and provider credentials are all already documented with their
  correct defaults and operational implications.

**Conclusion: no Critical or High security finding.** The RC's own
"no issue found" security spot-check is re-confirmed, not overturned, by
this sprint's deeper look.

## 5. Deployment checklist

1. **Set `REQUIRE_AUTH=true`** in the production environment before
   exposing the platform to more than one real user — this is the single
   highest-priority operational action from this sprint's review. Verify
   with a real sign-in/sign-out round trip immediately after deploying.
2. Set `BETTER_AUTH_SECRET` to a freshly generated, never-committed value
   (`openssl rand -base64 32`) and `BETTER_AUTH_URL` to the real deployed
   origin.
3. Set `CORS_ALLOWED_ORIGINS` to the real deployed frontend origin if the
   frontend is served from a different origin than the API; leave unset
   only for same-origin deployments.
4. Confirm `DATABASE_URL` points at the production database and that every
   manual migration under `lib/db/manual-migrations/` has been applied in
   order (see `lib/db/manual-migrations/` directory listing — sequential,
   numbered, none skipped).
5. Set real provider credentials as needed: `ALPACA_API_KEY` +
   `ALPACA_API_SECRET` for broker connectivity (paper trading only — no
   live-trading credential path exists in this codebase), `FMP_API_KEY`/
   `ALPHA_VANTAGE_API_KEY` for live fundamentals data, `ANTHROPIC_API_KEY`
   (preferred) or `OPENAI_API_KEY` for AI coach narration. All are optional
   — every provider honestly degrades to a SIMULATED/mock/deterministic
   fallback when unset, never fabricating live data.
6. Tune `RATE_LIMIT_MAX_REQUESTS`/`AUTH_RATE_LIMIT_MAX_REQUESTS` for real
   expected traffic if the Phase 4 Sprint 52 defaults (300/60s general,
   20/60s auth) prove too tight or too loose once real usage data exists.
7. Run the full validation suite one final time in the exact deployment
   environment (§6 below) before flipping traffic over.
8. Confirm health checks (`/api/healthz`) are wired into your
   infrastructure's own uptime monitoring — they remain auth-exempt and
   rate-limit-exempt by design.

## 6. Rollback plan

- **Application-level rollback:** this entire Version 1.5.0 line is a
  stacked sequence of git branches/PRs (Sprints 1–23). Reverting to any
  prior sprint's merged state is a standard git revert/redeploy of the
  previous commit — no destructive migration exists in this range that
  would block a code-only rollback.
- **Database rollback:** every migration under
  `lib/db/manual-migrations/` in this sprint range is purely additive
  (new tables/columns, `NOT NULL` only on brand-new tables with zero
  existing rows) — there is no destructive schema change to roll back.
  Rolling back application code without rolling back the schema is safe;
  new columns/tables simply go unused by older code.
- **Kill switch as the fastest operational rollback for automation
  behavior:** if any concern arises around the auto-execution/
  auto-adjustment scheduler specifically, the existing `autoExecuteEnabled`/
  `autoAdjustEnabled` settings-level kill switches (Phase 1/3, unmodified
  by this entire v1.5.0 sprint range) remain the fastest, safest
  containment action — flip them off per-user via `PATCH /settings`
  without any deployment/rollback at all. This sprint touched zero lines
  of `execution.ts`/`optionsMath.ts`/`risk.ts`/`autoExecution.ts`/
  `autoAdjustment.ts` (confirmed via `git diff --stat`), so this
  containment path is untouched and known-good.
- **REQUIRE_AUTH as an emergency containment lever:** if a genuine
  tenant-isolation concern is ever suspected in production, setting
  `REQUIRE_AUTH=true` (if not already set) immediately requires a real
  session for every business route, closing the shared-legacy-owner
  fallback path without any code change or redeploy beyond an environment
  variable update and restart.

## 7. Support checklist

- **"A user reports they can't see their own data"** — verify
  `REQUIRE_AUTH` is set as expected for the deployment; check
  `platform_audit_log` for `auth.login`/`auth.login_failed` events for
  that user's account; confirm the user is signed in with the account they
  expect (a shared/legacy-owner fallback session looks identical to a real
  session in the UI when `REQUIRE_AUTH` is unset).
- **"A user's broker connection shows Not Connected"** — check
  `GET /api/broker/health` (or the Settings page's own "Check Connection"
  action); confirm `ALPACA_API_KEY`/`ALPACA_API_SECRET` are set in the
  server's own environment (the secret is never read from anywhere else),
  and that the user has entered a Key ID in Settings if not relying on the
  environment-level key.
- **"The automation scheduler doesn't seem to be running"** — check
  `GET /api/monitoring/status` (Phase 4 Sprint 74) for the `auto-execution`/
  `auto-adjustment` job health snapshot (`lastRunAt`/`consecutiveFailures`);
  confirm the affected user's own `autoExecuteEnabled`/`autoAdjustEnabled`
  switches and `executionMode` in Settings.
- **"AI Coach / narration isn't responding"** — confirm an
  `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` is set; every coach path
  correctly degrades to a deterministic template fallback when no key is
  configured (never an error page) — check whether the response looks like
  a template (shorter, more mechanical) vs. a genuine LLM narration to
  triage.
- **General escalation path:** anything that appears to require touching
  `execution.ts`/`optionsMath.ts`/`risk.ts`/`autoExecution.ts`/
  `autoAdjustment.ts` requires the project owner's own explicit,
  separately-approved decision, per CLAUDE.md rule 2 — no support action,
  however urgent, may modify these files without that approval.

## 10. GO / GO WITH CONDITIONS / NO-GO recommendation

**Evidence:**
- Every Critical/High functional defect the RC review actually identified
  has been resolved this sprint (§1) — two real, deterministic pre-existing
  bugs (one test-fixture date-drift, one genuine production edge-case bug
  in delta-share concentration scoring) are both fixed and verified.

  confirmed dead-end-free, with zero broken internal links found across a
  71-link/101-route repo-wide audit (§3).

  concern investigated in depth (the Alpaca Key ID being echoed back via
  `GET /settings`) was traced conclusively to a low-risk, industry-standard

  touch the database or any API response (§4).
- Full validation (typecheck, backend tests, frontend tests, production
  build) passes clean — see §11 below for exact figures.
- Protected files (`execution.ts`, `optionsMath.ts`, `risk.ts`,
  `autoExecution.ts`, `autoAdjustment.ts`) remain zero-line-diff across
  this entire sprint, confirmed via `git diff --stat`.

**Conditions (must be satisfied before a real, multi-tenant public GA
deployment — none require further engineering, only operational/
deployment-time action):**
1. **`REQUIRE_AUTH` must be explicitly set to `true`** before onboarding
   more than one real user — this is the single highest-priority item in
   this entire report. Left unset, every visitor silently shares one
   account.
2. `BETTER_AUTH_SECRET`/`BETTER_AUTH_URL`/`CORS_ALLOWED_ORIGINS` must be
   set to real, deployment-specific values (§5, items 2–3).
3. The disclosed error-state coverage gap (§2) should be prioritized as
   the first Version 2.0 UX-quality item, since it affects perceived
   reliability even though it never causes data loss or a broken
   workflow.
4. E2E coverage should be expanded before treating this as a
   fully-unattended, high-scale public release (§2/§9) — acceptable as-is
   for a beta/limited-audience GA.

Given all functional/security blockers are resolved and the remaining
items are operational configuration steps plus disclosed, non-blocking
UX/testing debt, **v1.5.0 is ready to proceed to General Availability for
beta users once the 4 conditions above are satisfied.**
