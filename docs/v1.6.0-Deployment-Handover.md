### 1.9 Rollback plan
See `docs/Production-Rollout-Plan.md` §6 for the full, blast-radius-tiered procedure. Summary, fastest-to-slowest:
1. **Code-only issue, no migration involved:** `git checkout <previous-tag-or-sha>`, `pnpm install --frozen-lockfile`, `pnpm run build`, restart the service. Fastest path; no data risk.
2. **Migration-involved issue:** do **not** attempt to auto-reverse a manual migration. Restore from the pre-deploy `pg_dump` (§1.3), then roll back code to match that dump's schema version.
3. **Anything touching the automation engines' behavior:** the kill switch (`autoExecuteEnabled`/`autoAdjustEnabled` in Settings) is the fastest possible containment action — flip it off first, investigate second. This is faster than any code rollback and carries zero deploy risk.
4. **Full environment rollback:** revert the VPS to the previous release's tagged commit entirely, matching the last known-good `pg_dump`.

## 3. Deployment Commands

Exact sequence for deploying `v1.6.0` (or `main` at its current commit, if the tag push is still pending — see §1.1):

```bash
# 1. Pull latest main
cd /path/to/BULK-SMS
git fetch origin
git checkout main
git pull origin main
git log -1 --format="%H %s"   # confirm 2bbebeac10dd42f143deaf59f27a0165c6cd5ffa or later

# 2. Back up the database BEFORE touching anything else
pg_dump "$DATABASE_URL" -F c -f "pre-v1.6.0-deploy-$(date +%Y%m%d-%H%M%S).dump"

# 3. Install dependencies
pnpm install --frozen-lockfile

# 4. Run migrations (idempotent — safe to re-run from a partial prior attempt)
for f in lib/db/manual-migrations/*.sql; do
  psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "$f"
done

# 5. Build
pnpm run build

# 6. Restart services (example for systemd; substitute your process manager)
sudo systemctl restart bulk-sms-api
# — or, if using PM2 —
pm2 restart bulk-sms-api --update-env

# 7. Verify health
curl -sf https://<host>/api/healthz
curl -sf https://<host>/api/monitoring/status | jq '.database.connected'

# 8. Rollback if required (fastest path — code-only, no migration involved)
git checkout <previous-known-good-sha-or-tag>
pnpm install --frozen-lockfile
pnpm run build
sudo systemctl restart bulk-sms-api   # or: pm2 restart bulk-sms-api

# — if a migration was involved, restore the pre-deploy dump instead of
#   attempting to hand-reverse the SQL:
# pg_restore --clean --if-exists -d "$DATABASE_URL" pre-v1.6.0-deploy-<timestamp>.dump
```

## Known Operational Risks

- **No managed backup service.** The only backup mechanism today is the manual `pg_dump` step in this checklist. A missed pre-deploy backup means a migration-related rollback has nothing to restore from.
- **Rate-limit and alert thresholds are generous defaults, not tuned against real traffic.** They were deliberately set >10x the busiest measured test-suite request volume as a starting baseline (Phase 4 Sprint 52's own disclosed rationale) — expect to revisit them once real beta usage data exists.
- **CORS origin is unset by default.** Until explicitly configured for the real production frontend origin, the API behaves same-origin-only in practice — this is safe by default, but must be a deliberate decision, not an oversight, before `REQUIRE_AUTH=true` goes live.
- **SIMULATED-only for live-data-dependent features.** No `FMP_API_KEY`/`ALPHA_VANTAGE_API_KEY`/live Alpaca trading credentials exist in this environment's history — every data-dependent feature runs in SIMULATED/Paper mode. This is the platform's current, intentional, unchanged state (per `docs/v1.6.0-Beta-Deployment-Plan.md`), not a deployment defect.
- **No process manager or reverse proxy config is bundled in this repo.** Both are real VPS-side setup work still to be done before `v1.6.0` can actually serve traffic — this document names the requirement but the actual systemd unit / PM2 ecosystem file / nginx config does not yet exist anywhere in this repository and must be authored at the infrastructure layer.
- **Frontend largest JS chunk is 585.16 kB** (pre-existing from the broader feature buildout, not new this release) — a slow first-load on poor connections is a known, disclosed characteristic, not a regression.
- **The `v1.6.0` tag/Release is not yet live on GitHub** (see Go/No-Go §2 above) — purely a traceability gap, not a code risk, but should be closed out promptly by whoever has real push access.
