# v1.5.0 Sprint 13 — Institutional Decision Engine

Branch: `v1.5.0-sprint-13-decision-engine` (stacked on
`v1.5.0-sprint-12-command-centre`)

## What this sprint adds

The **Institutional Decision Engine** — not another dashboard, but the
intelligence layer connecting every existing module into one institutional
decision process. It guides a user through a 10-stage workflow (Research →
Evidence Collection → Investment/Trade Thesis → Risk Assessment → Strategy
Selection → Trade Plan → Execution (external broker) → Trade Review →
Portfolio Impact → Continuous Learning), computes one reusable **Decision
Score**, and explains that score in full via a new **Decision Trace**
panel and an **AI Decision Coach** — both built explicitly so the engine
never becomes a black box.

**This sprint introduces zero new database tables and zero new backend
routes.** Everything is a client-side composition layer over data the
platform already computes and already stores — Trade Plans (Sprint 10),
Strategies (Sprint 9), the Trading Journal, the Value Watchlist/Trading
Positions/Open Trades, the Learning Centre, and the pre-existing
single-symbol Decision Engine (Phase 14). The only genuinely new logic is
pure, client-side scoring/explanation math in `lib/decisionWorkflow.ts`.

## The central design decision: a "Decision" IS an existing Trade Plan

The sprint's own 10-stage description reads like a new workflow entity.
Direct inspection of `tradePlansApi.ts` (Sprint 10) found the Trade Plan
already structurally models almost the entire requested workflow: its 21
sections span market context through a psychology checklist, and it
already has a real, computed checklist-completion engine
(`TradePlanDetail.checklistProgress`) plus a "what's missing" endpoint
(`getMissingTradePlanInformation`). Rather than inventing a second,
duplicate entity, **a "Decision" in this module is not a new stored
thing — it IS an existing Trade Plan, reused as-is.** This satisfies "Do
not duplicate storage. Reference existing data." literally, and needed
zero new database migration.

Stage → Trade Plan section mapping (all real, pre-existing
`TradePlanSectionKind`s from Sprint 10 — nothing invented):

| Stage | Trade Plan sections used |
|---|---|
| Research | `market_context` |
| Evidence Collection | `research_reference`, `notebook_reference` |
| Investment / Trade Thesis | `trade_thesis`, `bias`, `catalysts` |
| Risk Assessment | `stop_loss`, `maximum_risk`, `invalidation`, `risk_reward` |
| Strategy Selection | the linked `AiStrategy`'s own `getMissingSections()` completeness (Sprint 9) |
| Trade Plan | `TradePlanDetail.checklistProgress.progressPct` directly — the exact "Trade Plan Quality" signal the sprint's own scoring examples name, reused not recomputed |
| Execution | `TradePlan.executedTradeRef` |
| Trade Review | whether a Trading Journal entry references the executed trade |
| Portfolio Impact | whether the planned asset is already reflected in the Value Watchlist / Trading Positions / Open Options Trades (which one depends on the plan's own `coachId`) |
| Continuous Learning | whether the user has engaged with the one recommended lesson for the decision's weakest stage |

Execution, Trade Review, and Portfolio Impact are deliberately
**informational**, not scored — a pending decision hasn't been executed
yet, and treating that as a scoring deficiency would be misleading, not
honest guidance.

## A second naming collision, resolved differently from Sprint 12's

This codebase already has a page called "Decision Engine"
(`pages/DecisionEngine.tsx`, `/decision-engine`, Phase 14) — a genuinely
different thing: a single-symbol, deterministic Buy/Accumulate/Hold/
Reduce/Sell/Avoid verdict engine, reusing Business Quality/Competitive
Advantage/Valuation/Investment Committee/Tom Nash analysis for one ticker.
A blast-radius check (grep across `.tsx`/`.ts` and their `.test.tsx`/
`.test.ts` files) found it deeply embedded — 12+ non-test files, 11+ test
files reference it.

Given that depth, this sprint's resolution is **deliberately different
from Sprint 12's own "move, relabel, cross-link" pattern**: the
pre-existing Decision Engine is left **completely untouched** — not
renamed, not relabeled, not relocated. The new page instead takes an
entirely distinct name and route (`pages/DecisionWorkflow.tsx`,
`/decision-workflow`, "Decision Workflow" in the sidebar), and the two
cross-link to each other in their own header copy. Where useful, the
pre-existing Decision Engine's own verdict is reused directly — via
`useGetInstitutionalDecision()` — as one Evidence Panel reference card for
`investing`-coachId decisions (see below), satisfying "reuse existing
scoring systems" literally without touching or duplicating that engine's
own logic.

## Architecture

- **New pure logic module:** `lib/decisionWorkflow.ts` — the sprint's only
  genuinely new business logic, and deliberately kept free of any I/O:
  - `computeCoreDecisionStages(input)` — the 9 core stages (everything
    except Continuous Learning, which needs the core stages' own weakest
    result first).
  - `buildLearningStage(learning)` — the 10th stage, built separately to
    avoid a circular dependency (learning depends on knowing the weakest
    *other* stage).
  - `computeDecisionScore(stages)` — averages exactly the 6 stages the
    sprint's own Decision Score examples name (research completeness,
    evidence, thesis, risk assessment, strategy readiness, trade plan
    quality) — never review/portfolio/execution (informational, always
    `null` confidence) or learning (a coaching nudge, never a
    decision-readiness signal).
  - `weakestScoredStage(stages)` — the lowest-confidence scored stage,
    feeding both the AI Coach's "what to review next" and the Learning
    Centre recommendation.
  - `buildDecisionCoachNarrative(stages, score, weakest)` — deterministic
    text templating (never an LLM call of its own) producing the score
    explanation, **positive/negative contributing factors**, missing
    evidence, assumptions to test, risks to review, and the next
    recommended review — see "Explainability" below.
  - `buildDecisionTrace(stages)` — the new Decision Trace panel's data:
    one entry per stage, each naming its real source module, a real
    status label, and (for Thesis/Risk) the real assumption it rests on.
  - `buildLearningContext(coachId, weakestStageId, ...)` — looks up
    `DECISION_LEARNING_RECOMMENDATIONS`, a small, hand-verified registry
    of real `pathKey`/`topicKey` pairs from `learningPaths.ts` (verified
    the same way Sprint 11's `moduleLearnRegistry.ts` was — a throwaway
    backend test importing the real `LEARNING_PATHS` array, run once,
    then deleted — never guessed).
- **New orchestrating hook:** `lib/useDecisionWorkflow.ts` — two hooks:
  - `useDecisionWorkflow(tradePlanId)` — fetches the trade plan, its
    missing-information report, and its linked strategy (if any) via
    plain `useEffect`/`useState`, mirroring `useWorkflowSnapshot.ts`'s own
    established pattern (Sprint 12) since `tradePlansApi.ts`/
    `strategiesApi.ts` are plain-fetch modules, not generated TanStack
    Query hooks. Review/portfolio context is read from the platform's own
    already-existing generated hooks (`useListJournalEntries`,
    `useGetValueWatchlist`, `useListTradingPositions`, `useListTrades`).
    Composes all of the above into `stages`/`score`/`weakestStage`/
    `learning`.
  - `useActiveDecisionSummary()` — a lighter summary for the Command
    Centre's new "Decision in Progress" card: picks the user's single
    most recently updated non-terminal (draft/ready/watching) trade plan
    across all 3 coaches and computes its score.
- **New page:** `pages/DecisionWorkflow.tsx`, mounted at
  `/decision-workflow` — Trade Plan picker (or `?planId=` deep link,
  mirroring `DecisionEngine.tsx`'s own `?symbol=` precedent), the
  Decision Score card, the new Decision Trace panel, the 10-stage
  stepper, the Evidence Panel, the AI Decision Coach, and Continuous
  Learning integration.
- **Extended:** `pages/InstitutionalCommandCentre.tsx` (Sprint 12) gained
  a new "Decision in Progress" card, reusing `useActiveDecisionSummary()`
  — never a second, duplicate scoring formula.
- **Extended:** `lib/nav-items.ts`/`App.tsx` — a new "Decision Workflow"
  sidebar item and route, placed in the Home group alongside "Command
  Centre," with a disclosed cross-reference comment explaining the
  disambiguation from the pre-existing "Decision Engine" item.

  duplicate storage, only a reference count and a link back to
  `/assistant`.

  `useListTrades({status:"open"})`, selected by the plan's own `coachId`.
- **Performance Analytics** — not directly queried this sprint (Portfolio
  Impact only needs a held/watched boolean, not a full performance
  read) — a deliberate, disclosed scope boundary, not an oversight.
- **AI Coach** — `AskCoachLauncher` (Sprint L1), reused directly inside
  the AI Decision Coach panel; the trade plan's own existing AI narration
  actions (`reviewTradePlan`, `summarizeTradePlan`,
  `generateTradePlanRiskHighlights`, Sprint 10) are reused as one-click
  buttons — zero new AI/LLM code was written this sprint.
- **Learning Centre** — `ModuleLearnTrigger`/`ModuleLearnDrawer` (Sprint
  11), opened with the real, verified lesson recommendation.
- **Command Centre** — the new "Decision in Progress" card.
- **Watchlists** — see Portfolio, above.
- **Existing scoring systems** — the pre-existing Decision Engine's own
  verdict (Phase 14), surfaced as an Evidence Panel reference card for
  `investing` decisions, via `useGetInstitutionalDecision()`.

No duplicate business logic. No duplicate AI systems. No new database
tables or migrations.

## Decision workflow

Every stage displays, honestly, from real data:

- **Completion status** — `complete` / `partial` / `missing` /
  `not-applicable`.
- **Confidence** — a real 0-100% derived from Trade Plan section presence,
  the checklist engine's own `progressPct`, or the linked strategy's own
  completeness — `null` when a stage is genuinely not-applicable
  pre-execution (never a fabricated number).
- **Missing information** — the real, named section/checklist-item labels
  still absent, never a generic "incomplete."
- **Recommended next action** — a plain-English, deterministic sentence
  pointing at exactly what to do (and where — `href`s back to `/assistant`,
  `/trading-journal`, `/portfolio-dashboard`, or `/learn`).

## Scoring framework

The Decision Score averages the 6 stages the sprint's own examples name
(research completeness, evidence, thesis/assumption quality, risk
assessment, strategy readiness, trade plan quality) — each already-
computed, never recomputed. A stage with no confidence yet (e.g. no
strategy linked) is simply excluded from the average, not treated as a
zero. The result is a 0-100 score plus one of four honest labels
(Well-Prepared ≥80, Developing ≥60, Early Stage ≥35, Just Started below),
**always presented as guidance, never as a buy/sell recommendation** — the
Decision Score card's own copy states this explicitly, matching the
sprint's approved framing.

## Explainability — the Decision Trace and AI Decision Coach

A follow-up requirement, delivered mid-sprint: *"The Decision Engine
should never become a black box... never display a score without
explaining how it was derived."* Two concrete additions satisfy this,
both pure functions over already-computed data — zero new scoring, zero
new database reads:

- **Decision Trace panel** (`buildDecisionTrace()`, rendered by the new
  `DecisionTracePanel` component) — one entry per stage, always shown
  directly beneath the Decision Score, listing:
  - A ✓ / ⚠ / • icon and a real status label (e.g. "Strong," "Moderate —
    missing Bias," "Missing Market Context," "Not yet applicable" — never
    a bare "incomplete").
  - **Which module supplied the information** — an explicit "Source: ..."
    line naming the real Trade Plan section group, the Strategy Builder,
    the Trading Journal, or the Value Watchlist/Trading Positions/Open
    Trades, per stage.
  - **Which assumptions were made** — for the Thesis and Risk stages
    specifically (the two stages where "assumption" is a meaningful
    concept), a real sentence naming exactly what's assumed, derived from
    the stage's own missing-information list.
- **AI Decision Coach, extended** — beyond the pre-existing score
  explanation/missing-evidence/next-review text, the coach panel now
  explicitly lists:
  - **Which factors contributed positively** — every scored stage at
    ≥70% confidence, named with its real percentage.
  - **Which factors reduced confidence** — every scored stage below 50%,
    named with its real percentage and its real first missing item.

Together, a user can always answer, for any Decision Score shown
anywhere on the page: which factors pushed it up, which pulled it down,
which evidence is still missing, which module the platform read that
information from, and what a professional would look at next — nothing
appears without a real, inspectable reason behind it.

## Learning integration

`DECISION_LEARNING_RECOMMENDATIONS` maps `(weakest stage, coachId)` to a
real, pre-verified `(pathKey, topicKey, label)` from `learningPaths.ts` —
e.g. a weak Risk Assessment on a `trading` decision recommends
`trading-engine` / `trading-risk-management`; a weak Thesis on an
`investing` decision recommends `institutional-investing` /
`investing-margin-of-safety`. Not every `(stage, coachId)` pair has a
registered lesson — where none exists (e.g. `options` + a weak Research
stage), the Continuous Learning stage and panel honestly report no
recommendation, never a fabricated or mismatched one. Engagement is
detected against the user's own real `useGetLearningProgress()` recent
history — never a second, parallel progress-tracking system.

## Future extensibility

- **Performance Analytics reuse** — Portfolio Impact currently only
  checks held/watched status; a future sprint could surface realized
  P&L context for an already-executed decision via the existing
  Performance Analytics page's own data, without changing this sprint's
  scoring.
- **Additional learning recommendations** — `DECISION_LEARNING_RECOMMENDATIONS`
  is a plain, additive lookup table; filling in the remaining
  `(stage, coachId)` gaps (e.g. `options` + Research/Thesis) requires no
  code change beyond adding a verified entry.
- **Decision Trace as a shared component** — `DecisionTracePanel` /
  `buildDecisionTrace()` were built generically enough (operating on the
  same `DecisionStage[]` shape the stepper already uses) that a future
  cross-engine surface (e.g. the Institutional Command Centre) could
  reuse the trace panel directly for its own "Decision in Progress" card,
  rather than only the current single-line summary.
- **Multiple concurrent decisions** — today's picker shows every trade
  plan flat; a future sprint could group by coach or status once the
  number of in-flight decisions grows.
