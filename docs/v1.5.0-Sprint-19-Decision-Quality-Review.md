# v1.5.0, Sprint 19 — Institutional Decision Quality & Review Engine

## Non-negotiable statement

This is **not** another analytics dashboard, **not** another trade journal,
and **not** another performance report. It evaluates the **quality and
consistency of the decision-making process itself** — using evidence the
platform has already collected — so a user becomes a better decision maker,
not just a better trader. Trade outcome (P&L) is shown for context only and
is **never** part of the process-quality score.

## 2. The Decision Review model

`DecisionReview` (`lib/decisionReview.ts`) is the one reusable object every
completed decision produces:

```ts
interface DecisionReview {
  tradePlanId, tradePlanTitle, coachId, symbol,
  currentStage, executedAt, updatedAt,
  fields: DecisionReviewField[],       // the 11 fields below
  processQuality: { score, label, componentFieldIds },
  outcome: { state, realizedPnl, unrealizedPnl, openRisk },
  playbookAdherence: DecisionReviewPlaybookAdherence[],
  learningEngaged: boolean,
}

interface DecisionReviewField {
  id, label,
  status: "strong" | "adequate" | "weak" | "not-applicable",
  confidence: number | null,   // null = excluded from scoring
  evidenceSummary, evidenceHref,
}
```

`computeDecisionReview()` honestly returns `null` when the Trade Plan has
no linked execution yet — there is no completed decision to review.

### The 11 fields and exactly where each one's evidence comes from

| # | Field | Evidence source | New logic? |
|---|---|---|---|
| 1 | Research Quality | Decision Engine's `research` stage confidence | No — direct reuse |
| 2 | Evidence Completeness | Decision Engine's `evidence` stage confidence | No — direct reuse |
| 3 | Alternative Scenarios Considered | Trade Plan's own `confirmation_rules` section presence | **New** — honest presence check |
| 4 | Strategy Alignment | Decision Engine's `strategy` stage confidence | No — direct reuse |
| 5 | Risk Planning | Decision Engine's `risk` stage confidence | No — direct reuse |
| 6 | Position Sizing | Trade Plan's own `position_size_notes` section presence | **New** — honest presence check |
| 7 | Decision Rationale | Pre-trade thesis stage confidence **vs.** post-trade Journal `thesis`/`entryReasoning` | **New** — genuinely new pre/post comparison |
| 8 | Execution Discipline | Trade Plan's own `checklistProgress` required-items ratio | **New** — honest reuse of existing checklist state |
| 9 | Journal Completeness | `TradeLifecycleRecord.journalStatus.state` | No — direct reuse |
| 10 | Post-Trade Reflection | Same `journalStatus.state`, a **stricter** threshold (only "reviewed" counts) | No new formula — a second read of the same enum |
| 11 | Portfolio Impact | `TradeLifecycleRecord.performanceStatus` | No — direct reuse, **confidence always `null`** |

Four fields are genuinely new (3/6/7/8), and each is explicitly disclosed in
`lib/decisionReview.ts`'s own header comment as the *closest honest existing
proxy* for what was asked — never a fabricated score standing in for data
the platform doesn't actually have.

## 3. The Decision Quality Framework — process, never outcome

The approved scope's central instruction: **evaluate process quality, never
trade outcome. Never reward lucky outcomes. Never punish disciplined
losses.**

This is enforced **structurally**, not just by convention:

```ts
// Deliberately EXCLUDED from process-quality scoring (confidence always
// null) — this field shows real dollar figures for context only.
const outcomeField: DecisionReviewField = {
  id: "portfolio-impact",
  confidence: null,   // <-- hardcoded, never computed from P&L
  ...
};
```

`processQuality.score` is the average of every field whose `confidence` is
**not** `null`. Because `portfolio-impact`'s confidence is permanently
`null`, it can never enter that average — a decision that lost money but
was fully documented and disciplined scores identically to an equally
well-documented winner. `decisionReview.test.ts`'s "never rewards lucky
outcomes" test proves this directly: two fixtures differing only in
`realizedPnl` (+$5,000 vs. -$5,000) produce byte-identical
`processQuality.score` values.

The framework's own named evaluation criteria map onto the fields as
follows:

- *Was the thesis documented?* → Research Quality, Decision Rationale
- *Were invalidation rules defined?* → Alternative Scenarios Considered
- *Was risk acceptable?* → Risk Planning, Position Sizing
- *Was the playbook followed?* → Playbook Adherence (a separate,
  non-scored breakdown — see §5)
- *Were portfolio limits respected?* → surfaced via the Related Knowledge
  card's connection to the bound Trade Plan, not a new limit check
  (portfolio-limit checking already exists in Portfolio & Risk Intelligence
  and is deliberately not re-implemented here)
- *Was evidence sufficient?* → Evidence Completeness
- *Were assumptions challenged?* → Alternative Scenarios Considered
- *Was journaling completed?* → Journal Completeness, Post-Trade Reflection

`SCORE_LABEL_THRESHOLDS` produces one of 4 honest labels — Excellent
Process (≥80), Solid Process (≥60), Developing Process (≥35), Needs
Attention (<35) — from the averaged score, never a qualitative judgment
invented independently of the number.

## 4. AI Decision Review Coach — coaches, never judges

`buildDecisionReviewCoachNarrative()` is a pure function, zero LLM calls,
mirroring `buildPlaybookCoachNarrative()`'s exact established shape
(Sprint 18):

- **Strong parts** / **weak parts** — every field whose `status` is
  `"strong"`/`"weak"`, rendered as `"<label>: <evidenceSummary>"`. No field
  is ever described using outcome language ("won," "lost," "good trade,"
  "bad trade") — `decisionReview.test.ts` proves this directly.
- **Missed opportunities** — every incomplete Playbook stage tied to this
  decision.
- **Institutional best practice** — one fixed, disclosed sentence
  explaining *why* process and outcome are scored separately (the only
  place in the narrative that legitimately uses the words "won"/"lost" —
  as meta-commentary about the philosophy itself, not a judgment of this
  specific decision).
- **Recurring patterns** — either a real, evidence-backed sentence citing
  a genuinely repeated Playbook deviation (see §6), or an honest "not
  enough reviewed decisions yet" fallback — never fabricated from a single
  data point.
- **Recommended learning** — points at the weakest field's own evidence
  link.

## 5. Playbook integration

Each reviewed decision's `playbookAdherence` is computed by calling Sprint
18's own `computePlaybookProgress()` once per trade-lifecycle-bound
playbook (Trade Planning, Decision Review, Execution Preparation, Trade
Management, Post-Trade Review), bound to that exact Trade Plan id via a
minimal `PlaybookProgressContext`. The result — completed/total stage
counts and the titles of any incomplete stages — is surfaced verbatim on
the Decision Quality Review page's Playbook Adherence card and fed into the
AI Coach's "missed opportunities." **Playbooks are never modified here —
only read**, consistent with the approved scope's explicit instruction.

## 6. Knowledge Graph integration

`RelatedKnowledgeCard` calls the Knowledge Graph's own already-exported
functions directly against the node id `trade-plan:${tradePlanId}`:

- **Related Research** — `relatedEntitiesWithinTwoHops(graph, nodeId, "notebook")`
- **Related Strategies** — `relatedEntities(graph, nodeId)` filtered to
  `"strategy"` nodes
- **Related Journals** — same, filtered to `"journal-entry"` nodes
- **Portfolio Reviews** — same, filtered to `"portfolio-review"` nodes
- **Recurring Patterns (platform-wide)** — `discoverPatterns()`, the exact
  same platform-wide pattern detector the Knowledge Graph page itself uses
- **Learning Completed** — `review.learningEngaged`, read directly from
  `TradeLifecycleRecord.learning`

Every recommendation traces to one of these real function calls — none is
synthesized independently by this page.

## 7. Trend Analysis — transparent, evidence-linked, never fabricated

`lib/decisionReviewTrends.ts`'s `computeDecisionQualityTrends()` splits a
caller-supplied, chronologically-sorted `DecisionReview[]` into an earlier
half and a later half, and compares the average confidence across a
related field group for each half:

| Trend | Component fields |
|---|---|
| Research Discipline | Research Quality, Evidence Completeness, Alternative Scenarios |
| Risk Management | Risk Planning, Position Sizing, Execution Discipline |
| Journal Completion | Journal Completeness, Post-Trade Reflection |
| Strategy Alignment | Strategy Alignment, Decision Rationale |

Honesty guarantees, each directly tested:

- Fewer than `MIN_REVIEWS_FOR_TREND` (4) reviewed decisions →
  `"insufficient-data"`, `earlierAverage`/`laterAverage` both `null` —
  never a trend claimed from too little evidence.
- A move smaller than `STABLE_BAND` (10 points) is classified `"stable"`,
  never inflated into a false "improving"/"declining" read.
- Every `DecisionQualityTrend.evidence` array lists the exact
  `tradePlanId`s behind it — a trend is never shown without its
  supporting decisions being individually citable.

`computeRecurringPlaybookDeviations()` buckets every reviewed decision's
own incomplete Playbook stages by `${playbookId}:${stageTitle}`, and
honestly reports nothing (`[]`) until the **same** stage of the **same**
playbook has been left incomplete across `MIN_OCCURRENCES_FOR_RECURRING`
(2) or more reviewed decisions — a single one-off gap is never labeled
"recurring," and two different playbooks that happen to share a stage
title (e.g. "Confirm Readiness") are never conflated.

## 8. Command Centre integration

`DecisionQualityCard` (`pages/InstitutionalCommandCentre.tsx`), reusing
`useDecisionQualityEngine()` directly with zero new calculation:

- Recently Reviewed Decisions (last 3, title/symbol/score)
- Best Process Improvements (trends currently reading `"improving"`)
- Recurring Issues (top 2 recurring Playbook deviations)
- Pending Reviews (count of executed-but-not-yet-fully-reviewed decisions)
- Recommended Next Review (the longest-pending decision)

Kept concise per the approved scope, mirroring `PlaybooksCard`'s exact
layout discipline.

## 10. Explicitly out of scope this sprint

Per the approved scope: no auto trade ratings, no AI trade predictions, no
duplicate journal system, no duplicate performance analytics, no hidden AI
scoring, no new portfolio engine. Every score in this module traces to a
field the user can see and a evidence link they can click through to —
nothing is computed silently.
